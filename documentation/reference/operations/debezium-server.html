Debezium provides a ready-to-use application that streams change events from a source database to messaging infrastructure like Amazon Kinesis, Google Cloud Pub/Sub, Apache Pulsar, Redis (Stream), or NATS JetStream. For streaming change events to Apache Kafka, it is recommended to deploy the Debezium connectors via Kafka Connect.

Installation

To install the server download and unpack the server distribution archive:

  • Debezium Server distribution

The above links refers to the nightly snapshot build of the Debezium main branch. If you are looking for a non-snapshot version, please select the appropriate version of this documentation in the menu to the right.

A directory named debezium-server will be created with these contents:

The server is started using run.sh script, dependencies are stored in the lib directory, and the directory config contains configuration files.

In case of using the Oracle connector you will have to add to the lib directory the ORACLE JDBC driver (if using XStream also the XStream API files), explained here: Obtaining the Oracle JDBC driver and XStream API files

Configuration

Debezium Server uses MicroProfile Configuration for configuration. This means that the application can be configured from disparate sources like configuration files, environment variables, system properties etc.

Configuration properties that contain the $ character are normally interpreted by Quarkus for property expansion. If a property value includes a $ character as a prefix, such as ${my.property}, the Microprofile configuration parser determines that the value is a property expression and attempts to expand it.

To prevent the parser from attempting to expand values that use this syntax, escape the $ prefix with a second $ character; that is, provide the value as $${my.property}. The value of the property is then passed to Debezium as ${my.property}.

The main configuration file is config/application.properties. There are multiple sections configured:

  • debezium.source is for source connector configuration; each instance of Debezium Server runs exactly one connector

  • debezium.sink is for the sink system configuration

  • debezium.format is for the output serialization format configuration

  • debezium.transforms is for the configuration of message transformations

  • debezium.predicates is for the configuration of message transformation predicates

An example configuration file can look like so:

debezium.sink.type=kinesis
debezium.sink.kinesis.region=eu-central-1
debezium.source.connector.class=io.debezium.connector.postgresql.PostgresConnector
debezium.source.offset.storage.file.filename=data/offsets.dat
debezium.source.offset.flush.interval.ms=0
debezium.source.database.hostname=localhost
debezium.source.database.port=5432
debezium.source.database.user=postgres
debezium.source.database.password=postgres
debezium.source.database.dbname=postgres
debezium.source.topic.prefix=tutorial
debezium.source.schema.include.list=inventory

In this configuration file example:

  • The sink is setup for AWS Kinesis in region eu-central-1

  • The source connector is setup for PostgreSQL using the default Debezium decoderbufs plugin. If using PostgreSQL’s built-in pgoutput plugin, set debezium.source.plugin.name=pgoutput

  • The source connector is set to capture events from a schema named inventory. If you want to capture all changes in the database, remove this line. Otherwise, update this line to correspond to your preferred schema or tables.

  • The source offset will be stored in a file named offsets.dat in the data directory. Note that you might need to create this directory to prevent an error on startup.

Format configuration

The message output format can be configured for both key and value separately. By default the output is in JSON format but an arbitrary implementation of Kafka Connect’s Converter can be used.

Property Default Description

debezium.format.key

json

The name of the output format for key, one of json/jsonbytearray/avro/protobuf/simplestring/binary.

debezium.format.key.*

Configuration properties passed to the key converter.

Redis Configuration Examples

The following examples show complete application.properties configurations for connecting Debezium Server to a Redis sink in both single-instance and cluster deployment modes.

Single Instance Mode

Use the following configuration when connecting to a single Redis instance for sink, offset storage, and schema history.

# Sink configuration
debezium.sink.type=redis
debezium.sink.redis.address=localhost:6379
debezium.sink.redis.password=password
debezium.sink.redis.cluster.enabled=false

# Offset storage configuration
debezium.source.offset.storage=io.debezium.storage.redis.offset.RedisOffsetBackingStore
debezium.source.offset.storage.redis.address=localhost:6379
debezium.source.offset.storage.redis.password=password
debezium.source.offset.storage.redis.cluster.enabled=false

# Schema history storage configuration
debezium.source.schema.history.internal=io.debezium.storage.redis.history.RedisSchemaHistory
debezium.source.schema.history.internal.redis.address=localhost:6379
debezium.source.schema.history.internal.redis.password=password
debezium.source.schema.history.internal.redis.cluster.enabled=false
Cluster Mode

Use the following configuration when connecting Debezium Server to a Redis Cluster, specifying multiple node addresses for sink, offset storage, and schema history.

# Sink configuration
debezium.sink.type=redis
debezium.sink.redis.address=redis-node-1:7001,redis-node-2:7002,redis-node-3:7003
debezium.sink.redis.password=password
debezium.sink.redis.cluster.enabled=true

# Offset storage configuration
debezium.source.offset.storage=io.debezium.storage.redis.offset.RedisOffsetBackingStore
debezium.source.offset.storage.redis.address=redis-node-1:7001,redis-node-2:7002,redis-node-3:7003
debezium.source.offset.storage.redis.password=password
debezium.source.offset.storage.redis.cluster.enabled=true

# Schema history storage configuration
debezium.source.schema.history.internal=io.debezium.storage.redis.history.RedisSchemaHistory
debezium.source.schema.history.internal.redis.address=redis-node-1:7001,redis-node-2:7002,redis-node-3:7003
debezium.source.schema.history.internal.redis.password=password

No default value

5000

(Optional) Specifies the maximum time, in milliseconds, that Debezium waits for acknowledgment from the NATS server after it sends a batch of messages for asynchronous processing. During asynchronous processing, each message is published with a timeout specified by asyncTimeoutMs.

Mapping definition

In the InstructLab sink configuration, you can set properties to specify how Debezium Server maps fields in event messages to question, answer, and contextattributes in an InstructLab qna.yml file.

For each attribute type that you want to populate in the qna.yml file, you specify a mapping prefix that determines the message field from which Debezium extracts the value. You can specify the following prefix values:

Value

If you prefix a mapping definition with the string value:, Debezium extracts the value of the specified field from the incoming event payload. For example, to populate an InstructLab question attribute with the value of the abc field in the event payload, set the debezium.sink.instructlab.taxonomy.<name>.question property to value:abc. When Debezium processes the message it takes the value of the payload field abc and adds it as a question attribute in the qna.yml file.

For events that have a Debezium-structured payload, Debezium extracts the specified field from the after section of the payload. If the event is flattened, the field is sourced directly from the event’s value.

Header

If you prefix a mapping definition with the string header:, Debezium extracts the value of the specified header field of the incoming event message. For example, if you specify the mapping header:h1, when Debezium detects a header with the name h1 in a source message, it extracts the value of the h1 field.

Constant

If the mapping definition does not include the header: or value: prefixes, when Debezium detects instances of the specified value in incoming messages, it treats them as constants, and uses them as-is. Use this option when you want to map the value of a specific static constant to an attribute in the qna.yml file.

Envelope row contract

Set debezium.sink.zerobus.payload.mode to envelope to preserve the change event for downstream materialization instead of mapping it directly onto the target table columns. The max.record.bytes, json.flexible.fields.encoding, idempotency.mode, tombstone.handling.mode, and filter.* properties apply only to this payload mode.

JSON and Protobuf envelope records expose the same logical fields:

Field Description

target_table

The fully qualified Unity Catalog table to which the sink routes the record.

destination

The original Debezium destination before the sink resolves the target table.

partition

The event partition, when one is present.

operation

One of create, read, update, delete, truncate, message, change, or tombstone. The sink uses change when the source value does not contain a recognized Debezium operation.

idempotency_key

A deterministic sha256:<64 hexadecimal characters> event identity when idempotency.mode is source. Use this field to deduplicate records after an at-least-once replay.

key

The original serialized record key.

value

The original serialized Debezium change-event value. The value is null for a tombstone.

source_position

A map containing source partition and offset entries. Entry names use the partition. and offset. prefixes.

headers

The record headers, ordered by header name.

For JSON records, json.flexible.fields.encoding controls whether key, value, source_position, and headers are canonical JSON strings or nested JSON values. For Protobuf records, the sink supplies the descriptor to Zerobus and encodes these flexible fields as canonical JSON strings.

The sink applies configured include filters in the following order: destination, operation, header, and value. Every configured regular expression must match the complete selected value. An event that does not match is skipped and is considered processed when the rest of the batch succeeds. If filter.operations is configured, a tombstone is ingested only when the allowlist includes tombstone, even if tombstone.handling.mode is event.

The sink provides an at-least-once delivery guarantee. For each contiguous target-table group, the sink serializes and validates every record before ingestion, ingests the group, and waits for Zerobus to acknowledge the final record. The sink commits source offsets only after every target-table group in the batch succeeds. If a later group fails, an earlier acknowledged group can be replayed because the source batch remains uncommitted. Use idempotency_key to deduplicate such replays downstream.

Kafka route

As an alternative to the zerobus and zerobus-rest routes, you can reuse the built-in kafka sink to write to the Zerobus Kafka-compatible endpoint. This route uses the standard Kafka producer with SASL_SSL and the OAUTHBEARER mechanism. Authentication is handled by io.debezium.server.databricks.zerobus.ZerobusOAuthBearerLoginCallbackHandler, which performs the OAuth token exchange and attaches the Unity Catalog authorization details that Zerobus requires.

Because this route uses the generic kafka sink rather than the Zerobus sink, the data type normalization that the Data type mapping section describes does not apply. Instead, the emitted JSON must match the target Delta table schema, which requires the source-side and format settings that the following sections describe. Zerobus is partitionless, and it ingests only the record value. It does not persist record keys, headers, partition assignments, or timestamps.

The Kafka-compatible endpoint must be enabled for the workspace. If it is not enabled, authentication fails with Access denied: feature "Zerobus Ingest Kafka Endpoint" is not enabled for workspace "<workspace-id>". Error Code: 4062.

Record format for the Kafka route

Zerobus accepts a record value only if it is a JSON object whose fields match the target Delta table schema. A record that does not match is rejected with InvalidRecordException: This record has failed the validation on broker and hence will be rejected. To satisfy the requirement, configure the following options in addition to the producer properties:

Property Description

debezium.transforms

Apply the ExtractNewRecordState SMT so that the emitted record is a flat row rather than a change event envelope. Optionally apply the RegexRouter SMT to map the topic name to the fully qualified name of the target table.

debezium.format.value.schemas.enable

Must be set to false. Otherwise, the JSON converter wraps each value in a {"schema": …​, "payload": …​} envelope, which does not match the table schema.

debezium.source.decimal.handling.mode

Must be set to string. Zerobus rejects a JSON number for a DECIMAL column, and the default precise mode emits a Base64-encoded byte array. The string mode emits the exact decimal value as a JSON string, which Zerobus accepts.

debezium.source.time.precision.mode

Use the default adaptive mode, which emits a TIMESTAMP column as the number of microseconds since the epoch. Zerobus rejects an ISO-8601 string for a TIMESTAMP column, and it interprets a numeric value as microseconds. Because of the latter, the connect mode, which emits milliseconds, silently stores an incorrect instant.
Tuning throughput on the Kafka route

Throughput on the Kafka route is bound by network round trips rather than by local processing, because Zerobus acknowledges each request from the region in which the workspace runs. When the default producer settings are active, the number of records that the service ingests per second is approximately equal to the number of in-flight requests, multiplied by the number of records per request, and divided by the request latency. As a result, a pipeline that produces one record at a time spends most of its time waiting.

You can modify the default behavior by configuring the producer properties in the following table. Optimal values for these settings depend on the latency between the service and the workspace. Use the values in the table as starting points and adjust them based on latency data. To find the request latency of a running pipeline, read the request_latency_avg attribute of the standard kafka.producer:type=producer-metrics MBean, and to confirm that batching takes effect, read records_per_request_avg.

Property Suggested value Description

debezium.sink.kafka.producer.linger.ms

100

Specifies how long the producer waits to send requests. Requests accumulate until the configured interval passes.

Set the value to 0 to remove the delay interval so that the producer sends each request as soon as possible. When the property is set to 0, the producer sends requests even if they contain a small number of records. Because each request incurs the overhead of a full network round trip, when the producer has a high number of records to process, a 0 value can result in lower throughput.

Set a value greater than 0 if you want the producer to wait between sending requests. Setting a value greater than 0 can improve throughput, because the producer batches more records per request.

In a change data capture pipeline, the end-to-end latency is typically much greater than the delay introduced by this setting, so the additional wait is usually negligible.

debezium.sink.kafka.producer.batch.size

1048576

Specifies the maximum size, in bytes, of a single batch. If linger.ms is set, set this option if you want the producer to send batches after their size reaches the configured limit. This setting overrides the linger.ms setting to allow the producer to send batches before the end of the configured wait time. Zerobus rejects records larger than 10 MB, so a batch size of 1 MB leaves ample headroom.

debezium.sink.kafka.producer.max.in.flight.requests.per.connection

10

Specifies the maximum number of unacknowledged requests that the producer can send before it receives a response. Increasing the value can improve throughput by allowing the producer to send additional requests before it receives acknowledgements from earlier requests. However, increasing the value can also result in records being delivered out of order if requests are retried.

Zerobus is partitionless and provides an at-least-once delivery guarantee, so strict record ordering is not guaranteed regardless of how you configure this property.

In standard Kafka environments where idempotence is enabled, max.in.flight.requests.per.connection must not exceed 5, because the idempotent producer only guarantees ordering and exactly-once semantics for up to five in-flight requests. The Kafka route for the Databricks Zerobus Ingest sink requires enable.idempotence=false, so you can set this property to a value greater than 5.

Monitoring

You can use JMX metrics and connector log output to monitor the operational status and performance of the Debezium Databricks Zerobus Ingest sink.

The Debezium Databricks Zerobus Ingest sink supports the following delivery routes: zerobus (gRPC), zerobus-rest (REST), and the Kafka route. All three routes expose sink metrics over JMX under the object name debezium.zerobus:type=connector-metrics,context=sink,server=<route>,task=0, where <route> is grpc for the zerobus route, rest for the zerobus-rest route, or kafka for the Kafka route. The metrics use the same JMX exposure model as the JDBC sink connector and Debezium source connectors, so existing JMX monitoring tools such as JConsole, jmxterm, and Prometheus JMX Exporter can read them without any Zerobus-specific configuration.

The sink registers the metrics when it starts, so no option is required to begin collecting them. Reading them from outside the process is a separate step: the service exposes JMX only after you set the JMX_HOST and JMX_PORT environment variables, and it starts the bundled Prometheus JMX Exporter only after you set JMX_EXPORTER_PORT. The Debezium monitoring documentation provides details about how to expose metrics by using JMX. You can automate periodic metric logging by setting debezium.sink.zerobus.metrics.log.interval or debezium.sink.zerobus-rest.metrics.log.interval to a positive value. After you enable either of these options, at the specified interval the connector writes an INFO log message that contains the same metric values that are available through JMX.

The Kafka route is the exception to metrics being collected automatically: because it writes through the generic kafka sink, the Zerobus sink is never invoked and cannot instrument itself. On that route the metrics are not collected until you register the following producer interceptor, which reports the same attributes under server=kafka:

debezium.sink.kafka.producer.interceptor.classes=io.debezium.server.databricks.zerobus.metrics.ZerobusProducerInterceptor

The interceptor reads the operation and the source timestamp from the record headers, and falls back to scanning the serialized value when the headers are absent. Because the interceptor runs for every produced record, prefer the headers on a high-volume pipeline: configure the ExtractNewRecordState SMT with add.headers=op,source.ts_ms in addition to add.fields, as shown in Kafka route. Zerobus does not persist record headers, so the metadata does not reach the target table, and reading it from a header rather than scanning the value makes the interceptor several times cheaper per record. To enable periodic metric logging on this route, set debezium.sink.kafka.producer.zerobus.metrics.log.interval to a positive value. The option is the counterpart of debezium.sink.zerobus[rest].metrics.log.interval, except that it counts records rather than batches, because a producer interceptor observes individual sends. Two attributes carry a route-specific meaning: TotalFlushes counts broker-acknowledged records, which is the durability boundary on this route, and TotalRecordsSkipped remains 0, because the generic sink forwards every record that it receives.

On the Kafka route the interceptor times one in every 128 records rather than every record, so that LastFlushDurationMillis and MaxFlushDurationMillis describe a representative sample. Reading the system clock is significantly more expensive when the producer’s network thread reads it concurrently, and on a high-volume pipeline that cost outweighs everything else the interceptor does. The first record is always timed, so the gauges report a value even on a pipeline that produces few records. All counters remain exact.

The standard kafka.producer:type=producer-metrics and kafka.producer:type=producer-topic-metrics MBeans remain available, and provide per-topic byte counts and request latencies that complement the sink metrics.

The following attributes are available:

Attribute Description

TotalRecordsIngested

Total number of change events that Zerobus durably accepted, across all tables. On the gRPC route the sink counts a record only after the flush that covers it succeeds, so a batch that fails to flush never advances this metric.

TotalInserts / TotalUpdates / TotalDeletes / TotalReads

These metrics report the number of ingested events sorted by operation type (c / u / d, and snapshot reads r).

TotalRecordsSkipped

Number of records skipped without being forwarded (tombstones / null payloads, and events whose destination is not a fully qualified catalog.schema.table, such as schema-history or DDL events). The value remains 0 on the Kafka route, which forwards every record that it receives.

TotalErrors

Number of ingestion or flush failures observed.

TotalFlushes

The metric counts one of the following operations, depending on the route configuration:

  • Stream flush operations (gRPC route).

  • Successful record POST requests (REST route).

  • Broker-acknowledged records (Kafka route).

For the REST and Kafka routes, a successful POST or acknowledgement indicates that the record has been durably accepted and is no longer at risk of loss due to a service failure.

MilliSecondsBehindSource

Indicates the age, in milliseconds, of the most recently processed event. The value is calculated as current time - source.ts_ms. The metric reports the value -1 until after the Delta table ingests an event that contains a source timestamp. Values near 0 indicates that the sink is catching up to, or is synchronized with, the source.

This metric is a primary indicator of pipeline freshness in a CDC-to-lakehouse deployment.

MilliSecondsSinceLastEvent

Indicates the time that elapsed since the sink last forwarded an event. The metric reports the value -1 until the sink forwards the first event.

Use this metric together with MilliSecondsBehindSource. Because MilliSecondsBehindSource reports the age of the last event that the sink processed, its value stops changing if the pipeline stops, and, as a result, an idle source cannot be distinguished from a stalled sink. By contrast, if the value of MilliSecondsSinceLastEvent grows while the source database is known to be receiving writes, the pipeline is stalled.

LastFlushDurationMillis

Duration of the most recent flush (gRPC), record POST (REST), or broker acknowledgement (Kafka) operation. On the Kafka route the value describes a sampled subset of records rather than every record, as the following note describes.

MaxFlushDurationMillis

Longest duration of any flush (gRPC), record POST (REST), or broker acknowledgement (Kafka) operation since the task started. On the Kafka route the value describes a sampled subset of records rather than every record, as the following note describes.

ActiveStreams

Number of currently open Zerobus streams (one per target table). For the REST and Kafka routes, which do not open persistent streams, this value is always 0.

Connected

Indicates whether the sink currently holds a usable connection to Zerobus. On the gRPC route the value reflects the state of the SDK client, and on the REST route the state of the HTTP client. On the Kafka route the value is always true while metrics are reported, because a producer interceptor observes records rather than connection state. To monitor the connection on the Kafka route, use the standard kafka.producer:type=producer-metrics attributes.

Route

The delivery route these metrics belong to (grpc, rest, or kafka).

Extensions

Debezium Server uses the Quarkus framework and relies on dependency injection to enable developer to extend its behaviour. Note that only the JVM mode of Quarkus is supported, but not native execution via GraalVM. The server can be extended in two ways by providing a custom logic:

  • implementation of a new sink

  • customization of an existing sink - i.e. non-standard configuration

Implementation of a new sink

The new sink can be implemented as a CDI bean implementing interface DebeziumEngine.ChangeConsumer and with annotation @Named and unique name and scope @Dependent. The name of the bean is used as the debezium.sink.type option.

The sink needs to read the configuration using Microprofile Config API. The execution path must pass the messages into the target system and regularly commit the passed/processed messages.

See the Kinesis sink implementation for further details.

Customization of an existing sink

Some of the sinks exposes dependency injections points that enable users to provide its own bean that would modify the behaviour of the sink. Typical examples are fine tuning of the target client setup, the destination naming etc.

See an example of a custom topic naming policy implementation for further details.
