The Debezium Milvus connector captures row-level changes in the collections of a Milvus vector database. For information about the Milvus versions that are compatible with this connector, see the Debezium release overview.

Milvus does not expose a change stream through its gRPC API. Instead, Milvus publishes every write to an internal message queue (MQ) channel before it persists the write. The Debezium Milvus connector reads that channel directly, which means that it connects to three parts of a Milvus deployment: the MQ backend, the etcd cluster that stores channel checkpoints, and the Milvus gRPC endpoint.

The first time that the connector connects to a Milvus cluster, it reads a consistent snapshot of the collections that it is configured to capture. The snapshot is anchored to the channel checkpoint that Milvus records in etcd, so that no change is lost or duplicated when the connector transitions from the snapshot to streaming. After the snapshot completes, the connector begins to emit change events for inserts and deletes that Milvus commits to the captured collections. By default, change events for a particular collection go to a Kafka topic that is named after the collection. Applications and services can then consume change event records from these topics.

The Debezium connector for Milvus is currently in the Incubating stage of development. You are encouraged to explore and test the connector, but it is not yet recommended for production use. The format of emitted messages may change, specific features may not be implemented, and it is expected to evolve before it is production-ready.

Overview

Milvus organizes its internal change stream around two kinds of channels: physical channels (pchannels) and virtual channels (vchannels). A pchannel is a real topic on the message queue backend; in a Kafka-backed deployment, each pchannel is an ordinary Kafka topic that Milvus writes all data manipulation operations into. A vchannel is a logical stream within a pchannel that carries the changes of a single collection shard. Milvus does not create a separate topic for each vchannel. Instead, it multiplexes several vchannels onto one pchannel and tags each message with the name of the vchannel that it belongs to, much as multiple logical event streams can share a single Kafka topic and be separated again by a message attribute. When a collection is created, Milvus assigns each of its shards a vchannel, and maps that vchannel onto one of the cluster’s pchannels. Alongside insert and delete messages, Milvus periodically publishes timetick messages on each vchannel; a timetick acts like a watermark that advances the vchannel’s logical clock and tells consumers that no earlier-timestamped changes will arrive on that channel.

The connector uses these three sources of information:

Message queue backend (Kafka)

The connector subscribes to the pchannel topic that is named by the milvus.pchannel.name property, and consumes the raw insert, delete, and timetick messages that Milvus writes to it.

etcd

Milvus tracks how far it has consumed and persisted each channel by recording a per-channel checkpoint in etcd: a guarantee_ts timestamp and the MQ offset that corresponds to it. Every operation at or before the checkpoint is durably stored in Milvus, which is what makes the checkpoint a safe anchor for the snapshot and a safe position from which to resume streaming. Because the Milvus API does not expose checkpoint data, the connector requires direct access to the etcd cluster that backs Milvus.

Milvus gRPC API

During the snapshot, the connector uses the API to list collections, read their schemas, and query rows. During streaming, the connector uses the API to resolve the schema of a collection that it has not yet observed in an insert event.

Milvus assigns every operation a timestamp from a Hybrid Logical Clock (HLC), which the Milvus documentation refers to as a TSO (timestamp oracle). The high 46 bits of a TSO encode the number of milliseconds that elapsed since the UNIX epoch, and the low 18 bits encode a logical counter that orders operations that occur within the same millisecond. The connector preserves this value in the source block of every event, and uses it to order events across vchannels.

How the connector works

To optimally configure and run a Debezium Milvus connector, it is helpful to understand how the connector performs snapshots, orders events, and names topics.

Snapshots

When a Milvus connector starts for the first time, it performs an initial snapshot of the collections that it captures. The connector completes the following steps:

  1. Reads the etcd checkpoint of the configured pchannel to obtain the guarantee_ts timestamp and the MQ offset that corresponds to it. The connector stores the MQ offset in its offsets so that the streaming phase knows where to resume.

  2. Retrieves the list of collections in the database that the milvus.database property names, and applies the milvus.collection.include.list and milvus.collection.exclude.list filters.

  3. Queries every included collection through the Milvus SDK with consistency_level set to Strong and guarantee_ts pinned to the checkpoint timestamp. Pinning the query to the checkpoint guarantees that the snapshot observes exactly the state of the collection at the point in the change stream from which streaming later resumes.

  4. Emits each row as a read (op=r) event.

  5. Records snapshot_completed=true in the connector offsets and hands off to the streaming phase.

If the etcd checkpoint does not exist, for example, because the Milvus cluster has not yet written to the pchannel, the snapshot completes immediately without emitting rows, and the streaming phase falls back to the latest position in the MQ.

If the connector fails after the snapshot begins but before it completes, the connector starts a new snapshot after it restarts.

The connector does not take a separate schema snapshot. Milvus collection schemas are resolved dynamically, either from the Milvus metadata API during the snapshot, or from the first insert event that the connector observes during streaming.

Snapshot modes

The snapshot.mode property controls the snapshot behavior:

initial

The connector performs a snapshot when no offsets exist, and then streams changes. This is the default.

never

The connector never performs a snapshot. It begins streaming from the position that its stored offsets specify, or from the latest position in the MQ if no offsets exist.

when_needed

The connector performs a snapshot if no offsets exist, or if the stored offsets refer to a position that is no longer available in the MQ.

The Milvus connector does not support incremental snapshots, ad hoc snapshots, or blocking snapshots.

Streaming changes

After the snapshot completes, the connector seeks its MQ consumer to the offset that the etcd checkpoint recorded, and enters the streaming loop. For each iteration, the connector completes the following steps:

  1. Polls a batch of raw messages from the pchannel topic.

  2. Deserializes each message. Depending on its version, a Milvus cluster uses one of two wire formats for its MQ payloads: a msgpack batch envelope, or a single protobuf message per record. By default the milvus.wire.format property is set to auto, which causes the connector to probe the channel and detect the format that the cluster uses. The connector expects the format to stay consistent on the same channel; if it changes, the connector reports an error.

  3. Buffers the deserialized events. Because several vchannels share the pchannel, and each vchannel advances its own timetick independently, events can arrive on the topic in a different order than the order they were committed. The connector must hold each event in a buffer, the timetick ordering engine, until it can guarantee that no earlier operation is still inflight.

  4. Flushes events whose TSO is behind the global watermark, which is the minimum timetick across all active vchannels. Because no vchannel can subsequently produce an event with a lower TSO, the flushed events are guaranteed to be complete and are released in strict TSO order.

  5. Dispatches the flushed events to the Debezium event pipeline, and only afterwards advances the connector offsets with the new MQ position and vchannel watermarks. Updating offsets after dispatch ensures that the connector never commits an offset for an event that it did not emit.

If a vchannel stops advancing its timetick for longer than the interval that the milvus.timetick.stall.timeout.ms property specifies, the connector logs a warning and force-flushes the buffered events rather than stalling indefinitely. To bound memory use, the ordering engine applies backpressure when the buffer exceeds the limits that the milvus.buffer.max.events and milvus.buffer.max.bytes properties set.

After a restart, the connector initializes the ordering engine with the vchannel watermarks that it stored in its offsets, so that streaming resumes without waiting for a fresh timetick from every vchannel.

A Milvus connector supports a single task and consumes a single pchannel. If tasks.max is set to a value greater than 1, the connector logs a warning and ignores the value.

Topic names

By default, the Milvus connector writes change events for all of the insert and delete operations in a collection to a single Kafka topic. The connector names change event topics according to the following format:

topicPrefix.databaseName.collectionName

The following list provides definitions for the components of the default name:

topicPrefix

The value that the topic.prefix configuration property specifies.

databaseName

The Milvus database that contains the collection, as specified by the milvus.database property.

collectionName

The name of the Milvus collection in which the operation occurred.

For example, if topic.prefix is set to milvus, the connector captures the default database, and a row is inserted into the orders collection, the connector emits the event to the milvus.default.orders topic.

To change the topic naming convention, you can configure a custom topic naming strategy.

Data change events

The Debezium Milvus connector generates a data change event for each row-level insert and delete operation. Each event contains a key and a value. The structure of the key and value depends on the collection that was changed.

The connector emits the following operations:

Operation op before after

Snapshot read

r

null

The full row, as it existed when the snapshot ran.

Insert

c

null

The full row that was inserted.

Delete

d

The primary key of the deleted entity only.

null

Milvus DeleteRequest messages carry only the primary keys of the entities that are deleted, and do not carry their prior state. As a result, the before field of a delete event contains a value for the primary key field only; every other field is null.

Milvus implements upserts as a delete followed by an insert, and the connector emits that pair of operations as it observes them on the channel; therefore, it emits no update (op=u) event. A downstream consumer will observe an upsert as a delete event, followed by a tombstone unless tombstones.on.delete is false, and finally the insert with the same key, rather than a single update event.

Collection creation and removal are tracked internally, so that the connector can order events correctly, but they are not emitted as schema change events. The connector does not produce a schema change topic.

Change event keys

The key of a change event contains the primary key field of the Milvus collection in which the change occurred. For a collection named orders in the default database with an Int64 primary key field named id, and a connector for which topic.prefix is set to milvus, the key of every change event has the following structure:

{

    "name": "milvus.default.orders.Key",

        "name": "id",

          "type": "INT64",

        }

    ]

Descriptions of source fields

The source block of a Milvus change event contains the following connector-specific fields, in addition to the fields that all Debezium connectors provide:

Field Description

db

The name of the Milvus database that contains the collection.

collection

The name of the Milvus collection in which the operation occurred.

pchannel

The name of the Milvus physical channel from which the connector read the event.

vchannel

The name of the Milvus virtual channel that carried the event. Each vchannel corresponds to a collection shard.

tso

The raw Milvus HLC timestamp of the operation. The high 46 bits encode milliseconds since the UNIX epoch, and the low 18 bits encode a logical counter. The ts_ms field is derived from the physical component of this value.

Setting up Milvus

Before you deploy the connector, configure the Milvus cluster so that the connector can read its change stream.

Prerequisites

  • A Milvus 2.5 or later deployment.

  • Java 17 or later on the Kafka Connect worker.

Procedure

  1. Verify that the Milvus deployment uses Kafka as its message backend. In the Milvus configuration file, verify that mq.type is set to kafka. The message backend is selected at deployment, so if it isn’t kafka, you must fully redeploy Milvus.

    mq:
  type: kafka
kafka:
  brokerList: kafka:19092

    The connector supports Kafka only. Milvus deployments that are backed by Pulsar or RocksMQ are not supported.

  2. Note the value of the etcd.rootPath property in the Milvus configuration, which defaults to by-dev. You supply this value to the connector through the milvus.etcd.root.path property, so that the connector can locate the channel checkpoints.

  3. Determine the name of the pchannel that the connector consumes. The default is by-dev-rootcoord-dml_0, which follows the pattern clusterPrefix-rootcoord-dmln, where n is the channel index. The clusterPrefix component is the value of the msgChannel.chanNamePrefix.cluster property in the Milvus configuration, which defaults to by-dev, the same default value as etcd.rootPath. The rootCoord.dmlChannelNum property controls how many pchannels a Milvus cluster creates.

    Because a connector instance consumes a single pchannel, deploy one connector for each pchannel that you want to capture.

  4. Verify that the Kafka Connect worker can reach the Milvus gRPC endpoint, the Kafka cluster that Milvus uses as its MQ backend, and the etcd cluster that backs Milvus.

  5. If the Milvus deployment requires authentication, create a user for the connector and supply its credentials through the milvus.token property.

Deployment

To deploy a Debezium Milvus connector, you install the connector archive on a Kafka Connect server, configure the connector, and start the Kafka Connect service.

Prerequisites

  • Milvus is set up to run a Debezium connector.

  • Apache Kafka and Kafka Connect are installed.

Procedure

  1. Download the Debezium Milvus connector plug-in archive.

  2. Extract the files into your Kafka Connect environment.

  3. Add the directory that contains the connector files to the Kafka Connect plugin.path.

  4. Restart the Kafka Connect process to pick up the new JAR files.

Connector configuration example

The following example shows the configuration of a connector that captures the collections whose names begin with orders from the default database of a Milvus instance:

{
  "name": "milvus-connector",  (1)
  "config": {
    "connector.class": "io.debezium.connector.milvus.MilvusConnector",  (2)
    "topic.prefix": "milvus",  (3)
    "milvus.uri": "http://localhost:19530",  (4)
    "milvus.database": "default",
    "milvus.etcd.endpoints": "http://localhost:2379",  (5)
    "milvus.etcd.root.path": "by-dev",
    "milvus.kafka.bootstrap.servers": "localhost:9092",  (6)
    "milvus.pchannel.name": "by-dev-rootcoord-dml_0",  (7)
    "milvus.collection.include.list": "orders.*",  (8)
    "snapshot.mode": "initial"
  }
}
1 The name of the connector.
2 The name of the connector class. Always specify this value for a Milvus connector.
3 The prefix of the Kafka topics to which the connector writes change events.
4 The gRPC endpoint of the Milvus cluster.
5 The endpoints and root path of the etcd cluster in which Milvus stores its channel checkpoints.
6 The Kafka cluster that the Milvus deployment uses as its message queue backend. This is typically distinct from the Kafka cluster that Kafka Connect writes change events to.
7 The Milvus physical channel that the connector consumes.
8 A comma-separated list of literal names or regular expressions that match the collections to capture.

You can send this configuration to a running Kafka Connect service with the POST command of the Kafka Connect REST API.

Monitoring

The Debezium Milvus connector provides the snapshot and streaming metrics that are common to all Debezium connectors, and a small number of Milvus-specific metrics.

The connector exposes snapshot metrics through the following JMX object name:

debezium.milvus:type=connector-metrics,context=snapshot,server=<topic.prefix>

Table 4. Milvus-specific snapshot metrics
Attribute Type Description

long

The etcd checkpoint TSO to which the snapshot is anchored, or 0 if no checkpoint was available.

SnapshotStartTs

long

The time, in milliseconds since the epoch, at which the snapshot phase started, or 0 if the snapshot has not started.

The connector exposes streaming metrics through the following JMX object name:

debezium.milvus:type=connector-metrics,context=streaming,server=<topic.prefix>

Attribute Type Description

boolean

true after the connector resolves and assigns the start offset of its MQ consumer for the current streaming run. Unlike the Connected attribute, which becomes true as soon as the streaming loop starts, this attribute distinguishes the state in which streaming has started from the state in which the consumer position is known and events are observed from that point onward.

The replication lag, in milliseconds. The connector computes this value as the difference between the current time and the physical component of the global timetick watermark.

Limitations

The connector has the following limitations:

  • The connector supports a single task, and consumes a single pchannel for each connector instance. To capture a Milvus cluster that uses multiple pchannels, deploy one connector for each channel.

  • The connector supports Kafka only as the Milvus message queue backend. Deployments that are backed by Pulsar or RocksMQ are not supported.

  • Delete events carry a before image that contains the primary key only, because Milvus does not publish the prior state of a deleted entity.

  • The connector does not emit update (op=u) events. Milvus implements upserts as a delete followed by an insert, and the connector emits that pair of operations.

  • The connector does not emit schema change events, and does not produce a schema change topic.

  • The connector does not support incremental snapshots, ad hoc snapshots, or blocking snapshots.
