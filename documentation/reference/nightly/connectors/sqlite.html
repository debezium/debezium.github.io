Debezium connector for SQLite

The Debezium SQLite connector captures row-level changes in the tables of a SQLite database file. For information about the SQLite versions that are compatible with this connector, see the Debezium release overview.

SQLite is an embedded database that stores an entire database in a single file, and it exposes no replication log or change stream that an external process can follow. Instead, the connector captures changes with SQL triggers. For each table that it captures, the connector installs AFTER INSERT, AFTER UPDATE, and AFTER DELETE triggers. Every trigger writes one row that describes the change into an internal table named _debezium_cdc_log, in commit order.

The Debezium connector for SQLite is currently in the Incubating stage of development. You are encouraged to explore and test the connector, but it is not yet recommended for production use. The format of emitted messages may change, specific features may not be implemented, and it is expected to evolve before it is production-ready.

Overview

Because SQLite has no server process and no built-in change stream, the connector runs against the database file directly and derives a change stream from SQL triggers.

The connector opens the same database file that the application writes to, and it opens the file in write-ahead logging (WAL) mode. WAL mode lets the connector read the database in short transactions while application writers continue to commit, so capture does not block the application and the application does not block capture.

For each captured table, the connector installs three triggers, one each for INSERT, UPDATE, and DELETE. Every trigger appends a single row to the _debezium_cdc_log table within the same transaction as the change that fired it, so a change and its log row commit together, or not at all. The CDC log table has the following structure:

Column Type Description

change_id

INTEGER PRIMARY KEY AUTOINCREMENT

A monotonically increasing identifier that SQLite assigns in commit order. It is the position that the connector streams from and stores in its offsets.

table_name

TEXT

The name of the table in which the change occurred.

operation

TEXT

The kind of change: c for an insert, u for an update, and d for a delete.

old_row_data

TEXT

A JSON object with the row’s values before the change. It is null for an insert.

new_row_data

TEXT

A JSON object with the row’s values after the change. It is null for a delete.

committed_at

INTEGER

The time, in milliseconds since the UNIX epoch, at which the change was recorded.

Because the triggers write to the log in the same transaction as the change, the change_id order is the commit order, and the connector emits change events in that order. The connector reads the log in small batches, emits a change event for each row, and advances its offset to the change_id of the last row that it processed. So that the log does not grow without bound, the connector periodically deletes the rows whose changes Debezium has already committed downstream.

A SQLite connector uses a single task, and each connector instance captures a single database file.

How the connector works

To optimally configure and run a Debezium SQLite connector, it is helpful to understand how the connector performs snapshots, streams changes, and names topics.

Snapshots

When a SQLite connector starts for the first time, it performs an initial snapshot of the tables that it captures. The connector completes the following steps:

  1. Switches the database file to WAL journal mode, and creates the _debezium_cdc_log table if it does not already exist.

  2. Installs the capture triggers on each table that it captures. From this point on, SQLite logs every insert, update, and delete to the CDC log table with a change_id, so that no change that occurs during or after the snapshot is lost.

  3. Opens a read transaction on the WAL, which provides a consistent view of the database without locking the tables or blocking application writers.

  4. Reads the highest change_id in the CDC log within that same view, and stores it in the connector offsets as the position from which streaming later resumes. Because the connector reads the mark and the table data from one consistent view, any change that is committed after the mark is left for the streaming phase, with no gap and no duplicate.

  5. Reads every row of each captured table, and emits it as a read (op=r) event. The connector also emits one schema change event per table.

  6. Records that the snapshot is complete in the connector offsets, and hands off to the streaming phase, which resumes from the stored change_id.

Snapshot modes

The snapshot.mode property controls the snapshot behavior:

initial

The connector performs a snapshot when no offsets exist, and then streams changes. This is the default.

always

The connector performs a snapshot every time that it starts, and then streams changes.

no_data

The connector does not snapshot data. It installs the capture triggers if they are missing, and begins streaming from the current position of the CDC log.

initial_only

The connector performs a snapshot when no offsets exist, and then stops without streaming.

The SQLite connector does not support incremental snapshots, ad hoc snapshots, or blocking snapshots.

Streaming changes

After the snapshot completes, the connector begins to poll the CDC log table, and streams the rows that the triggers append to it. For each poll, the connector completes the following steps:

  1. Reconciles the capture triggers if the database schema has changed since the previous poll, so that a schema change is picked up before the connector reads the next batch.

  2. Deletes already-committed rows from the CDC log once enough of them have accumulated, so that the log does not grow without bound.

  3. Reads a batch of rows whose change_id is greater than the stored offset, up to the limit that the cdc.log.batch.size property sets.

  4. Emits a change event for each row, in change_id order, and advances the offset to the change_id of the last row that it emits.

If a poll returns no rows, the connector pauses for the poll interval before it polls again. The connector reads each batch in a short, autocommitted transaction, so that SQLite can checkpoint the WAL between polls.

Because the triggers write to the CDC log in the same transaction as the change that fired them, the change_id order is the commit order, and the connector emits change events in that order.

A SQLite connector supports a single task, because SQLite allows a single writer. If you set tasks.max to a value greater than 1, the connector logs a warning and uses a single task.

Topic names

By default, the SQLite connector writes all of the change events for a table to a single Kafka topic. The connector names change event topics according to the following format:

topicPrefix.tableName

The following list provides definitions for the components of the default name:

topicPrefix

The value that the topic.prefix configuration property specifies.

tableName

The name of the table in which the operation occurred.

SQLite has no catalog or schema, so the table name is the only qualifier between the prefix and the name of the topic. For example, if topic.prefix is set to sqlite, and a row is inserted into the orders table, the connector emits the event to the sqlite.orders topic.

To change the topic naming convention, you can configure a custom topic naming strategy.

Data change events

The Debezium SQLite connector generates a data change event for each row-level insert, update, and delete operation. Each event contains a key and a value. The structure of the key and the value depends on the table that was changed.

The connector emits the following operations:

Operation op before after

Snapshot read

r

null

The full row, as it existed when the snapshot ran.

Insert

c

null

The full row that was inserted.

Update

u

The full row, as it existed before the update.

The full row, as it exists after the update.

Delete

d

The full row, as it existed before the delete.

null

Because the capture triggers record the complete OLD and NEW row for every change, update and delete events carry a full before image, not only the primary key.

Change event keys

The key of a change event contains the primary key of the table in which the change occurred. For a table named orders whose primary key is an INTEGER column named id, and a connector for which topic.prefix is set to sqlite, the key of every change event has the following structure:

{
  "schema": {
    "type": "struct",
    "name": "sqlite.orders.Key",
    "optional": false,
    "fields": [
      {
        "field": "id",
        "type": "int64",
        "optional": false
      }
    ]
  },
  "payload": {
    "id": 1004
  }
}

Descriptions of source fields

The source block of a SQLite change event contains the following connector-specific fields, in addition to the fields that all Debezium connectors provide:

Field Description

table

The name of the table in which the operation occurred.

change_id

The identifier that the connector assigned to the change in the CDC log. It increases monotonically in commit order, and is the position from which the connector resumes streaming.

Schema change events

The Debezium SQLite connector emits a schema change event whenever the structure of a captured table changes. It emits one event for each table that is created, altered, or dropped while the connector is running, and one event for each table during the initial snapshot.

SQLite exposes no data definition language (DDL) statement to an external reader, so the connector detects a schema change by watching SQLite’s schema_version counter, which SQLite increments for any DDL. When the counter moves, the connector re-reads the current schema from the database file, reconciles the capture triggers, and emits a schema change event for each captured table that was created, altered, or dropped. A DDL statement that does not change a captured table, such as CREATE INDEX, moves the counter but reconciles to no event.

Because no literal DDL text is available, the ddl field of a SQLite schema change event is always null. The change is described by the tableChanges array instead.

The connector does not keep a schema history topic. It reads the current schema directly from the database file whenever it needs it, so there is no separate history to replay after a restart.

The connector writes schema change events to a single topic that is named after the topic.prefix property. For example, if topic.prefix is set to sqlite, the connector writes schema change events to the sqlite topic.

Renames

SQLite gives no link between a table’s old and new name, so a table rename appears to the connector as two changes: a DROP of the old name, followed by a CREATE of the new name. The connector emits a separate schema change event for each.

Example: schema change event

The following example shows the value of a schema change event that the connector emits after a note column is added to the orders table:

{
  "source": {
    "version": "3.7.0.Final",
    "connector": "sqlite",
    "name": "sqlite",
    "ts_ms": 1754630700000,
    "snapshot": "false",
    "db": "sqlite",
    "table": "orders",
    "change_id": 44
  },
  "ts_ms": 1754630700123,
  "databaseName": "sqlite",
  "schemaName": null,
  "ddl": null,
  "tableChanges": [
    {
      "type": "ALTER",
      "id": "\"orders\"",
      "table": {
        "primaryKeyColumnNames": [ "id" ],
        "columns": [
          { "name": "id", "jdbcType": -5, "typeName": "INTEGER", "optional": false },
          { "name": "name", "jdbcType": 12, "typeName": "TEXT", "optional": true },
          { "name": "quantity", "jdbcType": -5, "typeName": "INTEGER", "optional": true },
          { "name": "note", "jdbcType": 12, "typeName": "TEXT", "optional": true }
        ]
      }
    }
  ]
}

SQLite records no log position for a DDL statement, so the change_id in the source block of a schema change event is the last log position that the connector consumed, rather than a new value.

Data type mappings

SQLite does not assign a fixed data type to a column. Instead, each column has a type affinity, which SQLite derives from the column’s declared type, and each stored value keeps its own storage class (INTEGER, REAL, TEXT, BLOB, or NULL). The connector builds one fixed Kafka Connect schema per column, from the column’s affinity, so that every value in the column shares one schema.

The connector derives a column’s affinity from its declared type, by applying the following rules in order:

  1. If the declared type contains INT, the affinity is INTEGER.

  2. Otherwise, if it contains CHAR, CLOB, or TEXT, the affinity is TEXT.

  3. Otherwise, if it contains BLOB, or the declared type is empty, the affinity is BLOB.

  4. Otherwise, if it contains REAL, FLOA, or DOUB, the affinity is REAL.

  5. Otherwise, the affinity is NUMERIC.

The rules are substring matches, so a column declared BOOLEAN, DATE, DATETIME, or DECIMAL falls through to NUMERIC, and a column declared with no type has BLOB affinity, which matches SQLite’s own behavior.

The connector maps each affinity to a Kafka Connect schema type:

SQLite affinity Kafka Connect schema type Notes

INTEGER

INT64

REAL

FLOAT64

NUMERIC

FLOAT64

SQLite has no fixed-precision decimal type. A NUMERIC column, including one that is declared DECIMAL, maps to FLOAT64.

TEXT

STRING

BLOB

BYTES

A column that is declared with no type also has BLOB affinity.
Affinity mismatches

Because SQLite is dynamically typed, a column can hold a value whose storage class does not match the column’s affinity, for example, a TEXT value in a column that has INTEGER affinity. The connector converts each value by the column’s affinity, so a value whose storage class does not fit that affinity cannot be converted.

The connector resolves the mismatch through the framework’s failure mode and a connector option. When a value’s storage class does not fit the column’s affinity, the converter reports a failure, and the event.converting.failure.handling.mode property decides the outcome:

fail

The connector stops. This is the default.

warn

The connector logs the column and leaves the field null.

skip

The connector leaves the field null quietly.

Under warn or skip, leaving the field null then resolves against the column:

  • For a nullable column, the field stays null.

  • For a non-nullable column that has a default, the schema default takes over.

  • For a non-nullable column that has no default, there is no null to fall back on. The nonnull.affinity.mismatch.fallback property decides what happens:

    true

    The connector substitutes a type placeholder for the value, so that the stream keeps flowing: 0 for INT64, 0.0 for FLOAT64, an empty string for STRING, and empty bytes for BYTES.

    false

    The field stays null, and the record fails downstream when the Kafka Connect struct is validated. This is the default.

The placeholder is a synthetic value in place of the real one, which is why it is off by default and takes effect only under the warn and skip failure modes.

Setting up SQLite

The connector installs its capture triggers and creates the _debezium_cdc_log table on the database itself, so there is no schema to prepare by hand. Before you deploy the connector, make sure that the connector can reach and write to the database file.

Prerequisites

  • A SQLite database file.

  • Read and write access to the database file for the process that runs the connector. The connector creates the _debezium_cdc_log table, installs the capture triggers, and deletes already-committed rows from the log, all of which write to the file.

  • Java 17 or later on the Kafka Connect worker.

Procedure

  1. Place the Kafka Connect worker on the same host as the application that writes to the database, with direct access to the database file on a local filesystem.

    SQLite coordinates WAL access through a shared-memory file and local filesystem locks, so every process that opens the database must run on the same host and share the same file. A database file on a network filesystem, or one that is reached from a different host or container than the application that writes to it, is not supported.

  2. Grant the connector’s process read and write permission on the database file and on the directory that contains it, so that SQLite can create the WAL and shared-memory files alongside it.

  3. Verify that the tables that you want to capture have a primary key. The change event key is built from the primary key, so a table with no primary key produces events that have a null key.

Deployment

To deploy a Debezium SQLite connector, you install the connector archive on a Kafka Connect server, configure the connector, and start the Kafka Connect service.

Prerequisites

  • SQLite is set up to run a Debezium connector.

  • Apache Kafka and Kafka Connect are installed.

Procedure

  1. Download the Debezium SQLite connector plug-in archive.

  2. Extract the files into your Kafka Connect environment.

  3. Add the directory that contains the connector files to the Kafka Connect plugin.path.

  4. Restart the Kafka Connect process to pick up the new JAR files.

Connector configuration example

The following example shows the configuration of a connector that captures the orders and customers tables from a SQLite database file:

{
  "name": "sqlite-connector",  (1)
  "config": {
    "connector.class": "io.debezium.connector.sqlite.SQLiteSourceConnector",  (2)
    "topic.prefix": "sqlite",  (3)
    "database.file.path": "/data/app.db",  (4)
    "table.include.list": "orders,customers",  (5)
    "snapshot.mode": "initial"  (6)
  }
}
1 The name of the connector.
2 The name of the connector class. Always specify this value for a SQLite connector.
3 The prefix of the Kafka topics to which the connector writes change events.
4 The path of the SQLite database file that the connector monitors.
5 A comma-separated list of the tables to capture. SQLite has no schema, so each entry is a bare table name.
6 The criteria for performing a snapshot on startup.

You can send this configuration to a running Kafka Connect service with the POST command of the Kafka Connect REST API.

Connector properties

The Debezium SQLite connector supports the Debezium properties that are common to all connectors, in addition to the following connector-specific properties.

Because SQLite is a single file with no server, no schema, and no separate databases, the connector does not use the relational connection and schema-filtering properties. The hostname, port, user, password, and database.name properties, and the schema.include.list and schema.exclude.list properties, do not apply.

column.include.list

No default

An optional, comma-separated list of regular expressions that match the fully-qualified names of columns that should be included in change event record values. Fully-qualified names for columns are of the form tableName.columnName.

To match the name of a column, Debezium applies the regular expression that you specify as an anchored regular expression. That is, the expression is used to match the entire name string of the column; it does not match substrings that might be present in a column name. If you include this property in the configuration, do not also set the column.exclude.list property.

column.exclude.list

No default

An optional, comma-separated list of regular expressions that match the fully-qualified names of columns that should be excluded from change event record values. Fully-qualified names for columns are of the form tableName.columnName.

To match the name of a column, Debezium applies the regular expression that you specify as an anchored regular expression. That is, the expression is used to match the entire name string of the column; it does not match substrings that might be present in a column name. If you include this property in the configuration, do not set the column.include.list property.

tombstones.on.delete

true

Controls whether a delete event is followed by a tombstone event.

true - a delete operation is represented by a delete event and a subsequent tombstone event.

false - only a delete event is emitted.

After a source record is deleted, emitting a tombstone event (the default behavior) allows Kafka to completely delete all events that pertain to the key of the deleted row in case log compaction is enabled for the topic.

event.converting.failure.handling.mode

fail

Specifies how the connector reacts when a value cannot be converted to its column’s schema type, for example, when a value’s SQLite storage class does not match the column’s affinity. Set one of the following values: fail, warn, or skip.

The connector always excludes SQLite’s internal sqlite_ tables and its own debezium tables from capture, regardless of the include and exclude lists.

Monitoring

The Debezium SQLite connector provides the snapshot and streaming metrics that are common to all Debezium connectors, and a few SQLite-specific streaming metrics.

The connector exposes snapshot metrics through the following JMX object name:

debezium.sqlite:type=connector-metrics,context=snapshot,server=<topic.prefix>

The connector exposes streaming metrics through the following JMX object name:

debezium.sqlite:type=connector-metrics,context=streaming,server=<topic.prefix>

Table 4. SQLite-specific streaming metrics
Attribute Type Description

CurrentChangeId

long

The change_id of the row that the connector most recently dispatched.

CommittedChangeId

long

The change_id that Kafka Connect most recently committed to the connector offsets.

CdcLogDepth

long

The number of rows in the _debezium_cdc_log table that the connector has not yet compacted. It is the backlog that is still waiting to be deleted from the log.

Limitations

The connector has the following limitations:

  • The connector supports a single task, and each connector instance captures a single database file. To capture more than one database file, deploy one connector for each file.

  • The connector and the application that writes to the database must run on the same host, with direct access to the same database file on a local filesystem. A database file on a network filesystem, or one that is reached from a different host or container than the writer, is not supported.

  • The connector requires read and write access to the database file. It creates the _debezium_cdc_log table, installs the capture triggers, and compacts the log, all within the user’s database.

  • The connector does not support incremental snapshots, ad hoc snapshots, or blocking snapshots.

  • SQLite exposes no DDL text to an external reader, so the ddl field of a schema change event is always null. The change is described by the tableChanges array.

  • A table that has no primary key produces change events that have a null key.

  • SQLite has no fixed-precision decimal type, so a NUMERIC column, including one that is declared DECIMAL, maps to FLOAT64.
