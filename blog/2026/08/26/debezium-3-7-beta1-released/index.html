Debezium 3.7.0.Beta1 Released

Chris Cranford
August 26, 2026 · 11 min read
releases mongodb mysql mariadb postgres sqlserver cassandra oracle db2 vitess outbox spanner jdbc informix ibmi cockroachdb yashandb ingres tidb

As summer continues, we’re excited to announce the release of Debezium 3.7.0.Beta1, bringing a broad set of improvements across connectors, Debezium Server, and the Platform UI.

Among the highlights, incremental snapshots now work on PostgreSQL read-only replicas, and Debezium Server gains a new Databricks ZeroBus Ingest sink for direct change event delivery to Unity Catalog-managed Delta tables. This release also includes performance and snapshot optimizations, new connector capabilities, and numerous bug fixes across the board.

Read on for the full details!

Debezium for MySQL

Support for NOBLOB binlog_row_image format

Debezium now supports the NOBLOB binlog row image format for MySQL. This format is commonly used in databases with large BLOB columns that are updated infrequently, as it reduces binlog size by excluding BLOB and TEXT columns from row images when they are not modified. Previously, the connector rejected this format at startup, forcing users to choose between FULL and MINIMAL row image modes.

This behavior is conceptually similar to how PostgreSQL handles unchanged TOAST columns and how Oracle handles LOB values. In all three cases, the database’s replication stream may omit large-value columns that were not modified in a given transaction. During snapshots, all column values are always available because Debezium reads the full row directly via SQL. During streaming, however, when a BLOB or TEXT column was not changed and is therefore excluded from the binlog row image, Debezium populates the field with the configured unavailable.value.placeholder value. This is the same approach used for unavailable TOASTed columns in PostgreSQL and LOB columns in Oracle, giving users a consistent way to detect and handle missing column values across all three databases. (dbz#473)

Debezium for Oracle

Support for BC (negative) timestamps

The Oracle connector now correctly captures dates in the BC era (negative years) across all four Oracle temporal types: DATE, TIMESTAMP, TIMESTAMP WITH TIME ZONE, and TIMESTAMP WITH LOCAL TIME ZONE. Previously, a date such as -2018-03-27 inserted via TO_DATE('-2018-03-27', 'SYYYY-MM-DD') would be incorrectly represented as the positive-year equivalent 2018-03-27.

Because Oracle’s calendar has no year zero while ISO 8601 does, BC years are offset by one: Oracle year 2018 BC becomes ISO year -2017. How BC values appear in change events depends on the time.precision.mode setting. Epoch-based types such as io.debezium.time.Timestamp and io.debezium.time.MicroTimestamp emit negative epoch values, while string-based types such as io.debezium.time.ZonedTimestamp emit ISO 8601 strings with a negative year (e.g., "-2017-03-27T01:34:56.007890-11:00").

Both snapshot and streaming paths are covered, and no new connector configuration properties are required. (dbz#1286)

BC values stored in TIMESTAMP(7-9) columns exceed the representable range of io.debezium.time.NanoTimestamp, so users with BC data at nanosecond precision should use time.precision.mode set as isostring or structured only.

LogMiner DML parser performance improvements

The LogMiner DML parser has been significantly optimized, delivering 1.7x to 2.6x higher throughput for UPDATE statement parsing across a range of table widths and column sizes. For tables with wide VARCHAR2 columns or extended 32K strings, the improvements are even more dramatic.

Users who enable the extended MAX_STRING_SIZE parameter may encounter a LogMiner bug where apostrophes in text column values are not properly escaped. Debezium’s relaxed quote detection mode addresses this Oracle limitation, but previously suffered from O(n^2) performance loss for such columns, compounded by text length. This release improves that mode by up to 94x in worst-case scenarios.

These improvements directly translate to higher event throughput for Oracle connectors processing tables with many columns or large column values. (dbz#2491)

The JMH Benchmarks for these changes can be found here.

Debezium for PostgreSQL

Incremental snapshots on read-only replicas

Incremental snapshots on PostgreSQL read-only replicas previously failed with cannot execute pg_current_xact_id() during recovery error, because the snapshot logic attempted to create a new transaction ID, which is not permitted on replicas. This caused connectors running with read.only=true to enter an infinite restart loop when an incremental snapshot was triggered.

This has been corrected, and users running against a hot standby can now use incremental snapshots for re-snapshotting subsets of data without restarting the connector or switching to the primary. (dbz#1080, dbz#2431)

Faster snapshots with per-column type caching

The PostgreSQL connector now caches the resolved column type per ResultSet during snapshots, rather than resolving it on every row. Previously, each row paid the cost of calling ResultSetMetaData.getColumnTypeName and TypeRegistry.get once per column, making overhead scale based on number of columns and rows. For a table with 82 columns, this kept the snapshot producer pinned at around 25K rows per second.

With caching in place, the rowToArray stage runs approximately 35% faster, and end-to-end snapshot throughput for the same table increased to over 30K rows per second. The gain scales with column count and benefits all snapshot flavors, including initial, blocking, incremental, and read-only incremental. (dbz#2350)

Debezium JDBC sink

Opt-in timestamp clamping for out-of-range values

Every database supports a different timestamp range, and Oracle’s BC-era values often fall outside what other databases can represent. The JDBC sink connector introduces timestamp.clamp.out.of.range.values, an opt-in setting that clamps incoming timestamps to the target dialect’s minimum or maximum rather than failing the sink operation. (dbz#1008)

Debezium Platform

Adaptive polling for resource listing pages

The Debezium Platform UI now uses adaptive polling on its resource listing pages. Previously, all listing pages (pipelines, sources, transforms, destinations, and connections) polled data at a fixed 5-second interval, regardless of user activity. The new approach decreases polling frequency when the user is idle and pauses it entirely when the browser tab is in the background, reducing unnecessary API traffic and improving overall UI responsiveness. (dbz#1878)

Connection handling in the pipeline designer

The pipeline designer now handles connections when creating pipelines via Debezium Server configuration. Previously, the flow automatically created sources, destinations, and transforms, but did not manage connection creation. The designer now creates and associates connections with the source and destination configuration, providing a more complete and streamlined pipeline setup experience. (dbz#1906)

Debezium Server

IRSA and WebIdentityToken support for the Kinesis sink

The Kinesis sink now supports AWS IRSA (IAM Roles for Service Accounts) and WebIdentityToken-based authentication. Previously, running the Kinesis sink in Kubernetes with a service account mapped to an AWS IAM role failed because the classpath did not include the required AWS STS module. The sink now bundles the software.amazon.awssdk:sts dependency, enabling the default credential provider chain to resolve web identity tokens and assume the target role.

This is especially important for Kubernetes-based deployments on Amazon EKS, where IRSA is the recommended approach for granting AWS permissions to pods without embedding static credentials. (dbz#1738, dbz#2386)

Databricks ZeroBus Ingest sink adapter

Debezium Server now includes a sink adapter for Databricks ZeroBus Ingest, enabling direct change event delivery to Unity Catalog-managed Delta tables without requiring an intermediate message broker. ZeroBus Ingest is Databricks' serverless ingestion API, generally available on AWS and Azure, which writes records directly into managed Delta tables. With this integration, Debezium Server users can set up a streamlined source database to Delta pipeline for change data capture into the Databricks lakehouse.

The sink commits source offsets only after ZeroBus durably writes and acknowledges each batch, providing at-least-once delivery semantics with deterministic idempotency keys. (dbz#2279, dbz#2378)

Correct Prometheus metric labels for sink connectors

The Prometheus JMX Exporter configuration shipped with Debezium Server now correctly labels sink connector metrics. Previously, sink connectors registered their MXBeans with a key ordering that did not match any existing rule pattern. This caused the task key to be embedded inside the name label (e.g., name="jdbc-sink, task=0" instead of name="jdbc-sink" with a separate task="0" label). This broke Prometheus queries, alerts, and dashboards that group or filter by connector name or task ID. (dbz#2380)

Connector profiles for the server distribution

The debezium-server-dist module now includes connector profiles (e.g., connector-postgres, connector-mysql) following the same pattern already present in debezium-server-native-dist. This enables trimmed distribution builds using profile combinations that produce a zip/tar.gz containing only the required connector and sink dependencies.

This is part of an upcoming Debezium feature to support minimal, connector-specific server distributions. More information will be shared in the coming weeks about this new system and how users can take advantage of it. (dbz#2421, dbz#2433)

Debezium for CockroachDB

Schema and table in the source info block

The CockroachDB connector now emits schema and table fields in the source info block of change events, matching the behavior of the PostgreSQL and SQL Server connectors. Previously, the source block carried only db and CockroachDB-specific fields (cluster, resolved_ts, hlc), which blocked JDBC sink topic-to-table routing using collection.name.format templates like ${source.schema}_${source.table}. (dbz#2432)

Optional consumer group offset commits for observability

The CockroachDB connector now supports an opt-in setting to asynchronously commit processed positions to the Kafka consumer group. The connector’s intermediate consumer stores positions in Connect offsets with explicit seeks, which is correct for delivery semantics but makes standard Kafka lag monitoring tools unreliable. For example, kafka-consumer-groups --describe shows no committed offset, and consoles alert on permanently growing lag.

With this option enabled, the connector mirrors its actual progress to the consumer group purely for observability, while correctness continues to rely on Connect offsets. (dbz#2472)

Container Images

PostgreSQL GUC logical decoder support

A recent PostgreSQL security update for PostgreSQL 15 and later introduces a new output_plugin_libraries GUC setting that restricts which logical decoding output plugins can start. By default, PostgreSQL now permits only pgoutput and test_decoding, so any updated PostgreSQL instance, including publicly available container images, will reject the decoderbufs plugin.

The Debezium PostgreSQL container images now explicitly configure this GUC to include decoderbufs alongside the default plugins. For users who have not yet migrated to pgoutput and continue to use decoderbufs, the output_plugin_libraries setting must be specified in the PostgreSQL server configuration to include decoderbufs. (dbz#2434)

About Debezium

Debezium is an open source distributed platform that turns your existing databases into event streams, so applications can see and respond almost instantly to each committed row-level change in the databases. Debezium is built on top of Kafka and provides Kafka Connect compatible connectors that monitor specific database management systems. Debezium records the history of data changes in Kafka logs, so your application can be stopped and restarted at any time and can easily consume all of the events it missed while it was not running, ensuring that all events are processed correctly and completely. Debezium is open source under the Apache License, Version 2.0.
