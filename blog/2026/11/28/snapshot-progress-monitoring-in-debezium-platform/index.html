Snapshot progress monitoring in the Debezium Platform

Indra Raj Shukla
November 28, 2026 · 6 min read
debezium-platform monitoring snapshots UI features

The Debezium Management Platform has been able to run snapshots for a while. An initial snapshot happens automatically on the first pipeline start, driven by snapshot.mode, and you can trigger an incremental snapshot anytime later yourself from the Platform UI. What was missing was visibility into what was actually happening behind the scenes.

Once a snapshot started, it disappeared. That is a long time to be in the dark, because snapshotting a large database is not a quick operation. It can run for hours, and until it finishes the backfill downstream is incomplete and you are the one being asked when it will be done. The failure modes are quiet too, as a table without a primary key gets skipped, a permission error knocks out another, and a single very large table holds up everything behind it. Although the logs are available in the UI, finding the relevant information still requires scrolling and searching through them, making what should be a routine check unnecessarily time-consuming.

Debezium already emits notifications throughout a snapshot, covering start, per table progress, per table completion, and the final outcome.

That is now improved, and this post walks through the new snapshot progress monitoring.

How the numbers reach the UI

The flow is straightforward. As a snapshot progresses, the connector emits notifications for each step which Debezium Server forwards to the Conductor. The Conductor aggregates these events into a consolidated view of the snapshot’s current progress and continuously pushes updates to the browser.

Once the snapshot completes its final state is saved as history, and the live progress view returns to its idle state. There’s nothing you need to configure or enable. The Platform takes care of wiring everything up when it deploys the pipeline.

Starting a snapshot

With default snapshot mode an initial snapshot runs on its own when the pipeline first starts, you can also trigger other snapshot from the Actions tab.

Action sends Debezium signals on your behalf. Pick an action from the dropdown and a form appears with the fields that action needs. You can start an incremental snapshot, and stop, pause or resume one that is already running, or start a blocking snapshot instead. You can also target specific tables and add filter conditions to narrow down which rows are included, and the action id comes prefilled with a UUID that you can replace with your own.

The Snapshots tab

Pipeline details has a new Snapshots tab. While a snapshot is running the tab title carries a badge, blue for Running and orange for Paused, so you can see snapshot status without actively monitoring it.

Inside, the tab is split into Snapshot progress and Snapshot history.

Snapshot progress

At the top is the global bar with the overall percentage, and under it a summary line carrying the status, the start time, the elapsed duration, how many tables are done out of the total, and the total rows scanned so far. The elapsed time ticks live while the snapshot is running, counted from startedAt rather than waiting on the next event.

Below that is the per table breakdown, ordered the way you want to read it: completed tables first, then anything skipped or failed, then the table currently being read, then what is still pending. Each row shows the table name, its status, progress, and rows scanned.

When the notification carries information about a specific table’s progress, the progress can be measured more precisely. Where it cannot, the row falls back to a spinner and a live rows scanned counter rather than showing a misleading zero. You will see this mostly on incremental snapshots, and the counter keeps moving, so a spinner means the table is being read and not that something is stuck.

There is deliberately no scan rate and no ETA. Both are easy to compute and easy to get wrong when table sizes vary by orders of magnitude, so we left them out rather than ship a number nobody should trust.

Snapshot history

When nothing is running, the progress view says so, and the history view is where the interesting part is.

Completed runs are listed newest first with type, outcome, tables completed out of total, rows scanned, duration, and date. Expand a row and you get the per table breakdown for that run, which is how you answer "why did last night’s snapshot take forty minutes" after the fact.

You can filter by type or by outcome, and by time using the presets (last 6, 12, or 24 hours) or a custom range. History is kept for 30 days by default.

One outcome worth explaining is Unknown. If the Conductor was down when a snapshot finished, it never saw the terminal notification, and a run that is no longer reporting would otherwise sit in Running forever. A watchdog closes those after 15 minutes of silence and records the outcome as unknown, which is a lot more honest than a progress bar frozen at 73%.

Knowing a snapshot’s status

The tab is where you go when you already know there is a snapshot worth watching. Two other places in the UI tell you that in the first place, and both of them hand you straight to the tab.

Pipeline Overview

The Overview is where a pipeline tells you what it is doing right now, so it is the natural home for this. Snapshot progress has joined what you find there, as a compact card that is present while a snapshot is running and gone once the pipeline is idle again.

It shows the snapshot type, the global bar, the percentage, the table count, and how long it has been running. View details takes you to the Snapshots tab.

Pipeline list

The pipeline listing page now shows a snapshot indicator next to the pipeline name, for snapshots that are running or paused. It is absent when nothing is active, so an idle list stays as clean as it was, and clicking it takes you straight to that pipeline’s Snapshots tab.

Try it out

Update to the latest Platform images, open a pipeline, and trigger an incremental snapshot from the Actions tab. The Snapshots tab picks up the label as soon as the first notification arrives, and the Overview card appears alongside it. A pipeline starting for the first time gives you the initial snapshot view for free.

If you want something with enough data to actually watch, the Debezium Platform examples bring up a local cluster with PostgreSQL, Kafka and the Platform already wired together.

Conclusion

Snapshots was the part of a pipeline’s life that the Platform UI ran but could not show you. Now a long snapshot is something you can watch, a stalled one is something you notice, and a finished one is something you can look back at.

About Debezium

Debezium is an open source distributed platform that turns your existing databases into event streams, so applications can see and respond almost instantly to each committed row-level change in the databases. Debezium is built on top of Kafka and provides Kafka Connect compatible connectors that monitor specific database management systems. Debezium records the history of data changes in Kafka logs, so your application can be stopped and restarted at any time and can easily consume all of the events it missed while it was not running, ensuring that all events are processed correctly and completely. Debezium is open source under the Apache License, Version 2.0.
