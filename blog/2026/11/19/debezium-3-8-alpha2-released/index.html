Debezium 3.8.0.Alpha2 Released

Chris Cranford
November 19, 2026 · 14 min read
releases mongodb mysql mariadb postgres sqlserver cassandra oracle db2 vitess outbox spanner jdbc informix ibmi cockroachdb yashandb ingres tidb milvus sqlite cli elasticsearch

With November in full swing, we’re pleased to announce Debezium 3.8.0.Alpha2, the second preview release of the 3.8 series.

This release brings initial snapshots to the TiDB connector. Debezium Platform gains configurable message formats for pipelines and monitoring that works with secured Prometheus deployments. Oracle LogMiner users get faster and more reliable change capture, and there are many bug fixes across the connectors. There are a few breaking changes for the Oracle connector to review before upgrading.

Breaking changes

With any new release of software, there can be breaking changes. This release is no exception, so let’s discuss the major changes you should be aware of before upgrading to Debezium 3.8.0.Alpha2

Debezium for Oracle

Snapshot locks are held for the whole snapshot

During an initial snapshot, Oracle raises an ORA-01466 error if a captured table’s definition changes while its data is being read. Debezium previously offered snapshot.database.errors.max.retries to retry the table when this happened. In practice, the retry fails with the same error each time, so this property has been removed.

Instead, the connector now focuses on preventing the error. In the default shared locking mode, each captured table stays locked until its data has been read, rather than only while its schema is captured. Other sessions can still read and write these tables, but most DDL changes wait until the snapshot finishes.

For stricter protection, a new extended locking mode is also available. It blocks all DDL, including the non-blocking DDL supported by Oracle 23.3 and later. Because this mode also pauses writes to the captured tables during the snapshot, the connector waits for each lock no longer than snapshot.lock.timeout.ms.

Before upgrading, we recommend removing snapshot.database.errors.max.retries from your connector configuration, as it is no longer recognized. Please also be aware that DDL on captured tables may now wait while an initial snapshot is in progress. If that is a concern for your environment, snapshot.locking.mode can be set to none, provided that no DDL is applied to the captured tables during the snapshot. (dbz#2787)

Extended string columns are captured correctly

When an Oracle database uses MAX_STRING_SIZE=EXTENDED, some VARCHAR2 and NVARCHAR2 columns could be emitted as null during streaming instead of carrying their new value. This affected columns whose declared length was small, but whose size in bytes could exceed 4000, such as VARCHAR2(2000 CHAR) in a database using the AL32UTF8 character set.

The connector now checks each column’s size in bytes rather than its declared length, and records this in the schema history. With lob.enabled set to true, these columns are now captured as expected.

Schema history recorded by earlier versions does not include this byte size information. If your database uses extended strings, we recommend running a snapshot with snapshot.mode set to recovery after upgrading, so that the schema history is rebuilt. Until then, the connector continues to use the previously recorded lengths and logs a warning for each table that may be affected. (dbz#2794)

Debezium Core

Periodic compaction for the RocksDB reselect cache

The reselect columns post processor can use RocksDB to cache column values, which is especially helpful for large LOB values. However, RocksDB only reclaims the disk space of expired entries when it compacts its files, which can happen rarely for a cache that receives few writes.

The new reselect.cache.rocksdb.periodic.compaction.seconds property lets you control how often this compaction runs. When a time-to-live is configured with reselect.cache.ttl.ms, RocksDB compacts every 30 days by default, so a lower value frees disk space sooner. (dbz#2865)

{
  "post.processors": "reselector",
  "post.processors.reselector.type": "io.debezium.processors.reselect.ReselectColumnsPostProcessor",
  "post.processors.reselector.reselect.cache.enabled": "true",
  "post.processors.reselector.reselect.cache.type": "io.debezium.storage.rocksdb.reselect.RocksDbReselectColumnCache",
  "post.processors.reselector.reselect.cache.ttl.ms": "86400000",
  "post.processors.reselector.reselect.cache.rocksdb.periodic.compaction.seconds": "86400"
}

Authentication for HTTP notifications

The HTTP notification channel can now deliver notifications to endpoints that require authentication. The new notification.http.authorization property defines the Authorization header sent with each notification, such as Bearer <token> or Basic <credentials>.

The value is treated as a secret, so it is masked in logs and in the connector status. When the property is not set, the channel works exactly as before. (dbz#3005)

JSON span context for ActivateTracingSpan

The ActivateTracingSpan transformation previously expected the stored tracing context to be a serialized Java Properties value. Many applications instead store headers such as traceparent and baggage as a JSON object.

The new tracing.span.context.format option can now be set to json to support this format directly. Only top-level string values are used, so the same column can safely hold other metadata. The default remains properties, so existing deployments are not affected. (dbz#3011)

More precise tracing span timestamps

The ActivateTracingSpan transformation now uses the most precise timestamp available in each event, preferring nanoseconds, then microseconds, then milliseconds. This gives more accurate span durations, which is particularly useful when Debezium is tuned for low latency. (dbz#3033)

Debezium for MongoDB

Memory limits for the change stream buffer

The connector reads change stream events ahead of time into an in-memory buffer. This buffer was sized by max.batch.size and was not limited by max.queue.size.in.bytes. With very large documents, it could use more memory than expected and cause the connector to run out of memory.

Two new properties now let you limit this buffer without reducing your batch size:

  • cursor.buffer.max.events limits how many events are buffered.

  • cursor.buffer.max.bytes limits the approximate memory the buffered events use.

cursor.buffer.max.events=64
cursor.buffer.max.bytes=268435456

When neither property is set, the buffer behaves as before. (dbz#2745)

Debezium for Oracle

Experimental CTE query mode retired

The experimental CTE query mode, enabled through the internal internal.log.mining.use.cte.query option, has been retired. Benchmarks showed it was considerably slower than the standard query, and it required several other options, such as log.mining.window.max.ms, to be disabled.

If this option is still present in your configuration, the connector logs a warning and uses the standard query mode. (dbz#2984)

Faster LogMiner queries for many tables

The LogMiner query now evaluates its schema and table filters more efficiently. The improvement grows with the number of captured tables. In benchmarks with 1000 tables, the query ran nearly three times faster, helping to reduce lag on busy systems. (dbz#2991)

More accurate resume positions with buffered LogMiner

When using buffered LogMiner, the connector now treats rolled-back transactions the same way as committed ones when it records where to resume. After a restart, the connector no longer re-reads redo data for transactions whose rollback it had already processed.

In addition, a long-running transaction that is abandoned because of the retention setting is now handled consistently across restarts. (dbz#3048)

Debezium for PostgreSQL

Clearer warnings when a restart is waiting on the WAL

When the connector restarts, it looks for its last recorded position in the WAL. If that position cannot be found, the connector could wait without any indication of why.

The connector now logs a warning at startup when the replication slot and the stored offset do not line up. It also logs a periodic warning while it is waiting, with suggestions such as reviewing offset.mismatch.strategy. This makes a stalled restart much easier to understand and resolve. (dbz#1337)

Table and column comments

The PostgreSQL connector now supports include.schema.comments, which is already available for the MySQL, MariaDB, and Oracle connectors. When enabled, column comments are included as documentation in the event schemas, so this metadata travels downstream together with your data.

include.schema.comments=true

Comments are read when the connector takes a snapshot or refreshes a table’s schema. A comment changed on its own is picked up at the next schema refresh. The option is disabled by default. (dbz#2534)

Debezium Quarkus Extensions

Stopping the engine with @ShutdownCondition

Quarkus applications can now stop the Debezium engine based on a condition, using the new @ShutdownCondition annotation. This is useful, for example, to stop once an initial_only snapshot has been fully delivered.

Annotate a bean method that receives a SourceRecord and returns a boolean. When the method returns true, the engine stops. The BEFORE and AFTER phases control whether this happens before or after the record’s batch reaches your consumers.

@ShutdownCondition(Phase.AFTER)
boolean stopOnOrders(SourceRecord record) {
    return "dbserver1.inventory.orders".equals(record.topic());
}

This annotation is currently incubating. (dbz#3034)

Debezium Platform

Configurable message formats for pipelines

Pipelines previously always used JSON for message keys and values. You can now choose a different format, such as Avro with a schema registry, by adding debezium.format.key, debezium.format.value, or debezium.format.header as additional properties on a source. Related options can be set the same way.

{
  "debezium.format.value": "json",
  "debezium.format.value.schemas.enable": "false"
}

When no format is specified, pipelines continue to use JSON. (dbz#1963)

Easier table selection for large catalogs

The table explorer is now easier to use with databases that contain many schemas and tables. (dbz#2946)

  • The current schema name stays visible while scrolling.

  • Each schema shows how many of its tables are selected, and a summary lists your full selection.

  • Searches show how many tables matched, and expand and collapse work on search results.

Table selection on a large catalog

Monitoring with secured Prometheus deployments

The monitoring panels could previously only connect to a Prometheus server that required no authentication. On OpenShift, Prometheus is typically secured, so the panels did not display any data.

The conductor can now connect using a bearer token or basic credentials, and it can trust a private certificate authority. These options are available in the Helm chart under monitoring.prometheus, and the chart’s README includes an example for OpenShift. (dbz#3049)

Debezium CLI

Simpler, structured configuration

The CLI configuration is now organized into clear sections for the platform, container builds, Maven, and OCI settings. Default values ship with the CLI and are combined with your own settings, making it easy to see what can be configured. (dbz#2886)

platform:
  active: default
  environments:
    default:
      url: "http://localhost:8080"
build:
  container:
    base:
      image: "eclipse-temurin"
      tag: "21-jre"

Debezium for TiDB

Initial snapshots

The TiDB connector can now capture the existing data in your tables, not just the changes made after the changefeed was created. It supports the initial and initial_only snapshot modes, in addition to the default no_data.

The snapshot reads all captured tables at a single consistent point in time, without locking them. Streaming then continues seamlessly from where the snapshot ended, without duplicate events. Connection details for the TiDB SQL endpoint are only required when a snapshot mode that captures data is used. (dbz#2439)

Debezium Examples

Up-to-date JBang examples

The Debezium version used by the JBang examples is now updated automatically, so the examples always match the current release. (dbz#2979)

BinaryLog Client

Java 17 is now required

The MySQL binlog client now requires Java 17, matching the Debezium connectors that use it. This change does not affect Debezium users. Applications that use the client directly with an older Java version can continue to use release 0.41.5 or earlier. (dbz#3069)

About Debezium

Debezium is an open source distributed platform that turns your existing databases into event streams, so applications can see and respond almost instantly to each committed row-level change in the databases. Debezium is built on top of Kafka and provides Kafka Connect compatible connectors that monitor specific database management systems. Debezium records the history of data changes in Kafka logs, so your application can be stopped and restarted at any time and can easily consume all of the events it missed while it was not running, ensuring that all events are processed correctly and completely. Debezium is open source under the Apache License, Version 2.0.
