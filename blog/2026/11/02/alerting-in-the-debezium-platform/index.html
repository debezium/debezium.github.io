Alerting in the Debezium Platform

Indra Raj Shukla
November 2, 2026 · 7 min read
debezium-platform monitoring alerting UI features

The Debezium Management Platform has been able to show you how your pipelines are doing for a while now. The monitoring dashboard tells you the event rate, the source lag, the queue utilization, whether the snapshot finished, and so on. But it is passive as it only helps while somebody is looking at it. In his mid-year Platform update, Mario listed alerting as one of the next things we wanted to tackle. That work has now landed.

The Platform can now watch those same panels for you and tell you when one of them crosses a line you care about. This post walks through what alerting looks like in the Platform, how a rule is defined, where notifications go, how an alert moves from quiet to firing, and where to review it all afterwards.

Quick recap of monitoring

Alerting is built on the monitoring panels, so it is worth recapping the path those numbers take.

A pipeline in the Platform is a Debezium Server instance deployed by the Debezium operator. The Platform wires it up with the OpenTelemetry Java Agent, which exports metrics over OTLP to an OpenTelemetry Collector. The collector re-exposes them in Prometheus format, Prometheus scrapes the collector, and the Conductor (Debezium Platform backend) queries Prometheus with PromQL when the UI asks for a panel.

For more details, take a look at the pipeline monitoring documentation.

Alerting

Rules apply a comparison and threshold to a monitoring panel. They evaluate globally, triggering a separate incident for each breaching pipeline, including those created later. You can find the full design in DDD-57: Alerting for Debezium Platform.

Anatomy of an alert rule

You will find a new Alerts section in the left navigation, with Rules, Channels and Events.

In the alert rule form, the fields read as a sentence:

When    Source Lag          (panel)
Reduce  last                (how to collapse the time series)
Is      greater than  10    (comparison)
For     5 minutes           (how long it has to hold)

Read left to right, that is: when the last value of Source Lag is greater than 10 seconds for 5 minutes.

The pieces:

When: the monitoring panel, picked from a dropdown that groups panels into Streaming and Snapshot, exactly as on the monitoring tab.

Reduce: a panel is a time series, and a rule needs a single number. The reduce function decides how to get one: last, avg, min, max or sum. last is the default and is what you want for gauges like lag, connection status or queue utilization. avg is the better choice for noisy rate panels, where a single spike should not wake anybody up.

Evaluation window: how much history the reduce function looks at, from 1 minute to 1 hour, 5 minutes by default. It is ignored when reduce is last, and the form hides it in that case.

Is: the comparison, an operator such as greater than, with the threshold beside it. Once a panel is selected, its unit is shown next to the number, so a lag panel is entered in seconds and a utilization panel in percent.

For: the noise suppression knob, and the one worth getting right. The condition has to hold continuously for this long before the alert fires. Set it to Immediately and the slightest breach raises an alert, set it to 5 minutes and a transient blip resolves itself quietly.

Severity: Critical, Warning or Info. Severity is shown with both a colour and an icon rather than colour alone, and it determines whether the alert contributes to the badge in the header.

Additional channels: where to notify, on top of the UI itself.

A red dot in front of the name, as on pipeline-stalled in the screenshot above, means that rule has a firing incident. The status switch turns a rule off without deleting it, which is how you silence one during planned maintenance.

Where the notifications go

Alerts always appear in the Platform UI, so a freshly installed Platform gives you working alerting with no notification configuration at all. On top of that there are two more channel types, managed from Alerts → Channels:

Email: a list of recipients and an optional subject prefix.

Webhook: a URL, an HTTP method and optional headers, which is the integration point for Slack, PagerDuty, OpsGenie, Teams, or anything else that accepts a POST.

Channels are reusable: several rules can share one, and one rule can notify through several. Test, in the actions menu, sends a sample notification and reports back, so a bad SMTP setup shows up before a real incident does.

The webhook payload is intentionally flat and stable, with a version field so it can evolve without breaking your receiver:

{
  "version": "1",
  "status": "firing",
  "alert": {
    "ruleName": "high-source-lag",
    "severity": "CRITICAL",
    "pipelineId": "inventory-pipeline",
    "value": 15.2,
    "threshold": 10.0,
    "message": "Source lag (15.2s) exceeded threshold (10.0s)",
    "firedAt": "2026-10-25T14:30:00Z"
  }
}

The same shape is sent with "status": "resolved" when the incident closes, so a receiver can correlate the two.

The life of an alert

Saving a rule does not notify anyone by itself. Each time a pipeline crosses the line and comes back, that cycle is recorded as an incident.

From quiet to firing and back

The Platform runs an evaluation loop every 60 seconds by default. For each enabled rule it queries Prometheus, applies the reduce function, compares the result against the threshold for every pipeline reporting that metric, and moves that (rule, pipeline) pair through a small state machine:

Transition What happens

OK → Pending

The condition is met for the first time. Nothing is sent yet; the engine just remembers when it started.

Pending → OK

The condition cleared before the for duration elapsed. Silent reset, no notification. This is exactly what the for duration is there for.

Pending → Firing

The condition held for the whole for duration. An incident is created and notifications go out.

Firing → Resolved

The condition cleared. The incident is closed and a resolution notification goes out.

OK → Firing

Same as above but with for set to Immediately, skipping the pending state.

A firing alert sends one notification, and a resolution sends one. There is no repeat while it stays firing.

Alert events

The table lists each incident newest first. Expand a row for the value, the threshold and the message, and the pipeline name links to that pipeline’s monitoring dashboard. Filter by status or time range, and use Manage columns to choose which fields the table shows.

There is also a badge in the header, counting active Critical and Warning alerts across all pipelines. It takes the colour of the highest active severity: red when a Critical alert is firing, amber when the highest is a Warning. Clicking the badge opens this page filtered to firing incidents. Info alerts are recorded but left out of the badge.

A daily cleanup job removes resolved incidents older than the retention period, 30 days by default. Still-firing incidents are never purged, regardless of age.

Try it out

If you want to see it running end to end you can follow the platform monitoring and alert example in the debezium-examples repository. It brings up a local minikube cluster with PostgreSQL, Kafka, the OpenTelemetry Collector, Prometheus and the Platform, seeds a pipeline, and includes scripts that make the panels move by generating traffic, replaying a snapshot, and breaking the source connection.

From there, create a rule, trip it with one of those scripts, and watch it resolve.

Conclusion

Monitoring answered "how is my pipeline doing?" as long as you were looking. Alerting answers it when you are not.

Give it a try on the latest Platform images, and tell us which rules you end up writing.

About Debezium

Debezium is an open source distributed platform that turns your existing databases into event streams, so applications can see and respond almost instantly to each committed row-level change in the databases. Debezium is built on top of Kafka and provides Kafka Connect compatible connectors that monitor specific database management systems. Debezium records the history of data changes in Kafka logs, so your application can be stopped and restarted at any time and can easily consume all of the events it missed while it was not running, ensuring that all events are processed correctly and completely. Debezium is open source under the Apache License, Version 2.0.
