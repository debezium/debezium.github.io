Debezium 3.8.0.Alpha1 Released

Chris Cranford
November 2, 2026 · 25 min read
releases mongodb mysql mariadb postgres sqlserver cassandra oracle db2 vitess outbox spanner jdbc informix ibmi cockroachdb yashandb elasticsearch

As the leaves fall and November gets underway, we’re pleased to announce Debezium 3.8.0.Alpha1, the first preview release of the 3.8 series.

This release introduces a new Elasticsearch sink connector. It also brings snapshot progress monitoring to Debezium Platform, a new default mode for the JDBC sink, and improvements across many connectors. There are also many bug fixes and a few breaking changes to review before upgrading.

Read on for the full details!

Breaking changes

With any new release of software, there can be breaking changes. This release is no exception, so let’s discuss the major changes you should be aware of before upgrading to Debezium 3.8.0.Alpha1

Debezium for MySQL

REAL columns are now emitted as FLOAT64

MySQL and MariaDB treat REAL as a synonym for DOUBLE unless the REAL_AS_FLOAT SQL mode is enabled. Debezium already emitted these columns as FLOAT64 during snapshots, but when a table’s DDL was captured while streaming, the column was emitted as FLOAT32, silently truncating values to about seven significant digits.

The connectors now map REAL to FLOAT64 in all cases, so the schema is stable across snapshot and streaming, and no precision is lost. Default values for REAL columns are emitted as doubles accordingly.

If your consumers or Schema Registry subjects expect a float schema for these columns, they will now see double, so check your compatibility settings before upgrading. Tables captured before this change keep their recorded schema until the table model is rebuilt by a new snapshot or a later DDL statement on that table. If you previously used the JdbcSinkDataTypesConverter with treat.real.as.double as a workaround, it is no longer needed. (dbz#2217)

Debezium for PostgreSQL

NULL elements are preserved in ENUM arrays

A PostgreSQL ENUM array containing a NULL element, such as ARRAY['plain', NULL], previously failed schema validation. The entire array was then emitted as null, and if the column was declared NOT NULL, the connector stopped.

The element schema for ENUM arrays is now optional, matching how all other array types are handled, so values like ["plain", null] are preserved.

Because the array element schema changes from required to optional, consumers using Avro and Schema Registry will see a new schema version for affected columns. (dbz#2771)

VARBIT(1) columns are now emitted as bits

PostgreSQL accepts an empty bit string (B'') as a valid, non-null value in a VARBIT(1) column. Debezium mapped these columns to a boolean, so an empty value was emitted as null, and a NOT NULL column caused capture to stop.

VARBIT columns of any length are now consistently mapped to the io.debezium.data.Bits semantic type, a BYTES schema. This keeps B'', B'0', B'1', and SQL NULL distinct from one another. Fixed-length BIT(1) columns are not affected and are still emitted as booleans.

If you capture VARBIT(1) or BIT VARYING(1) columns, the field schema changes from BOOLEAN to BYTES, so update any consumers or sink mappings that rely on a boolean value. (dbz#2772)

Debezium Server

Kafka sink delivery timeout now defers to the producer

The Kafka sink had two settings that controlled how long to wait for record delivery: the producer’s own delivery.timeout.ms and the sink’s wait.message.delivery.timeout.ms. Depending on how the two were set, the sink could fail a batch while the producer was still retrying, or the sink setting would never take effect at all.

The default for wait.message.delivery.timeout.ms is now 0, which means the sink waits for the producer to finish and relies solely on the producer’s delivery.timeout.ms.

If you relied on the previous 30 second default, configure the timeout through debezium.sink.kafka.producer.delivery.timeout.ms instead, or set wait.message.delivery.timeout.ms explicitly to restore the old behavior. (dbz#2597)

Zerobus sink event filter removed

The Databricks Zerobus sink introduced in 3.7 shipped with its own event filter, configured through the debezium.sink.zerobus.filter.* properties. Debezium’s standard mechanisms already cover the same cases, so the sink-specific filter has been removed.

If you configured debezium.sink.zerobus.filter.* properties, migrate them to the standard equivalents:

  • To skip operations, use skipped.operations, and use snapshot.mode=no_data to skip snapshot read events.

  • To filter by topic or header, use the Filter transformation with the TopicNameMatches or HasHeaderKey predicates.

  • To filter by value, use the Filter transformation with the new FieldValueMatches predicate.

Note that HasHeaderKey only checks whether a header is present, so there is currently no direct replacement for matching on a header value. (dbz#2915)

Debezium Core

Claim-check storage for oversized events

A change event can exceed the Kafka producer or broker message size limit when columns hold very large values. Until now, the options were to raise transport limits, truncate the large values with the EnforceRecordSize transformation, or exclude the columns entirely and lose their data.

The EnforceRecordSize transformation now offers an opt-in claim_check strategy that works with any connector. When an event exceeds max.bytes, the complete original record is written to external storage, and the configured columns in the emitted event are replaced with a small marker that points to the stored object. The marker is only emitted after the write succeeds, so a failed write never results in a reference to data that wasn’t stored.

Storage is pluggable, and Debezium ships with an Amazon S3 implementation. The following example stores oversized records from the inventory.customers table in S3:

transforms=EnforceRecordSize
transforms.EnforceRecordSize.type=io.debezium.transforms.EnforceRecordSize
transforms.EnforceRecordSize.max.bytes=1048576
transforms.EnforceRecordSize.strategy=claim_check
transforms.EnforceRecordSize.claim.check.columns.include.list=inventory[.]customers[.]payload
transforms.EnforceRecordSize.claim.check.storage.class=io.debezium.storage.s3.S3OversizedRecordStorage
transforms.EnforceRecordSize.claim.check.storage.base.path=s3://my-bucket/debezium/oversized
transforms.EnforceRecordSize.claim.check.storage.region=us-west-1

The debezium-storage-s3 artifact must be on the same plugin path as the connector. Debezium never deletes stored objects, so configure a retention policy, such as an S3 lifecycle rule, to expire them once consumers no longer need them. (dbz#2379)

Signal data collection is validated up front

The signal.data.collection setting is now validated when the connector configuration is validated, for the MySQL, MariaDB, PostgreSQL, SQL Server, Oracle, and MongoDB connectors. Misconfigurations are reported immediately rather than surfacing later when a signal is sent.

The validation checks that the table or collection exists and that the value uses the form the connector expects. If the form is wrong, the error message names the exact value to use instead. For relational connectors, it also checks that the table resolves to at least three columns after column filters are applied. (dbz#2633)

New StringifyFields transformation

Some sinks store flexible data in JSON text columns and reject native struct, array, or map values. Examples include Databricks Delta VARIANT columns and PostgreSQL JSON and JSONB columns.

The new StringifyFields transformation serializes selected fields to JSON strings and changes their type to STRING, while the rest of the record stays strongly typed. Fields can be addressed by a dot path, such as after.payload, which makes it easy to handle nested data, for example after a MongoDB document is flattened with ExtractNewDocumentState.

The following example serializes the nested payload field in a change event:

transforms=stringify
transforms.stringify.type=io.debezium.transforms.StringifyFields
transforms.stringify.fields=after.payload,before.payload

Because the before and after fields share the same schema, a nested path inside the envelope must be listed under both. For a top-level field, such as one produced by a flattening transformation, list the field name on its own, for example fields=properties. (dbz#2903)

Debezium for MongoDB

Resume tokens in event source metadata

MongoDB change events now include an optional source.resume_token field that contains the full resume token as a JSON string, formatted according to the json.serialization.mode setting. Consumers can use this token with MongoDB’s resumeAfter to pick up a change stream from a specific event.

The token is only present for streaming events, and snapshot records carry a null value. For split events that are reassembled, the token of the final fragment is exposed. (dbz#718)

Readable starting timestamps

Starting capture from a point in time previously required capture.start.op.time, which expects a packed 64-bit BSON timestamp that is easy to confuse with a Unix timestamp.

The new capture.start.timestamp property accepts readable values instead, including Unix seconds, ISO-8601 timestamps such as 2026-09-11T00:00:00Z, and BSON Timestamp Extended JSON. It applies when the connector starts without a stored offset, and stored offsets still take precedence. MongoDB must still retain the requested position in the oplog. (dbz#2610)

Independent and required pre- and post-image policies

The MongoDB connector previously requested pre- and post-images with MongoDB’s whenAvailable policy, so a missing image went unnoticed. For workloads that depend on complete document states, this could silently produce incomplete events.

Pre- and post-images are now configured independently with two new properties, and each one can be marked as required. When a required image is unavailable, for example because image recording was disabled on a collection or the retained images expired, the connector fails visibly instead of emitting an incomplete event.

Property Value Behavior

off (default)

when_available

The connector fails if a pre-image is unavailable.

capture.mode.post.image

off

lookup (default)

The full document is retrieved with a separate lookup.

post_image

post_image_required

For example, the following configuration requires both images:

capture.mode.pre.image=required
capture.mode.post.image=post_image_required

Images must be enabled on the captured collections with changeStreamPreAndPostImages, which requires MongoDB 6.0 or later.

The capture.mode.full.update.type property defaults to lookup. If you set either new property explicitly, including to off, it takes precedence over the deprecated settings for that image only. (dbz#2688)

query.fetch.size applies to change streams

The query.fetch.size property is now honored when opening MongoDB change streams, letting you tune how many change stream documents are fetched per server response. This setting is independent of snapshot.fetch.size and max.batch.size.

When the property is omitted or set to 0, the connector keeps its current behavior and lets the driver decide. (dbz#2690)

Lower latency after idle periods

When the connector’s internal buffer was empty, the streaming consumer slept between polls, so an event arriving during that sleep waited until the sleep finished.

The consumer is now woken as soon as a buffered event becomes available, reducing latency for events that arrive after an idle period. (dbz#2754)

Required images work with regex collection filters

With a required image policy, the connector previously failed when an excluded collection without image recording changed, as long as it was within the change stream scope. This affected the default filters.match.mode=regex with capture.scope set to deployment or database.

Excluded collections are now filtered out before MongoDB looks up images, so only the collections you capture need image recording enabled. (dbz#2881)

Debezium for MySQL

Schema from binlog metadata without a schema history topic

When the server runs with binlog_row_metadata=FULL, available in MySQL 8.0 and later and MariaDB 10.5 and later, every binlog event carries complete column metadata for the table it changes.

The new opt-in binlog.metadata.based.schema property lets the MySQL and MariaDB connectors rebuild table schemas directly from that metadata. When enabled, the connector no longer needs a schema history topic, which removes the bootstrap, recovery, and operational overhead of managing one. The connector fails fast at startup if binlog_row_metadata is not set to FULL. (dbz#978)

Debezium for Oracle

Column reselection uses the physical standby

When the connector is configured with capture.mode=physical_standby, the ReselectColumnsPostProcessor now automatically queries the standby database through the secondary connection. Previously, reselection queries always went to the primary database, even though the connector was otherwise reading from the standby.

No additional configuration is needed, and this keeps reselection load off the primary. Other capture modes continue to query the primary database as before. (dbz#2444)

Faster transaction cache event counting

The transaction cache previously recomputed the count of all events across all transactions every time an event was processed, which took a noticeable share of event processing time. It now keeps a running count, removing that overhead from the hot path. (dbz#2777)

Faster eldest transaction lookup

Finding the eldest transaction in the cache runs on every commit. Its implementation has been streamlined, which improves throughput for workloads with many interleaved transactions that each contain only a few events. (dbz#2780)

Heartbeats for quiet tables with unbuffered LogMiner

With the unbuffered LogMiner adapter, the connector did not emit periodic heartbeats when the captured tables received no changes, even though the database itself remained active. As a result, the connector’s offset could not advance.

Unbuffered LogMiner now emits heartbeats on quiet streams just like the buffered adapter, so the safe recovery position can be checkpointed as it advances. (dbz#2781)

Debezium for PostgreSQL

Text array column defaults

Adding a text[] or varchar[] column with a default value, such as DEFAULT '{}', previously dropped the default from the generated schema. This broke Avro and Schema Registry compatibility checks and could stop the connector.

Default values for these array columns are now parsed and included in the schema. (dbz#1269)

Faster pgoutput string decoding

String decoding for pgoutput messages has been optimized to avoid unnecessary copies and allocations. Benchmarks show roughly 1.4 to 2 times higher throughput for the length-prefixed strings found on the hot path, and up to 4.6 times for null-terminated strings, while also reducing garbage collection pressure. (dbz#2710)

Debezium for SQL Server

Non-blocking reads from CDC tables

Queries that read directly from SQL Server CDC tables now use WITH (NOLOCK). This keeps Debezium’s reads from blocking the SQL Server capture job or production workloads.

This follows Microsoft’s guidance for CDC. Because CDC change tables contain only committed, insert-only data, these reads cannot see uncommitted changes. (dbz#2334)

Faster change timestamps in function query mode

In the default data.query.mode=function, the change query computed each row’s commit timestamp by calling a SQL Server function once per row. Function mode now resolves timestamps the same way as direct mode already does, avoiding the per-row function cost on high-volume tables without changing which rows are returned. (dbz#2693)

Debug logging of captured CDC tables

The connector already logged CDC-enabled tables that were excluded by its filters, but nothing listed the tables it actually captures. It now logs the CDC-enabled tables on the include list at DEBUG level, which makes it easier to troubleshoot why a table isn’t being captured. (dbz#2712)

Debezium JDBC sink

Resilient schema evolution with multiple tasks

When several sink tasks consumed from a multi-partition topic with schema evolution enabled, they could all try to add the same missing column at once. The first task succeeded, while the others failed with a "column already exists" error and stopped.

The sink now handles this race gracefully, so tasks keep processing records instead of failing. (dbz#2302)

Shared Sink Framework is now the default

The JDBC sink connector now uses the Shared Sink Framework by default. The framework adds a common buffering and batch processing layer, which deduplicates records by primary key within a batch and can route failing records to the Kafka Connect errant record reporter. Documentation for the new configuration options has been added as well.

The new buffer.mode property controls how records with the same key are handled within a batch, and it replaces the deprecated use.reduction.buffer property, which no longer has any effect. Its default is deduplication, which keeps only the most recent event for each key, similar to enabling the old reduction buffer. If you did not previously set use.reduction.buffer=true, set buffer.mode=passthrough to keep the same behavior as before, where every change event is written to the database:

buffer.mode=passthrough

If you run into problems with the new mode, you can switch the connector back to the legacy mode with the following setting:

internal.enable.sces=false

If you need to fall back, please let us know about the problem so we can address it. (dbz#2512)

MULTIPOLYGON support for SingleStore

The SingleStore JDBC sink previously rejected MULTIPOLYGON values, so spatial data from sources such as PostGIS could not be written to a SingleStore GEOGRAPHY column. These values are now converted to SingleStore’s POLYGON representation, which can describe multiple regions and holes. (dbz#2880)

Optional polygon repair for SingleStore

SingleStore limits coordinates to eight decimal places and validates polygons on insert, so some source geometries are rejected after rounding or because they self-intersect. In one migration, about 8% of records failed for this reason.

The new dialect.singlestore.geometry.repair.enabled option, disabled by default, rounds coordinates and repairs invalid polygons before writing them. Repair may change boundaries, holes, or regions, so enable it only when that tradeoff is acceptable. (dbz#2909)

Debezium Elasticsearch sink

New Elasticsearch sink connector

Debezium now includes a sink connector for Elasticsearch that consumes events from Kafka topics and writes them as documents to Elasticsearch indices. It works with native Debezium change events, flattened events, and plain structured events, and it preserves the meaning of Debezium’s logical types. For example, decimals are written as numbers, temporal values as ISO-8601 strings, JSON columns as embedded objects, geometry as GeoJSON, and vectors as arrays.

Every write and delete is addressed by a stable document ID, derived from the record key by default. If an event is delivered more than once after a restart or rebalance, it updates the same document rather than creating a duplicate. The connector supports Elasticsearch 8.x and 9.x clusters, while OpenSearch and other forks are not supported.

The connector runs in Kafka Connect, and Debezium Server also includes it as a built-in elasticsearch sink. The following examples show a basic configuration for each:

Kafka Connect
{
    "name": "elasticsearch-connector",
    "config": {
        "connector.class": "io.debezium.connector.elasticsearch.ElasticsearchSinkConnector",
        "tasks.max": "1",
        "connection.url": "https://elasticsearch:9200",
        "connection.auth.mode": "basic",
        "connection.username": "elastic",
        "connection.password": "changeme",
        "topics": "inventory.customers",
        "collection.name.format": "customers",
        "write.method": "upsert",
        "primary.key.mode": "record_key",
        "mapping.mode": "create_if_absent"
    }
}
Debezium Server
debezium.sink.type=elasticsearch
debezium.sink.elasticsearch.connection.url=https://elasticsearch:9200
debezium.sink.elasticsearch.connection.auth.mode=basic
debezium.sink.elasticsearch.connection.username=elastic
debezium.sink.elasticsearch.connection.password=changeme
debezium.sink.elasticsearch.write.method=upsert
debezium.sink.elasticsearch.primary.key.mode=record_key

In Debezium Server, any connector property can be set with the debezium.sink.elasticsearch. prefix. The dead letter queue is a Kafka Connect feature, so in Debezium Server a record that Elasticsearch rejects stops the server instead, ensuring no event is committed past a failed write.

The connector is currently incubating, so we encourage you to try it out and share your feedback, but it is not yet recommended for production use. Configuration properties, defaults, and behavior may change in future releases. (dbz#819)

Debezium Quarkus Extensions

Debezium components as CDI beans

Debezium normally creates pluggable components, such as topic naming strategies, post-processors, and custom converters, from class names in the configuration or through Java’s ServiceLoader. In a Quarkus application, you can now define these components as CDI beans instead, so they can take part in dependency injection like the rest of your application.

When the Debezium Engine Quarkus extension finds a bean of a supported type, it uses that bean automatically, with no additional configuration. If a class is also configured for the same component, such as topic.naming.strategy, the bean takes precedence. Supported types include TopicNamingStrategy, PostProcessor, CustomConverter, HeartbeatFactory, SchemaHistory, and TransactionMetadataFactory.

For example, the following bean adds a custom prefix to every topic name:

PrefixTopicNamingStrategy.java
@ApplicationScoped
public class PrefixTopicNamingStrategy implements TopicNamingStrategy<DataCollectionId> {

    @Override
    public void configure(Properties props) {
    }

    @Override
    public String dataChangeTopic(DataCollectionId id) {
        return "inventory." + id.identifier();
    }

    @Override
    public String schemaChangeTopic() {
        return "inventory.schema-changes";
    }

    @Override
    public String heartbeatTopic() {
        return "inventory.heartbeat";
    }

    @Override
    public String transactionTopic() {
        return "inventory.transaction";
    }

    @Override
    public String sanitizedTopicName(String topicName) {
        return topicName;
    }
}

When your application runs more than one engine, annotate the bean with @Engine("<engine-id>") to apply it to a single engine. A bean with the @Engine annotation takes precedence over a bean without one, which applies to all engines. (dbz#1349)

Debezium Platform

Snapshot progress monitoring

Debezium Platform can now show the progress of initial and incremental snapshots. (dbz#2536)

Duplicate an existing transform

Creating a transform similar to an existing one previously meant re-entering its class, configuration, and predicate. You can now duplicate a transform, which opens the create form pre-filled with a unique name, while the original stays unchanged.

In the pipeline designer, you can either reuse an existing transform or create a copy that is attached only to the current pipeline. (dbz#2644)

Duplicating an existing transform

Snapshot progress on Overview and a new Snapshots tab

The pipeline overview page now shows a snapshot card while a snapshot is running, with the snapshot type, overall progress, completed tables, and elapsed time.

A new Snapshots tab in the pipeline details page shows a per-table breakdown with status, progress, and rows scanned, along with the reason for any skipped or failed tables. Progress updates are streamed live, and a badge appears on the tab while a snapshot is active. (dbz#2724)

Snapshot progress on the Overview and Snapshots tab

Host deployment example

A new runnable example in Debezium Examples demonstrates host-based pipeline deployment on a Linux VM. It walks through letting Conductor discover and provision the VM, creating a PostgreSQL to HTTP pipeline, and verifying a change event end to end. (dbz#2855)

Debezium Server

NATS offset and schema history storage

A new debezium-storage-nats module lets Debezium store connector offsets and schema history in NATS JetStream. If you already use NATS, for example as a Debezium Server sink, you can keep Debezium’s state there too, without running Kafka or another storage service.

Offsets are stored in a NATS Object Store bucket, and schema history is stored in a JetStream stream. Multiple connectors can share the same offset bucket, and the schema history stream is created automatically if it does not exist.

The following example configures both stores:

offset.storage=io.debezium.storage.nats.offset.NatsOffsetBackingStore
offset.storage.nats.url=nats://localhost:4222
offset.storage.nats.bucket.name=debezium-offsets

schema.history.internal=io.debezium.storage.nats.history.NatsSchemaHistory
schema.history.internal.nats.url=nats://localhost:4222
schema.history.internal.nats.stream.name=debezium-schema-history
schema.history.internal.nats.subject=debezium.schema.history

In Debezium Server, prefix these properties with debezium.source.. The debezium-storage-nats artifact must be on the classpath, and both stores support user and password or token authentication, as well as TLS. (dbz#1079)

Debezium for Spanner

Change streams for placement tables

The Spanner connector now supports change streams for placement tables. (dbz#1415)

Debezium for YashanDB

Advanced YStream client options

The YashanDB connector previously exposed only a subset of the YStream client’s options, so using any other option required a new connector release.

The new ystream.additional.properties setting accepts a list of name=value entries that are passed to the YStream client, and a dedicated ystream.fault.tolerance property has been added. Dedicated connector properties take precedence when both configure the same option, and invalid entries are rejected with a clear error. (dbz#2861)

Container Images

Fedora 44 base image

The Debezium container images have been upgraded to the Fedora 44 base image. (dbz#2774)

Debezium Examples

JBang and Hardwood Parquet example

A new example shows how to build a CDC pipeline with a single JBang script that uses the Debezium Quarkus extension and Hardwood. It captures snapshot events from PostgreSQL and writes them to Apache Parquet files. You can find the example in the debezium-examples repository. (dbz#2963)

About Debezium

Debezium is an open source distributed platform that turns your existing databases into event streams, so applications can see and respond almost instantly to each committed row-level change in the databases. Debezium is built on top of Kafka and provides Kafka Connect compatible connectors that monitor specific database management systems. Debezium records the history of data changes in Kafka logs, so your application can be stopped and restarted at any time and can easily consume all of the events it missed while it was not running, ensuring that all events are processed correctly and completely. Debezium is open source under the Apache License, Version 2.0.

Get involved

We hope you find Debezium interesting and useful, and want to give it a try. Follow us on Twitter @debezium, chat with us on Zulip, or join our mailing list to talk with the community.
