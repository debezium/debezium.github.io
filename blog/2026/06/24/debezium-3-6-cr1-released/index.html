Debezium 3.6.0.CR1 Released

Chris Cranford
June 24, 2026 · 8 min read
releases mongodb mysql mariadb postgres sqlserver cassandra oracle db2 vitess outbox spanner jdbc informix ibmi cockroachdb yashandb

As we approach the final stages of the Debezium 3.6 release cycle, we’re excited to announce the release of Debezium 3.6.0.CR1, the first candidate release for this milestone.

This release delivers several notable enhancements, including Spanner Omni compatibility, a monitoring REST API and multi-panel dashboard in Debezium Platform, JDBC sink support in Platform, off-heap memory management for table history and schemas using RocksDB, and performance improvements that significantly reduce allocation and CPU overhead in the MySQL connector’s poll path. On the bug-fix front, this release resolves a KafkaSchemaHistory recovery race condition, PostgreSQL varbit column handling, Vitess timestamp processing, NanoTimestamp overflow for extreme dates, and CockroachDB temporal type alignment.

Read on for all the details!

Debezium Core

Off-heap memory management for table history and schemas

Internal schema history and table mappings can consume a significant amount of heap memory, especially for connectors tracking many tables. This release introduces a new pluggable interface for externalizing table mapping storage, along with a RocksDB-based implementation that stores table history and schema mappings on disk rather than in heap memory. This allows connectors to manage large schema histories without excessive memory pressure, improving stability in environments with many captured tables. (dbz#2015)

Debezium for MySQL

Reduced allocation and CPU overhead in poll batch conversion

The MySQL connector’s doPoll() method is called repeatedly by Kafka Connect and previously used a stream/collector pipeline to unwrap DataChangeEvent objects into SourceRecord instances. This release replaces that with a pre-sized ArrayList and a direct loop, reducing memory allocation by approximately 75% and CPU overhead by 31–42% on this hot path. For the default max.batch.size of 2048, per-operation allocation drops from roughly 34 KB to 8 KB, meaningfully reducing garbage collection pressure under sustained load. (dbz#2113)

Debezium for Oracle

Improved diagnostics for missing archive logs

During the log gathering process, when all fetch retries are exhausted, Debezium previously threw a generic LogFileNotFoundException stating that none of the log files contain the specified SCN. Now, Debezium performs an additional check against V$ARCHIVED_LOG to determine whether the required log has been purged, providing a clearer and more actionable error message when a log has been deleted rather than simply missing. (dbz#1532)

Unified Oracle JDBC driver version

The Oracle connector previously maintained two separate JDBC driver versions: 21.15 for Oracle 19/21 and 23.3.x for Oracle 23/26. This release consolidates to a single latest Oracle 23.26.x driver across all supported database versions, simplifying dependency management and ensuring consistent behavior. The driver is fully backward-compatible with Oracle 19 and 21 databases. (dbz#1837)

Exponential back-off for XStream attach retries

When the XStream adapter fails to attach to the Outbound Server, it retries up to 10 times. Previously these retries occurred in rapid succession over approximately 10–20 seconds, often failing because the previous process had not fully detached. An exponential back-off delay strategy is now applied between retries, providing sufficient time for prior connections to release cleanly and significantly improving reattach reliability. (dbz#2031)

Deferred transaction creation until first DML

A new deferred transaction start mode allows the connector to delay creating a transaction in the buffer until the first DML event occurs, while still preserving user_name and client_id metadata from the transaction START event. This reduces the number of tracked transactions by excluding "stub" transactions that contain only a START and eventual COMMIT or ROLLBACK with no DML, which are common in environments with frontend applications and SQL developer tools. (dbz#2046)

This mode also changes how the mining session window advances. Rather than pinning the lower watermark to the oldest in-flight transaction, the mining window slides forward block-by-block, which is similar to how the connector behaved prior to Debezium 3.2.

While this prevents long-running or idle transactions from holding the mining window open, it reintroduces the same trade-offs from that earlier behavior: because the mining boundaries are no longer anchored to the oldest transaction, there is a risk that parts of a transaction may not be fully re-mined if an event spans a window boundary.

Users should evaluate whether the reduced memory footprint and narrower mining window are appropriate for their workload before enabling this option.

Filtering of PRIVATE redo thread logs in RAC environments

In Oracle RAC deployments, when a node is shut down and its redo thread becomes PRIVATE, archive logs from that thread were still collected and fed to LogMiner. This could unnecessarily extend the SCN mining window and cause LogFileNotFoundException if archive log gaps existed on other threads. The connector now filters out logs belonging to threads not present in the current RedoThreadState, preventing PRIVATE and DISABLED thread logs from being collected. (dbz#2049)

Scenarios where a DBA reuses a redo thread that transitions from PUBLIC to PRIVATE are not supported. If Debezium has not fully consumed all changes from a thread before it is marked PRIVATE, those unconsumed changes will be skipped, which can lead to data loss.

Debezium Platform

Monitoring REST API in Conductor

A new monitoring REST API has been added to Conductor to serve pipeline metrics to the Stage UI. The API queries Prometheus for time-series data, transforms responses into a compact array format that reduces JSON payload size by approximately 53%, and implements efficient caching. Two endpoints are provided: one to list available monitoring panels and another to query panel data for specific pipelines, with support for configurable time ranges and step intervals. (dbz#1898)

Improved connection edit flow UX

The connection edit flow in the Stage UI has been updated to match the page styling and design patterns used in the source and destination creation flows, providing a more consistent and polished user experience when modifying existing connections. (dbz#1978)

Multi-panel monitoring dashboard

A new monitoring tab has been added to the pipeline overview with a grid layout for multiple metric panels. The dashboard uses React Query for shared caching across panels, supports global controls for time range and refresh rate selection, and renders visualizations with PatternFly charts. Partial failure handling ensures that if one panel fails, the others continue to display data, and refresh is automatically paused when the tab is inactive. (dbz#2025)

JDBC sink support

Debezium Platform now supports creating sink pipelines using the Debezium JDBC sink connector, enabling database migration and replication scenarios directly through the Platform UI. This allows users to configure end-to-end change data capture pipelines with a JDBC-based destination without leaving the Platform interface. (dbz#2079)

Debezium for Spanner

Spanner Omni compatibility

The Spanner connector is now compatible with Spanner Omni, extending Debezium’s change data capture capabilities to Spanner deployments running outside of Google Cloud. This enables users running Spanner Omni on other cloud providers or on-premises to leverage the same connector for streaming changes. (dbz#1858)

About Debezium

Debezium is an open source distributed platform that turns your existing databases into event streams, so applications can see and respond almost instantly to each committed row-level change in the databases. Debezium is built on top of Kafka and provides Kafka Connect compatible connectors that monitor specific database management systems. Debezium records the history of data changes in Kafka logs, so your application can be stopped and restarted at any time and can easily consume all of the events it missed while it was not running, ensuring that all events are processed correctly and completely. Debezium is open source under the Apache License, Version 2.0.
