Debezium 3.7 Release Summary Debezium 3.7 Release Summary
September 29, 2026 by Chris Cranford
releases mongodb mysql mariadb postgres sqlserver cassandra oracle db2 vitess outbox spanner jdbc informix ibmi cockroachdb yashandb ingres tidb milvus sqlite cli

As September draws to a close, we’re thrilled to announce the general availability of Debezium 3.7, the latest milestone in the Debezium 3.x series. This release brings together everything from the last three months of development, adding a wide range of new features, improvements, and bug fixes across the entire ecosystem.

Debezium 3.7 welcomes new incubating connectors for TiDB, Milvus, and SQLite, and the CockroachDB connector is no longer incubating. The Debezium CLI has its first official release, the Debezium Platform now supports alerting and can deploy pipelines to hosts outside of Kubernetes, and PyDebeziumAI brings real-time change data capture to LangChain and LangGraph applications.

Thanks to our amazing community of contributors, this is one of Debezium’s largest feature-packed releases. Read on for the full details of everything that shipped in Debezium 3.7!

Breaking changes

With any major release, there can be breaking changes. Let’s discuss the key changes you should be aware of before upgrading to Debezium 3.7.

Debezium for Oracle

Continuous mining removed for Oracle 12

Oracle deprecated continuous mining in Oracle 12c and permanently removed it in 19c, and Debezium previously only supported it on a best-effort basis for Oracle 12c deployments. This feature has now been removed entirely from the Oracle connector.

If you are currently using continuous mining with Oracle 12c, you will need to switch to a different capture mode before upgrading. The LogMiner adapter remains the recommended approach for Oracle change data capture. (dbz#1953)

Savepoint partial rollbacks handled correctly

The Oracle connector handles a rollback to a savepoint by walking back through the buffered events of the transaction and discarding the change that was undone. Two defects in this process could cause the target to drift out of sync with the source.

First, when LOB support is enabled, the connector consolidates related INSERT and UPDATE events for the same row, but this consolidation only carried the column values forward and left the merged INSERT with a placeholder row identifier. When the partial rollback arrived, the connector could not find the event to discard, logged a "Cannot undo" warning, and emitted the rolled-back change that looked like a normal change to the target.

Second, when a rollback-to-savepoint event was mined near the end of a LogMiner session for a transaction that had not yet committed, the same rollback could be applied a second time when the transaction’s events were re-read in the next mining session. Depending on the shape of the transaction, this produced either a spurious "Cannot apply undo change" warning or, more seriously, marked an earlier legitimate change such as the original INSERT as rolled back and silently dropped it from the change stream.

The connector now preserves the correct row identifier when an UPDATE is folded into an INSERT, and partial rollbacks are applied idempotently so that a rollback already processed is never re-applied in a later mining session. Together these ensure the connector emits exactly the changes that survived the rollback.

No configuration changes are required. After upgrading, changes that were rolled back to a savepoint no longer reach downstream consumers, changes that were previously dropped in this scenario are emitted correctly, and the associated warnings no longer appear in the connector log. Any downstream compensation put in place to filter the spurious events can be removed. (dbz#1422, dbz#1914)

Last enqueued event tracking moved to the transaction cache

The buffered LogMiner implementation now tracks the most recently enqueued event for each transaction directly in the transaction cache, rather than in a separate structure maintained alongside it. This consolidates transaction state in a single place, reducing duplicated bookkeeping in the streaming pipeline.

To support this, the XML begin and end events now carry the redo sequence number (SEQUENCE#), which the connector uses to detect the boundary between statements that contain XML updates when handling rollbacks. As a result, the serialized form of these events stored in the Ehcache and Infinispan transaction buffers has changed.

If you use the Ehcache or Infinispan buffer types and capture XMLTYPE columns, allow any in-flight transactions to complete and clear the transaction buffer caches before upgrading, as XML events persisted by an earlier version cannot be deserialized. Deployments using the default heap buffer are not affected. (dbz#2652)

Debezium JDBC sink

MySQL type preservation audit and fixes

Several MySQL data types that were previously silently corrupted or mishandled in MySQL-to-MySQL JDBC sink pipelines have been fixed. Users upgrading should verify their pipelines, as some behaviors that previously appeared to work (but produced wrong data) may now surface errors instead. Affected types include BIGINT UNSIGNED max values, BIT(>1) columns with Avro converters, ENUM/SET values containing commas or quotes, spatial coordinate ordering, and TIME values outside the standard clock range. (dbz#2102)

Debezium for Cassandra

Removal of Cassandra 3 connector

Cassandra 3 has reached end of life, and the Cassandra 3 connector has been removed from Debezium. As part of this change, the Guava dependency has been upgraded to version 32.0.0, which is incompatible with Cassandra 3 but aligns with the requirements of Cassandra 4 and later.

If you are currently using the Cassandra 3 connector, you will need to upgrade to Cassandra 4 or later before upgrading to Debezium 3.7. The Cassandra 4 and Cassandra 5 connectors remain fully supported. (dbz#2273)

Debezium Core

Schema history memory optimization

Deployments with many identically structured tables, such as multi-tenant databases where each tenant has its own schema, can now see significantly reduced memory consumption. Debezium now deduplicates schema history objects so that only one copy of each unique table, column, and attribute definition is retained in memory, rather than storing redundant copies for every structurally identical table. (dbz#1813)

Caching for reselected column values

The ReselectColumnsPostProcessor re-queries the source database to fill in large out-of-line columns, such as PostgreSQL TOAST columns or Oracle LOBs, that the database leaves out of change events when they haven’t changed. On tables where these columns rarely change but the rows are updated often, that can mean a lot of repeated queries for the same values.

The post processor can now cache reselected values, so when the same column value is needed across multiple events, it’s served from the cache instead of the source database. The cache invalidates an entry as soon as a real change to the value is detected, so correctness doesn’t depend on expiration alone. Caching is disabled by default and can be enabled with reselect.cache.enabled=true.

The cache is built on a standard contract that any storage backend can implement, and Debezium ships two implementations. One keeps a bounded cache on the JVM heap, while the RocksDB implementation stores values on disk, allowing much larger working sets to be cached and further reducing round trips to the source database. (dbz#2002, dbz#2435)

ExtendedTimestamp for high-precision timestamps beyond INT64 limits

Databases like PostgreSQL, Oracle, and SQL Server support timestamp ranges and precisions that can exceed what a single INT64 epoch value can represent, leading to silent overflow and data corruption for far-future dates or high-precision values.

A new io.debezium.time.ExtendedTimestamp semantic type addresses this by separating calendar range from sub-second precision, using a composite STRUCT with seconds and nanos fields. This approach follows the same design used by Java’s Instant and Google Protocol Buffers Timestamp, and eliminates the overflow risk that affected MicroTimestamp and NanoTimestamp at the boundaries of their representable ranges. (dbz#2119)

Embeddings SMT for the OpenAI API

Debezium’s AI embeddings transformations gain a new module for the OpenAI API. Built on the LangChain4j OpenAI integration, the transformation sends the configured text field of each change event to an embedding model through the OpenAI API and adds the resulting vector to the record.

Because the module targets the API rather than a specific provider, it works with OpenAI’s own embedding models and with any inference server that exposes an OpenAI-compatible API. For example, users can run an IBM Granite embedding model locally with an inference server such as llama.cpp and point the transformation at it. This lets users enrich their change events with embeddings directly in the pipeline, alongside the existing embedding providers, without any custom code. (dbz#1067)

Dedicated metric for snapshot read events

Snapshot events are emitted with the READ operation, which previously had no dedicated counter in Debezium’s event metrics. As a result, monitoring dashboards in the Debezium Platform or in Prometheus showed zero create, update, and delete events while a snapshot was actively processing rows, making snapshot throughput effectively invisible.

Debezium now exposes a TotalNumberOfReadEventsSeen metric through JMX, following the same pattern as the existing create, update, and delete counters. The OpenTelemetry JMX configuration generated by the Debezium Operator maps the new attribute as a read event type, and the Debezium Platform gains a snapshot event count rate panel built on it. Note that the counter covers both initial and incremental snapshot events. (dbz#2167)

Faster JMX LastEvent metric rendering improved snapshot throughput

The common pipeline metrics render a JSON summary of every dispatched change event to populate the JMX LastEvent attribute. Previously, each rendering constructed a brand new Jackson ObjectMapper, a cost paid for every snapshot and streaming event across all source connectors and both the Kafka Connect and Debezium Server runtimes.

The rendering now uses jackson-core’s stateless JsonStringEncoder, which is roughly seven times faster and allocates about five times less memory per event. In end-to-end snapshot benchmarks of a one million row table, this translated to up to 47% higher throughput on PostgreSQL and 38% on MySQL, with allocation per row roughly halved and noticeably fewer garbage collections and lower CPU usage. The rendered output is byte-identical to before and no new dependency is introduced. (dbz#2492)

Captured tables included in snapshot notifications

Debezium now emits a dedicated notification that lists the tables to be captured once an initial snapshot has resolved its data collections. The same information is also available for incremental snapshots. This gives monitoring tools and operators clear visibility into exactly which tables a snapshot is going to process, without having to infer it from connector configuration or logs. (dbz#2537)

HTTP notification channel

Debezium now provides an http notification channel that delivers connector notifications as JSON to an HTTP endpoint. This makes it straightforward to integrate snapshot progress and other notifications with webhooks, alerting systems, or custom services, without having to consume a Kafka topic or JMX.

To use it, add http to notification.enabled.channels and set the target URL with notification.http.url. Delivery supports configurable timeouts and retries, and the channel includes built-in protection against server-side request forgery (SSRF), with private network destinations only reachable when explicitly allowed via notification.http.allow.private.networks. (dbz#2538)

Debezium for Db2

Change table pruning support

Change tables captured by the DB2 Capture Agent can now be automatically pruned, preventing unbounded growth that previously required a separate Apply Agent to manage. After successfully producing change events, the connector signals the Capture Agent with the most recent processed position, allowing it to purge entries that are no longer needed. (dbz#1843)

LOB column serialization support

The Db2 connector now correctly serializes LOB columns (CLOB, BLOB, and DBCLOB) during both snapshot and streaming. Previously, CLOB and DBCLOB columns emitted internal driver handle strings during snapshots and null values during streaming, while BLOB columns always produced null values.

With this fix, text-based LOB columns are emitted as their string content, and binary LOB columns are serialized according to the configured binary.handling.mode (e.g., base64). (dbz#2304)

Debezium for MariaDB

Support for InnoDB-based binary logs

MariaDB 12.3 introduced a new InnoDB-based binary log storage format designed for improved throughput and crash recovery. The MariaDB connector and binary log client have been updated to ensure compatibility with this new format, allowing Debezium to capture changes from MariaDB deployments that use InnoDB-based binary logging. (dbz#2259)

Debezium for MongoDB

Date type keys in incremental snapshots

Incremental snapshots of MongoDB collections now support collections whose key is a BSON Date type. This continues the ongoing work to broaden the key types that can be used to chunk and resume MongoDB incremental snapshots, so collections keyed by dates no longer need a workaround to be captured incrementally. (dbz#765)

Read preference honored after replica set promotion

The connector now continues to respect the configured read preference when a replica set member it is streaming from changes role. Previously, when a secondary serving the change stream was promoted to primary, the connector kept streaming from that node, placing unwanted load on the primary.

The connector now monitors the replica set topology, and when a promotion invalidates the read preference, it closes the change stream cursor, reopens it against a node matching the read preference, and resumes from the last resume token. This completes the remaining work for reading changes from MongoDB secondaries and helps keep streaming load off the primary. (dbz#917)

New SMT for relational-style MongoDB events

Unlike relational connectors, which emit before and after states as nested Struct values, MongoDB change events carry these states as JSON strings. The new io.debezium.connector.mongodb.transforms.MongoToRelationalMapper transformation converts them into Kafka Connect Struct values while preserving the rest of the change event envelope, record key, headers, and operation. This lets MongoDB events flow through the same pipelines as relational events, including transformations such as ExtractChangedRecordState and the Debezium JDBC sink.

Users can define a fixed projection per collection using schema.mapping.<database>.<collection>, selecting document paths, naming output fields, and assigning Connect types. This produces a stable, pre-defined schema even when fields are missing from individual documents or change shape, which is especially valuable when writing MongoDB data into relational targets. When no projection is configured, the transformation infers a schema from each event’s document images. (dbz#1715)

Lossless handling mode for BSON Timestamp values

The ExtractNewDocumentState transformation previously converted a BSON Timestamp into a Kafka Connect Timestamp using only its time component, silently discarding the increment. As a result, distinct values such as Timestamp(1710000000, 7) and Timestamp(1710000000, 8) became indistinguishable after transformation.

A new bson.timestamp.handling.mode option addresses this. The default, connect, retains the existing behavior for compatibility, while struct emits both the time and increment components so consumers can faithfully reconstruct the original BSON value. (dbz#2570)

Debezium for MySQL

CREATE TABLE …​ LIKE syntax support

The MySQL connector now correctly handles CREATE TABLE …​ LIKE DDL statements, which create a new table using the structure of an existing table. Previously, this common MySQL pattern could cause schema tracking issues, potentially leading to missed or incorrectly shaped change events for the newly created table. (dbz#248)

Correct boolean conversion for negative TINYINT(1) values

The TinyIntOneToBooleanConverter now correctly treats negative TINYINT(1) values as true, matching MySQL’s own semantics where any non-zero value is considered true. This applies to both the MySQL and MariaDB connectors. Previously, negative values such as -1 or -128 were incorrectly converted to false because the converter used a greater-than-zero check instead of a not-equal-to-zero check. (dbz#2260)

Support for NOBLOB binlog_row_image format

Debezium now supports the NOBLOB binlog row image format for MySQL. This format is commonly used in databases with large BLOB columns that are updated infrequently, as it reduces binlog size by excluding BLOB and TEXT columns from row images when they are not modified. Previously, the connector rejected this format at startup, forcing users to choose between FULL and MINIMAL row image modes.

This behavior is conceptually similar to how PostgreSQL handles unchanged TOAST columns and how Oracle handles LOB values. In all three cases, the database’s replication stream may omit large-value columns that were not modified in a given transaction. During snapshots, all column values are always available because Debezium reads the full row directly via SQL. During streaming, however, when a BLOB or TEXT column was not changed and is therefore excluded from the binlog row image, Debezium populates the field with the configured unavailable.value.placeholder value. This is the same approach used for unavailable TOASTed columns in PostgreSQL and LOB columns in Oracle, giving users a consistent way to detect and handle missing column values across all three databases. (dbz#473)

Accurate binlog positions beyond 4GB

The log_pos field in a MySQL binlog event header is an unsigned 32-bit value, yet a binlog file can legitimately grow beyond 4GB because MySQL never splits a transaction across files. Once a file crosses that boundary the server truncates the position it writes into the header, and the binlog client previously trusted that wrapped value. Every position the connector exposed past 4GB was therefore wrong, even though streaming itself continued: committed offsets, the source.pos field of emitted events, the reconnect position, and the BinlogPosition metric. On servers without GTIDs, a restart from a wrapped offset could land in the middle of an unrelated event and fail with the misleading "log event entry exceeded max_allowed_packet" error.

The binlog client now tracks the real 64-bit position itself, anchored on the 8-byte position carried by the ROTATE event and advanced by the length of each event read from the stream. Behavior for positions below 4GB is unchanged. Above it, offsets and source.pos now report the real position, consistent with what SHOW BINARY LOGS and mysqlbinlog report, and positions compare in the correct order. This change is complemented by the fix for the schema history comparator in dbz#2506.

One limitation remains: the binlog dump protocol itself only carries a 32-bit start position, so restarting from a position beyond 4GB on a server without GTIDs is still not possible. Tracking the real position removes the silent corruption and lays the groundwork for handling that case explicitly. (dbz#2508)

Debezium for Oracle

ROWID surrogate key sorting by primary key

Incremental snapshots using the ROWID pseudocolumn as a surrogate key can now execute significantly faster. Previously, the snapshot query sorted by ROWID, which can be very expensive on large tables. The connector now uses the table’s primary key for ordering while still projecting ROWID as the surrogate key, avoiding the costly sort without changing the snapshot behavior. (dbz#1726)

Downstream mining support for XStream

The Oracle connector can now capture changes from a downstream mining database when using the XStream adapter. A downstream mining database receives the primary’s transaction logs and replays them on a separate host, so all change data capture mining work can move off the production database. This avoids placing mining load on the primary and lets DBAs tune the downstream environment independently.

In this mode, snapshots and metadata queries are sent to the primary database, while the XStream outbound server runs against the downstream system. To enable it, set capture.mode to downstream and point the secondary.* connection properties at the downstream database. The downstream database must be configured as a STANDBY SNAPSHOT with transaction logs registered automatically through Oracle RFS. Downstream mining isn’t available for the LogMiner adapter. LogMiner users can offload mining to a physical standby with capture.mode set to physical_standby instead. (dbz#1868)

Non-blocking OpenLogReplicator client

The OpenLogReplicator client has been converted from a blocking to a non-blocking architecture. This improves the responsiveness of connector shutdown operations, as the client can now promptly exit its read loop when a stop is requested rather than waiting for the socket read timeout to expire. (dbz#1198)

Snapshot-only mode no longer requires archive log configuration

The Oracle connector no longer validates archive log destination configuration when running in snapshot-only mode (initial_only). Previously, the archive log validation ran unconditionally at startup, causing snapshot-only runs to fail on managed deployments like Oracle Autonomous Database where the archive log configuration is hidden from the connector user.

This change makes snapshot-only deployments simpler, particularly in cloud-managed Oracle environments where archive log destinations are controlled by the service provider. (dbz#2305)

Support for BC (negative) timestamps

The Oracle connector now correctly captures dates in the BC era (negative years) across all four Oracle temporal types: DATE, TIMESTAMP, TIMESTAMP WITH TIME ZONE, and TIMESTAMP WITH LOCAL TIME ZONE. Previously, a date such as -2018-03-27 inserted via TO_DATE('-2018-03-27', 'SYYYY-MM-DD') would be incorrectly represented as the positive-year equivalent 2018-03-27.

Because Oracle’s calendar has no year zero while ISO 8601 does, BC years are offset by one: Oracle year 2018 BC becomes ISO year -2017. How BC values appear in change events depends on the time.precision.mode setting. Epoch-based types such as io.debezium.time.Timestamp and io.debezium.time.MicroTimestamp emit negative epoch values, while string-based types such as io.debezium.time.ZonedTimestamp emit ISO 8601 strings with a negative year (e.g., "-2017-03-27T01:34:56.007890-11:00").

Both snapshot and streaming paths are covered, and no new connector configuration properties are required. (dbz#1286)

BC values stored in TIMESTAMP(7-9) columns exceed the representable range of io.debezium.time.NanoTimestamp, so users with BC data at nanosecond precision should use time.precision.mode set as isostring or structured only.

LogMiner DML parser performance improvements

The LogMiner DML parser has been significantly optimized, delivering 1.7x to 2.6x higher throughput for UPDATE statement parsing across a range of table widths and column sizes. For tables with wide VARCHAR2 columns or extended 32K strings, the improvements are even more dramatic.

Users who enable the extended MAX_STRING_SIZE parameter may encounter a LogMiner bug where apostrophes in text column values are not properly escaped. Debezium’s relaxed quote detection mode addresses this Oracle limitation, but previously suffered from O(n^2) performance loss for such columns, compounded by text length. This release improves that mode by up to 94x in worst-case scenarios.

These improvements directly translate to higher event throughput for Oracle connectors processing tables with many columns or large column values. (dbz#2491)

The JMH Benchmarks for these changes can be found here.

Total abandoned transaction count metric

The Oracle LogMiner JMX metrics now include a TotalAbandonedTransactionCount metric that increments every time a transaction is abandoned. The existing metrics expose abandoned transactions as an array of transaction identifiers, which is impractical to scrape and chart in tools such as Prometheus and Grafana. The new counter makes it easy to monitor and alert on abandoned transactions over time. (dbz#2428)

Richer in-flight transaction logging

When the buffered LogMiner implementation logs transactions that have not yet committed or rolled back, it now includes additional metadata about each transaction, such as its creation time and the number of buffered events, rather than only the transaction identifier and SCN. This gives administrators the details they need to make an informed decision about dropping a long-running transaction without having to run manual LogMiner queries.

When deferred transactions are in use, the state of the deferred transactions is also logged as a separate entry, using the same format. (dbz#2576)

Signal to log pending transactions

A new signal lets you dump the connector’s current view of active and deferred transactions to the connector logs on demand. Previously, obtaining this information required additional logging that may not have been enabled at the time, or direct access to query LogMiner.

For each transaction, the output includes the transaction identifier, starting SCN, change time, username, client identifier, redo thread, and, for active transactions, the number of buffered events. Entries are sorted from oldest to newest, making it easy to identify which transactions are holding back the mining window and to pair the output with the existing drop-transaction signal. (dbz#2577)

ORA-02002 treated as a retriable error

The connector now treats ORA-02002 as a retriable error. During a switchover or failover with multiple archive destinations configured, Oracle can raise ORA-02002: error while writing to audit trail, which previously caused the connector to stop unexpectedly. The connector now retries in this scenario, allowing it to recover automatically once the failover completes. (dbz#2625)

Improved parsing of partition-conversion DDL

The Oracle DDL parser now recognizes ALTER TABLE …​ MODIFY statements that convert a non-partitioned table into a partitioned table as a distinct operation, aligning the grammar with Oracle’s documented ALTER TABLE partition operations. This improves the reliability of DDL parsing for these statements and avoids side effects caused by the grammar previously conflating them with other partition modifications. (dbz#2408)

Debezium for PostgreSQL

First-class geometric type mapping

Tables containing PostgreSQL geometric columns (box, circle, line, lseg, path, polygon) now produce usable, structured change events instead of opaque binary data. Previously, these types had no explicit mapping, so their values were either dropped entirely or emitted as raw bytes that downstream consumers couldn’t interpret.

The types box, lseg, path, and polygon are mapped to the existing Geometry Struct using WKB encoding, with an extension field that preserves the original PostgreSQL type. The circle and line types receive new dedicated Struct schemas (io.debezium.data.geometry.Circle and io.debezium.data.geometry.Line) because they have no faithful Well-Known Binary representation. (dbz#2135)

Incremental snapshots on read-only replicas

Incremental snapshots on PostgreSQL read-only replicas previously failed with cannot execute pg_current_xact_id() during recovery error, because the snapshot logic attempted to create a new transaction ID, which is not permitted on replicas. This caused connectors running with read.only=true to enter an infinite restart loop when an incremental snapshot was triggered.

This has been corrected, and users running against a hot standby can now use incremental snapshots for re-snapshotting subsets of data without restarting the connector or switching to the primary. (dbz#1080, dbz#2431)

Faster snapshots with per-column type caching

The PostgreSQL connector now caches the resolved column type per ResultSet during snapshots, rather than resolving it on every row. Previously, each row paid the cost of calling ResultSetMetaData.getColumnTypeName and TypeRegistry.get once per column, making overhead scale based on number of columns and rows. For a table with 82 columns, this kept the snapshot producer pinned at around 25K rows per second.

With caching in place, the rowToArray stage runs approximately 35% faster, and end-to-end snapshot throughput for the same table increased to over 30K rows per second. The gain scales with column count and benefits all snapshot flavors, including initial, blocking, incremental, and read-only incremental. (dbz#2350)

TimescaleDB 2.29 compatibility

TimescaleDB 2.29 removed the schema and table name columns from its internal chunk catalog, which caused the TimescaleDB transformation to fail while streaming with a Failed to read TimescaleDB metadata error. The transformation now works with TimescaleDB 2.29, so users can upgrade their Timescale deployments without breaking their change data capture pipelines. (dbz#2335)

Debezium for SQL Server

Support for specifying capture instance

The SQL Server connector now allows users to specify which CDC capture instance to use when multiple capture instances exist for the same table. This is useful when different capture instances track different column subsets, preventing unwanted schema changes in downstream topics when a new capture instance is created. (dbz#960)

Debezium JDBC sink

Starrocks catalog name support

Users connecting to a Starrocks target through the MySQL driver can now specify the desired catalog name with a new dialect.starrocks.catalog_name option. Previously, the driver defaulted to a schema that did not match the intended catalog, with no way to override it. (dbz#979)

JMX metrics support

The JDBC sink connector now exposes JMX metrics, giving users visibility into what is actually happening at the target database. These complement the standard Kafka Connect sink task metrics by describing operations beyond the connector’s put() boundary. (dbz#1174)

Metric Name Description

TotalNumberOfWrites

Total number of processed events (insert/update/upsert) applied to the target database.

TotalNumberOfDeletes

Total number of delete operations applied to the target database.

TotalNumberOfTruncates

Total number of truncate operations applied to the target database.

TotalNumberOfFilteredEvents

Number of records skipped without being applied, such as unresolvable tables, disabled deletes/truncates, or schema-change events.

TotalNumberOfTablesCreated

Total number of tables the sink created in the target database when schema evolution is enabled.

TotalNumberOfTablesAltered

Total number of tables the sink altered in the target database when schema evolution is enabled.

CockroachDB dialect support

CockroachDB users can now use Hibernate’s native CockroachDialect with the JDBC sink without losing upsert support. Previously, the sink did not recognize this dialect and fell back to a generic mode that could not generate INSERT …​ ON CONFLICT …​ DO UPDATE statements, forcing users to manually override with PostgreSQLDialect as a workaround. A dedicated CockroachDB dialect provider now handles this automatically. (dbz#1639)

SingleStore database support

The JDBC sink connector can now write directly to SingleStore, a distributed SQL database that is compatible with the MySQL wire protocol but has its own SQL syntax and type-handling differences. A dedicated dialect ensures correct DML operations without requiring manual configuration workarounds. Geospatial type support is planned for a future release. (dbz#2146)

Startup validation with validate-only schema evolution mode

A new schema.evolution=validate-only mode catches missing target tables at startup rather than waiting for the first record to arrive. For low-traffic topics, this can mean the difference between discovering a configuration problem in seconds versus hours.

This mode is designed for deployments where target tables are managed externally (e.g., by a DDL pipeline) and the connector should only perform DML. It validates statically resolvable table names using the default collection naming strategy; configurations that rely on ${source.*} placeholders in the collection name format or custom naming strategies are not eligible for startup validation. When topics.regex is used, validation is deferred until topic assignment. (dbz#2179)

Dead letter queue support

The JDBC sink connector can now route records that fail to write to a dead letter queue, rather than stopping the task. Previously, a single bad record, such as one that violates a constraint, would stop the sink task until someone restarted it manually.

When a batch fails with a non-transient error, the connector retries the records one at a time to isolate the ones that fail, sends only those to the dead letter queue, and carries on with the rest. Transient failures, such as lost database connections, are never sent to the dead letter queue and are still retried based on flush.max.retries and flush.retry.delay.ms. A new TotalNumberOfErrantRecords metric reports how many records have been routed to the dead letter queue.

This feature is available when the shared change event sink framework is enabled with internal.enable.sces=true, which is disabled by default. The shared change event sink framework is incubating, so this option and its behavior may change in future releases. With that in place, it uses the standard Kafka Connect error handling options, errors.tolerance=all and errors.deadletterqueue.topic.name. Because the connector provides at-least-once delivery, we recommend the upsert insert mode when using a dead letter queue, so that records redelivered after a restart aren’t routed there as constraint violations. (dbz#984)

Sink support for PostgreSQL enum columns

The JDBC sink connector now correctly handles writing to PostgreSQL enum columns. Previously, sinking to a PostgreSQL enum column would fail with a type mismatch error because the generated SQL did not include the necessary type cast. The connector now detects enum column types via the propagated source type metadata and applies the appropriate PostgreSQL cast. (dbz#1344)

Record value and header primary key modes now support deletion

The JDBC sink connector now supports row deletion when using record_value or record_header primary key modes. Previously, deletion was only supported with record_key mode. This provides more flexibility for pipelines where the primary key is derived from the record value or headers rather than the Kafka record key. (dbz#1421)

Opt-in timestamp clamping for out-of-range values

Every database supports a different timestamp range, and Oracle’s BC-era values often fall outside what other databases can represent. The JDBC sink connector introduces timestamp.clamp.out.of.range.values, an opt-in setting that clamps incoming timestamps to the target dialect’s minimum or maximum rather than failing the sink operation. (dbz#1008)

SingleStore ARRAY to JSON mapping

The JDBC sink connector can now write Kafka Connect ARRAY schema values into SingleStore JSON columns. Array values arriving from Kafka topics are serialized to JSON on the way into the target column, so users no longer need a custom transformation or additional pre-processing to sink array fields into SingleStore. (dbz#2567)

User-friendly names and descriptions for Debezium Server sink connectors

MongoDB signal data collection verification

The conductor’s signal verification endpoint, used by the debezium source verify-signals CLI command, lets users confirm that a signal data collection is correctly set up for a source connection. For MongoDB connections this check was previously a stub that always reported success, so a misconfigured or non-existent signal collection went unnoticed.

The verification is now fully implemented for MongoDB sources, checking that the signal collection actually exists in the configured namespace. This brings MongoDB in line with the behavior already available for relational connections and makes the verification results trustworthy across all supported sources. (dbz#2270)

Alerting support

The Debezium Platform has offered pipeline monitoring through a set of predefined panels, but monitoring was passive: users had to watch dashboards to notice problems. Alerting closes this gap by letting users define threshold-based rules against existing monitoring panels and receive notifications when those thresholds are breached.

Alert rules are built by selecting a monitoring panel, a comparison operator, a numeric threshold, and an evaluation window that suppresses transient spikes. The evaluation window can be one of the predefined durations or a custom value between 1 and 60 minutes. Rules are evaluated globally across all pipelines, and each alert identifies which pipeline triggered it. Alerts follow a pending, firing, and resolved lifecycle with incident tracking, and support critical, warning, and info severity levels. They’re always visible in the Platform UI and can also be delivered by email over SMTP or through an HTTP webhook. A queryable, filterable alert history with configurable retention rounds out the feature.

The UI gains a new Alerts section with Rules, Channels, and History pages, plus a global alert badge in the header. Alert grouping, silencing, escalation policies, and repeat notifications are out of scope for this initial implementation. (dbz#2314, dbz#2450, dbz#2563)

Debezium Server

Smarter sink-to-storage property remapping

When the sink and storage backends use the same technology (e.g., Redis) but with different endpoints, Debezium Server could previously overwrite explicitly configured storage properties with sink properties, leading to subtle misconfiguration.

The automatic sink-to-storage property remapping now respects explicit storage configuration; if schema.history.internal or offset.storage sub-properties are already set, the remapping is skipped. The original convenience behavior, where sink properties are shared with storage when no explicit storage configuration exists, continues to work as before. (dbz#2078)

Native distribution module for Debezium Server

Debezium Server can now be built as a native executable, enabling faster startup times and lower memory footprint compared to the traditional JVM distribution. A new debezium-server-native-dist module provides the build configuration and packaging needed for native compilation. (dbz#2108)

Debezium Server now delegates all JDBC consumer operations to the JDBC sink connector, minimizing future maintenance and inheriting all future improvements to the sink connector out of the box. (dbz#2265)

Readiness probe for health checks

Debezium Server now includes a proper readiness health check that reflects whether the connector is actually ready to process changes. Previously, the /q/health/ready endpoint always returned UP as soon as the Quarkus application started, regardless of the connector’s actual state.

The new readiness probe checks the engine’s polling status, giving orchestration tools like Kubernetes an accurate signal for routing traffic. (dbz#2393)

IRSA and WebIdentityToken support for the Kinesis sink

The Kinesis sink now supports AWS IRSA (IAM Roles for Service Accounts) and WebIdentityToken-based authentication. This is especially important for Kubernetes-based deployments on Amazon EKS, where IRSA is the recommended approach for granting AWS permissions to pods without embedding static credentials. (dbz#1738, dbz#2386)

Databricks ZeroBus Ingest sink adapter

Debezium Server now includes a sink adapter for Databricks ZeroBus Ingest, enabling direct change event delivery to Unity Catalog-managed Delta tables without requiring an intermediate message broker. ZeroBus Ingest is Databricks' serverless ingestion API, generally available on AWS and Azure, which writes records directly into managed Delta tables. With this integration, Debezium Server users can set up a streamlined source database to Delta pipeline for change data capture into the Databricks lakehouse.

The sink commits source offsets only after ZeroBus durably writes and acknowledges each batch, providing at-least-once delivery semantics with deterministic idempotency keys. (dbz#2279, dbz#2378)

Correct Prometheus metric labels for sink connectors

The Prometheus JMX Exporter configuration shipped with Debezium Server now correctly labels sink connector metrics. Previously, sink connectors registered their MXBeans with a key ordering that did not match any existing rule pattern. This caused the task key to be embedded inside the name label (e.g., name="jdbc-sink, task=0" instead of name="jdbc-sink" with a separate task="0" label). This broke Prometheus queries, alerts, and dashboards that group or filter by connector name or task ID. (dbz#2380)

Connector profiles for the server distribution

The debezium-server-dist module now includes connector profiles (e.g., connector-postgres, connector-mysql) following the same pattern already present in debezium-server-native-dist. This enables trimmed distribution builds using profile combinations that produce a zip/tar.gz containing only the required connector and sink dependencies.

These profiles are the foundation for minimal, connector-specific Debezium Server distributions, such as those assembled by the Debezium CLI. (dbz#2421, dbz#2433)

Connection validator for RocketMQ

The Debezium Platform can now verify connections to Apache RocketMQ before a pipeline is deployed. A dedicated connection validator, connection type, and schema have been added for RocketMQ, so users get immediate feedback on misconfigured hosts or credentials rather than discovering the problem when the pipeline starts. (dbz#1094)

TLS and mTLS support for the RabbitMQ Stream sink

The RabbitMQ Stream sink previously had no way to configure TLS, so connecting to a TLS-enabled stream port failed with a closed connection as the client sent plaintext to the encrypted endpoint.

The rabbitmqstream sink now supports TLS and mutual TLS, with configurable trust and client certificate material and hostname verification, bringing it to parity with the TLS support already available in the AMQP-based RabbitMQ sink. This allows Debezium Server to publish to RabbitMQ Stream clusters that enforce encrypted, certificate-authenticated connections, a common requirement in Kubernetes deployments. (dbz#1582)

Kafka sink respects SMT-selected partitions

The Debezium Server Kafka sink now sends each record to the partition chosen by a single message transformation, such as PartitionRouting. Previously, the sink ignored the partition selected by the SMT and let the Kafka producer choose a partition based on the record key, so records that should have been co-located were spread across all partitions.

This brings the Kafka sink in line with Kafka Connect and the other Debezium Server sinks. Configurations that don’t set a partition through an SMT are unaffected. (dbz#2691)

First official release of the Debezium CLI

Configurable changefeed strategy

Users can now choose how changefeeds are created with a new cockroachdb.changefeed.strategy option. The single strategy (default) creates one multi-table changefeed, which CockroachDB recommends for clusters with many tables. The per-table strategy creates a separate changefeed per table, providing better parallelism, fault isolation, and the ability to tune settings like resolved intervals independently for each table. (dbz#1636)

Sinkless changefeed support

The CockroachDB connector can now stream change events directly over the SQL connection using sinkless (core) changefeeds, eliminating the need for an intermediate Kafka cluster. Previously, the connector required CockroachDB to push changes to a separate Kafka cluster first, which meant managing a second Kafka client and its associated configuration.

With sinkless changefeeds, the connector produces directly to the output topics like other Debezium connectors, inheriting the worker’s existing Kafka configuration automatically. (dbz#2024)

Documentation and warnings for static capture sets

The CockroachDB connector now documents that table.include.list patterns are resolved once at startup, meaning tables created after the connector starts are not automatically captured. Additionally, an execute-snapshot signal targeting a table outside the running capture set now produces a clear warning instead of silently succeeding without emitting any rows. This aligns the CockroachDB connector’s behavior with all other Debezium connectors. (dbz#2392)

The CockroachDB connector now emits schema and table fields in the source info block of change events, matching the behavior of the PostgreSQL and SQL Server connectors. The CockroachDB connector now supports an opt-in setting to asynchronously commit processed positions to the Kafka consumer group. Debezium for Milvus

The Milvus connector is still incubating, so its configuration and behavior may change in future.

Milvus source connector

Milvus is an open-source vector database built for storing, indexing, and searching high-dimensional embeddings at scale, and it sits at the heart of many retrieval-augmented generation and semantic search systems. Debezium has supported Milvus as a sink for some time, and this release adds the other direction: a new source connector that captures inserts, updates, and deletes from Milvus collections in real time.

Milvus does not expose a change stream through its API, so the connector reads directly from the internal message queue channels that Milvus publishes every write to, resolving collection schemas through the Milvus metadata API and using etcd checkpoints and timestamp-oracle ordering to provide resumable, correctly ordered events. Change events carry full schema fidelity, including vector field dimensions, so downstream consumers can replicate embeddings to other stores, keep search indexes in sync, or feed AI pipelines. The connector supports an initial snapshot of existing collections with a seamless hand-off to streaming, heartbeats, notifications, and metrics.

The connector is compatible with the transaction log architecture of Milvus 2.5, deployed with Kafka as the message queue backend. Milvus 2.6 uses a different architecture that the source connector does not support. (dbz#2065)

Debezium for SQLite

SQLite source connector

SQLite is the most widely deployed database engine in the world, embedded in browsers, mobile and desktop applications, and a growing number of edge and IoT devices, and increasingly used as a primary application database. Until now it has been one of the most common sources of data with no standard way to stream its changes, and this release closes that gap with a new Debezium source connector for SQLite.

Debezium AI for Python

PyDebeziumAI for real-time RAG with LangChain and LangGraph

PyDebeziumAI is a new Python library, introduced during the 3.7 release cycle, that integrates directly with Debezium to keep vector stores in sync with your relational database in real time.   • MySQL connector crashed with "Connection reset by peer" on TLS 1.3 due to an unhandled KeyUpdate (dbz#2213)

  • MySQL stream-only start (no snapshot) permanently failed on restart against a server with a non-empty gtid_purged (dbz#2227)

  • MySQL connector could get stuck in a permanent keepalive reconnect loop when the GTID auto-position seek exceeded connect.keep.alive.interval.ms (dbz#2266)

  • CockroachDB connector deduplication dropped events for different rows sharing a timestamp (dbz#2283)

  • PostgreSQL parallel snapshot connections were not pinned to the exported snapshot, giving inconsistent reads (dbz#2330)

  • Incremental snapshot silently lost data for NUMERIC keys holding NaN or Infinity (dbz#2333)

  • MySQL connector silently lost rows after a keepalive reconnect under backpressure (dbz#2359)

  • Cassandra connector silently dropped cdc=true change events bundled with cdc=false tables in the same mutation (dbz#2388)

  • JDBC sink failed against PostgreSQL targets whose primary key is GENERATED ALWAYS AS IDENTITY (dbz#2459)

  • Oracle ambiguous partial rollbacks left a stale deferred transaction that pinned the offset SCN (dbz#2531)

  • Oracle standby connector silently skipped events after DDL changes (dbz#2598)

  • MySQL and MariaDB error handlers treated every error as non-retriable (dbz#2611)

  • Parallel chunked snapshot failed with an arithmetic overflow on SQL Server tables with more than 2.14 billion rows (dbz#2670)

  • Connection string masking failed to mask the username in MongoDB connection strings (dbz#2719)

About Debezium

Debezium is an open source distributed platform that turns your existing databases into event streams, so applications can see and respond almost instantly to each committed row-level change in the databases. Debezium is built on top of Kafka and provides Kafka Connect compatible connectors that monitor specific database management systems. Debezium records the history of data changes in Kafka logs, so your application can be stopped and restarted at any time and can easily consume all of the events it missed while it was not running, ensuring that all events are processed correctly and completely. Debezium is open source under the Apache License, Version 2.0.
