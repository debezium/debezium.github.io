Supersonic Subatomic Debezium Server: Native builds with Quarkus and Mandrel Supersonic Subatomic Debezium Server: Native builds with Quarkus and Mandrel
September 17, 2026 by Giovanni Panice
debezium-server quarkus graalvm mandrel cdc migration

The Debezium 3.7.0.Beta2 release comes with a lot of changes, one of which is a complete rewrite of Debezium Server to support native builds with Quarkus and Mandrel. In this article, we’ll walk through creating a native distribution of Debezium Server and follow the steps from a previous article as an example.

Introduction

When we talk about native builds for Java Applications, we mean GraalVM, a high-performance runtime and toolchain for Java that was released by Oracle Labs in 2018. It extends the traditional Java platform with advanced compilation technologies, like ahead-of-time (AOT) compilation, enabling applications to be compiled into standalone executables with fast startup times and reduced memory consumption.

Building on these capabilities, Red Hat released the first version of Quarkus in 2019 Quarkus, designed to maximize build-time optimizations and minimize runtime overhead, making it one of the leading Java frameworks for native execution. By integrating closely with GraalVM Native Image, Quarkus lets applications achieve significant performance improvements over traditional JVM deployments.

To further support the Quarkus ecosystem, Red Hat introduced Mandrel in 2020, a downstream distribution of GraalVM focused specifically on native image generation for Quarkus applications.

The native distribution of Debezium Server leverages this ecosystem, combining Quarkus and Mandrel to deliver a lightweight, self-contained executable.

Gold for the Price of Silver: JIT Compilation in the Data Streaming Context

As mentioned before, AOT compilation is an approach in which machine code is generated before an application is executed, rather than during runtime. While AOT has long been used across many software ecosystems, it became a practical and widely adopted option for Java applications with the introduction of GraalVM Native Image.

By contrast, Just-In-Time (JIT) compilation has been a core part of Java’s execution model since the late 1990s. Sun introduced its first JIT compiler for Java in 1996, and the HotSpot JVM, released in 1999, further popularized adaptive runtime optimization by compiling frequently executed code paths into highly optimized machine code.

With JIT, Java applications start by running bytecode and gradually optimize themselves based on actual runtime behavior. This dynamic profiling enables excellent peak performance and throughput, making JIT the preferred choice for long-running services.

The trade-off between JIT and AOT depends on the target use case: JIT generally delivers higher maximum throughput for applications that run continuously and can benefit from runtime profiling and optimization. AOT, on the other hand, prioritizes operational efficiency, fast startup, and lower memory footprint at the cost of some runtime optimization opportunities.

Data streaming has traditionally been JIT territory: the JIT analyzes how code behaves during streaming and optimizes frequently executed methods, often called hot spots. Unlike AOT, the JIT can leverage runtime profiling to perform adaptive optimizations such as profile-guided inlining, speculative devirtualization, branch prediction tuning, and dynamic recompilation of hot code paths. These optimizations are continuously refined while the application is running, enabling the JVM to generate machine code tailored to real workload characteristics: the product of a well-established engineering effort spanning three decades.

The real price is the weight

The JVM runtime infrastructure and JIT compilation have a memory cost: a traditional HotSpot deployment requires memory not only for application data, but also for the JVM itself, including class metadata, dynamic class loading mechanisms, garbage collection metadata, profiling information, the JIT compiler, and the code cache that stores dynamically generated machine code. These components enable adaptive optimizations and high peak throughput, but they increase the overall memory footprint. Native executables generated with GraalVM Native Image or Mandrel remove much of this overhead by performing analysis and compilation at build time.

In this new era of rapidly increasing cloud costs driven by AI, optimizing memory consumption has become more important than ever.

The Hidden Gold of a Lost Age: Batch Ingestion

In some business scenarios, deploying a full ingestion and streaming platform capable of managing trillions of events in milliseconds is unnecessary. Sometimes the business simply needs to move data on an hourly or daily schedule from one source to another, without dealing with infrastructure complexity and costs. Debezium 3.6 introduced start/stop APIs for deterministic engine shutdown, which, combined with native builds, enable CDC pipelines for serverless environments. In this scenario, the native executable’s fast startup makes batch ingestion cost-effective in cloud environments.

A large ecosystem: why Quarkus

Currently, the Debezium community supports about 15 connectors for different data sources and 20 Debezium Server sinks. In addition, we maintain CDC-ready containers for testing, the Debezium Server operator, the Debezium Platform, and many other components that make our community vibrant and busy. Introducing native builds requires additional effort: Debezium’s own libraries and their dependencies must be compatible with native compilation — for example, classes accessed via reflection need to be registered with the compiler. Quarkus and its community maintain a large number of native-ready Java libraries, which makes adopting this layer significantly easier for our project.

Supported Connectors & Sinks

The following Debezium Connectors are supported for the native build in Debezium Server:

  • Postgres

  • MySQL

  • MariaDB

  • SQLServer

  • Oracle

  • MongoDB

and the following Debezium Server sinks:

  • Redis

  • HTTP

  • JDBC (not yet supported in native mode)

Please keep in mind that Debezium Server supports many other connectors and sinks in JVM mode.

Run Debezium Server

Following the example from the previous article, we can use Debezium Server to create a data integration pipeline from Postgres to Redis.

The example shown in this article is available in the debezium-examples repository.

We can start the source and target databases with the following Docker Compose file:

infrastructure-compose.yaml
services:

  postgres:
    container_name: postgres
    image: quay.io/debezium/example-postgres:3.6
    ports:
      - "5432:5432"
    environment:
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=postgres
    networks:
      - backend

  redis:
    container_name: redis
    image: mirror.gcr.io/redis:7.0
    ports:
      - 6379:6379
    environment:
      - ALLOW_EMPTY_PASSWORD=yes
    networks:
      - backend

networks:
  backend:
    name: debezium-native-backend

Run the Docker Compose command below:

docker compose -f infrastructure-compose.yaml up -d

Once the source and target destination are healthy, you can start replicating your data with the following command:

 docker run --name inventory-pipeline -d \
    -v $(pwd)/application.properties:/debezium/config/application.properties:z \
    -p 8080:8080 \
    --network debezium-native-backend \
    quay.io/debezium/server-native:nightly

The configuration used is the following:

application.properties
# Debezium CDC configuration
debezium.source.offset.storage=org.apache.kafka.connect.storage.MemoryOffsetBackingStore
debezium.source.connector.class=io.debezium.connector.postgresql.PostgresConnector
debezium.source.name=debezium
debezium.source.topic.prefix=migration
debezium.source.plugin.name=pgoutput
debezium.source.snapshot.mode=initial

# datasource configuration
debezium.source.offset.flush.interval.ms=0
debezium.source.database.hostname=postgres
debezium.source.database.port=5432
debezium.source.database.user=postgres
debezium.source.database.password=postgres
debezium.source.database.dbname=postgres
debezium.source.schema.include.list=inventory

# sink
debezium.sink.type=redis
debezium.sink.redis.address=redis:6379
debezium.sink.redis.cluster.enabled=false

quarkus.log.console.json=false

Similar to the previous article, you should see data flowing from Postgres to Redis. You can check the data has been correctly migrated to Redis:

docker exec -it redis redis-cli KEYS '*'

To inspect the replicated stream entries:

docker exec -it redis redis-cli XRANGE migration.inventory.customers - +
docker exec -it redis redis-cli XRANGE migration.inventory.products - +
docker exec -it redis redis-cli XRANGE migration.inventory.orders - +
docker exec -it redis redis-cli XRANGE migration.inventory.products_on_hand - +

Then let’s add a new customer:

docker exec -it postgres psql -U postgres -d postgres -c \
"INSERT INTO inventory.customers (first_name, last_name, email) VALUES ('John', 'Doe', 'john.doe@example.com');"

Performance Considerations

Performance evaluation is a serious thing. While we haven’t yet had time to perform a comprehensive performance analysis, the result is already clear: the memory footprint has been significantly reduced together with the startup time. You should notice a substantial decrease in the amount of memory used by Debezium Server with a speed-up in the startup. In the coming months, we will focus on evaluating Debezium Server’s performance under certain conditions and, based on the findings, continue improving it step by step.

What’s next

We are in the Beta stage and many things still need to be addressed. We plan to distribute binaries and support additional sinks for the native build in a future release. Additionally, the Debezium CLI project aims to integrate a simplified build process for Debezium Server that includes only the libraries required for a given pipeline (source and sink).

The future is bright for CDC!

About Debezium

Debezium is an open source distributed platform that turns your existing databases into event streams, so applications can see and respond almost instantly to each committed row-level change in the databases. Debezium is built on top of Kafka and provides Kafka Connect compatible connectors that monitor specific database management systems. Debezium records the history of data changes in Kafka logs, so your application can be stopped and restarted at any time and can easily consume all of the events it missed while it was not running, ensuring that all events are processed correctly and completely. Debezium is open source under the Apache License, Version 2.0.
