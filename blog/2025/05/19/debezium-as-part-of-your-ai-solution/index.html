Debezium as part of your AI solution Debezium as part of your AI solution
May 19, 2025 by Jiri Pechanec
demo ai rag

One question that we encountered recently is how to effectively integrate change data capture (CDC) with AI workloads — particularly for scenarios in which critical organizational knowledge is not publicly available. To help you to take advantage of your internal data, Debezium 3.1 introduces AI-focused features such as the Embeddings SMT and the Milvus sink, which you can combine to supply inputs to an LLM. You can read more about these enhancements in the Debezium 3.1 release notes.

Introduction

In this post, we’ll show how Debezium, Milvus, and Ollama can work together to form a Retrieval-Augmented Generation (RAG) pipeline. By capturing changes from a relational database, enriching them with vector embeddings, and enabling similarity search across these vectors, you can build AI-driven applications that are powered by up-to-date, domain-specific knowledge.

Let’s look at an example that illustrates how you can use Debezium to enrich your AI applications with knowledge captured from experts within your organization.

Suppose that our organization introduces a new AI-driven application that is backed by an LLM. To enrich and extend the language model, we want to take advantage of internal organizational knowledge that is stored in text documents in a PostgreSQL database. Whenever users within the organization interact with the AI application, we want to make sure that its responses are informed by the most current local knowledge. Because the local knowledge that is stored in the PostgreSQL database is in constant flux, with documents being added, updated, or withdrawn to comply with regulatory requirements, we need a solution that has the agility to keep up with these changes.

The common solution to address this problem is to implement Retrieval-Augmented Generation (RAG). This post demonstrates how to use Debezium to build a CDC-fed RAG system that uses the following components:

  • A PostgreSQL database for data storage

  • Milvus vector database

  • Debezium Server to feed Milvus from PostgreSQL

  • A local Ollama hosted LLM

  • A Java application that interacts with the LLM and uses RAG to provide prompt context

What is RAG (Retrieval-Augmented Generation)?

Retrieval-Augmented Generation (RAG) is an AI technique that combines information retrieval with generative models to produce more accurate and contextually relevant responses. Instead of relying solely on a model’s internal knowledge, RAG pipelines retrieve relevant documents or data from an external source (like a vector database) and use that information to enrich the model’s responses. In our scenario, Debezium, Milvus, and Ollama work together to form a RAG workflow: data changes are captured and vectorized, stored in Milvus, and then retrieved to augment LLM outputs with up-to-date, domain-specific information.

What is Debezium Server?

Debezium Server is a Debezium implementation that you can use to stream change events from databases to various sinks without the need to deploy a Kafka cluster. It provides a lightweight way to consume CDC events and forward them to destinations from which they can be consumed by other applications. Debezium Server also supports the use of Kafka Connect single message transformations within its processing pipeline.

What is Milvus?

Milvus is a specialized vector database designed for similarity search and AI-heavy workloads. Whether it’s product recommendations, image search, or any other use case that relies on fast vector retrieval, Milvus is built for that. A vector database and fast vector retrieval is the heart of any RAG solution. The vector database stores so called embeddings - vector representations of the data that can be used for tasks like similarity search or clustering. Based on similarities between a prompt and the stored data, the AI application extends the context of the prompt.

Why Milvus as a Sink?

For applications where you need up-to-date vector representations of your data, pushing changes from a transactional database into Milvus makes a lot of sense. By using Milvus, not only can you keep your AI models in sync with operational data, you can also offload similarity search to a system that is built for it.

How Debezium Milvus Sink Works

A typical deployment of Milvus sink uses the following workflow:

  • The Debezium connector captures changes from a source database.

  • If the source database does not contain a field with embeddings, then the FieldToEmbedding SMT is used to enrich change events with vector embeddings.

  • Milvus sink writes the vector data into Milvus.

  • Milvus stores and indexes the vectors for fast similarity search.

Example application

This blogpost is based on the Debezium ai-rag example application. Let’s go step-by-step through the details and internals of the application so you can easily build your own.

The application architecture consists of the following two flows, which share a common Milvus instance:

  • Data pipeline

  • AI application

The data pipeline ingests data into Milvus, while the AI application queries Milvus to find similarities in the data.

Data pipeline

Our organization sources documents in an arXiv service that provides scholarly articles for download in different formats. The test application downloads a requested article based on its identifier and stores it in a PostgreSQL table.

The PostgreSQL table is created with the following DDL:

CREATE TABLE documents (
  id VARCHAR(64) PRIMARY KEY,
  metadata JSON,
  text TEXT
);
ALTER TABLE documents REPLICA IDENTITY FULL;

The replica identity of the table is set to FULL, so Debezium preserves the original state of a row in update and delete messages. Our demo doesn’t require preservation of the original row state, but being able to refer back to the original state is useful for some implementations.

Upon user request, the application downloads documents in text form and stores them in the table. Debezium stores the document identifier in the id field of the event; the textual representation of the article in the text field; and JSON metadata {"id:" "<document id>"} in metadata. The table does not provide a column with embeddings, so Debezium must use its FieldToEmbedding SMT (described later) to calculate them.

In our environment, we run a local LLM that is based on the Ollama LLM framework. For the model, we selected granite3.1-dense:2b, a text-only model that is optimized for RAG. Our model is one of large family of open-source IBM Granite models, but the application is not limited to it and can use an arbitrary model.

Debezium Server provides an interface between the PostgreSQL store and the Milvus sink. Because embeddings are not provided, we can use the Debezium FieldToEmbedding SMT to calculate them and store them a field named vector.

Internally, our application uses the Milvus embedding store for LangChain4j, so we retain the following default Milvus collection structure:

  • id - VarChar

  • metadata - JSON

  • text -VarChar

  • vector - FloatVector

There is a known issue in the module that causes an application failure when the store is empty. To work around the issue, we store a dummy document in the database (and thus in Milvus).

AI Application

The AI application interacts with the LLM and extends the prompt based on similarities in the embeddings in the prompt and in the data that it loads from the Milvus store.

The demo application is command-line driven, and is written using the Quarkus framework. For AI features, the application uses the Quarkus LangChain4j extension, specifically the open-source Ollama LLM and the Milvus Store for RAG.

The AI service is registered via the Debezium Chat class.

package io.debezium.examples.airag;

import dev.langchain4j.service.SystemMessage;
import dev.langchain4j.service.UserMessage;
import io.quarkiverse.langchain4j.RegisterAiService;

@RegisterAiService(retrievalAugmentor = MilvusRetrievalAugmentor.class)
public interface Chat {

    @SystemMessage("You are an expert that provides short summaries.")
    String chat(@UserMessage String message);
}

You use application.properties to configure the module.

quarkus.langchain4j.ollama.base-url=http://localhost:11434
quarkus.langchain4j.ollama.chat-model.model-id=granite3.1-dense:2b
quarkus.langchain4j.ollama.embedding-model.model-id=granite3.1-dense:2b
quarkus.langchain4j.ollama.timeout=120s

RAG is enabled using the retrievalAugmentor parameter on the @RegisterAiService annotation and is implemented in the MilvusRetrievalAugmentor bean.

@ApplicationScoped
public class MilvusRetrievalAugmentor implements Supplier<RetrievalAugmentor> {

    private final RetrievalAugmentor augmentor;

    MilvusRetrievalAugmentor(MilvusEmbeddingStore store, EmbeddingModel model) {
        EmbeddingStoreContentRetriever contentRetriever = EmbeddingStoreContentRetriever.builder()
                .embeddingModel(model)
                .embeddingStore(store)
                .maxResults(3)
                .build();
        augmentor = new RetrievalAugmentorDecorator(DefaultRetrievalAugmentor
                .builder()
                .contentRetriever(contentRetriever)
                .build());
    }

    @Override
    public RetrievalAugmentor get() {
        return augmentor;
    }

    private class RetrievalAugmentorDecorator implements RetrievalAugmentor {

        private final RetrievalAugmentor delegate;

        public RetrievalAugmentorDecorator(RetrievalAugmentor delegate) {
            this.delegate = delegate;
        }

        @Override
        public AugmentationResult augment(AugmentationRequest augmentationRequest) {
            Log.infof("Requested augmentation of %s", augmentationRequest.chatMessage());
            final var result = delegate.augment(augmentationRequest);
            Log.infof("Result of augmentation is %s", result.contents());
            return result;
        }
    }
}

The EmbeddingStoreContentRetriever class queries the Milvus vector database and enhances the prompt context with the three most similar documents. The class also provides the RetrievalAugmentorDecorator, which logs details of the augmentation operation.

You also use application.properties to configure the Milvus embedding store, as shown in the following example:

quarkus.langchain4j.milvus.host=localhost
quarkus.langchain4j.milvus.port=19530
quarkus.langchain4j.milvus.create-collection=false
quarkus.langchain4j.milvus.collection-name=demo_ai_documents

# The following two settings are not supported by the current version of Quarkus Langchain4j extension
# Also field with text cannot be overriden and is default text
quarkus.langchain4j.milvus.primary-field=id
quarkus.langchain4j.milvus.vector-field=vector

Demo

The demo is composed of the following two components:

  • A Docker Compose configuration file that starts all of the services.

  • A Java CLI application in the client directory that emulates both the data pipeline and the AI application.

Starting the deployment

In Terminal 1, enter the following command and wait for the containers to start.

$ docker-compose up --build

The preceding command extends the standard Debezium Server image with the debezium-ai-embeddings-ollama module (the AI embeddings modules are not included by default). The command also starts the PostgreSQL (postgres), Milvus (milvus), Debezium Server (debezium-server) and Ollama (ollama) containers.

In Terminal 2, enter the following command to start the Granite LLM model:

$ docker exec -it ollama ollama run granite3.1-dense:2b

We need to make sure that we are testing the application with facts that the model is unaware of. First, we will check the model’s cut-off date (what’s the latest data the model has seen).

>>> What is your cut off date?
My knowledge cut off date is April 2024. I can provide information and answer questions based on data up to
that point. For more recent events or discoveries, I'm unable to include those details in my responses as
they weren't available at the time of my training data. If you have any questions within this timeframe,
feel free to ask!

Based on that fact, we selected the paper 2504.05309v1 (IterQR: An Iterative Framework for LLM-based Query Rewrite in e-Commercial Search System) to represent knowledge that is new to the application. This paper was published in February 2025, after cut-off date, and it contains the very specific keyword, IterQR. We will test the model by asking about the framework.

>>> Describe IterQR framework in 20 words.
Iterative Quantized Ridge Regression (IterQR), a scalable method for large-scale regression, iteratively
refines coefficients via quantization and ridge regression techniques to minimize computational complexity
while maintaining accuracy.

The answer is completely unrelated to the framework and exhibits traits of hallucination. The model does not know about the fact so it invents its own without any connection to reality. When we ask the model this question multiple times it provides different and unrelated responses.

Stopping the demo

To end the demo deployment, enter the following command:

$ docker-compose down

The preceding command terminates the containers in all terminals.

Conclusion

Debezium enables organizations to plug their existing databases directly into modern Retrieval-Augmented Generation (RAG) pipelines — with zero modifications to source applications. That means all the innovation, experimentation, and AI development can happen in parallel, without interfering with established processes, compliance controls, or legacy architecture.

This blogpost describes how Debezium 3.1 can be integrated into AI workflows, particularly those using Retrieval-Augmented Generation (RAG). Debezium captures real-time changes from a database and feeds them into vector databases. These updates are essential for keeping AI systems current with fresh, domain-specific data. The example setup involves PostgreSQL, Debezium Server, Milvus, and Granite LLM (with embeddings). This architecture enables you to deploy intelligent applications that respond with accurate, up-to-date information.

Turn your company’s data into a competitive advantage — without rewriting a single line of production code.

About Debezium

Debezium is an open source distributed platform that turns your existing databases into event streams, so applications can see and respond almost instantly to each committed row-level change in the databases. Debezium is built on top of Kafka and provides Kafka Connect compatible connectors that monitor specific database management systems. Debezium records the history of data changes in Kafka logs, so your application can be stopped and restarted at any time and can easily consume all of the events it missed while it was not running, ensuring that all events are processed correctly and completely. Debezium is open source under the Apache License, Version 2.0.
