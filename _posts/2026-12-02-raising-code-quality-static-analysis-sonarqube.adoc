Code quality has always been a core value of the Debezium project.
With a growing codebase, an expanding list of connectors, and a steady stream of community contributions, keeping quality consistently high across the board becomes harder over time.
Code reviews catch a lot, but reviewers are human and some classes of issues — subtle bugs, code smells, security vulnerabilities — are easier for machines to spot.
That is why we have adopted https://www.sonarsource.com/products/sonarqube/[SonarQube] as part of our development workflow.
In this post we explain what motivated this decision, how the integration works, and what it means for contributors and maintainers going forward.

[id="what-is-static-analysis"]
== What is static analysis and why does it matter?

Static analysis is the automated inspection of source code without executing it.
A static analysis tool reads your code, applies a set of rules, and reports issues it finds — potential bugs, security vulnerabilities, code smells, duplicated blocks, and gaps in test coverage.

This is different from testing, which is a form of _dynamic_ analysis: you run the code with specific inputs and check that the outputs are correct.
Tests tell you whether the code behaves as expected for the cases you thought of.
Static analysis tells you about problems you might not have thought to test for — a resource that is opened but never closed, a branch that can never be reached, or a pattern known to cause vulnerabilities.
The two approaches are complementary: tests verify behavior, static analysis enforces structural quality.

For a project like Debezium, static analysis is especially valuable.
The codebase spans dozens of modules across multiple connectors, contributions come from a wide range of developers with different levels of familiarity with the project, and consistency matters when different people touch the same code over time.
Automated rules act as a shared baseline that applies equally to every change, regardless of who wrote it or who reviews it.


[id="why-sonarqube"]
== Why SonarQube?

SonarQube is a static analysis platform that inspects your code in a single pass and reports bugs, vulnerabilities, security hotspots, code smells, duplication, and test coverage gaps.
It goes beyond a simple linter: each finding is classified by severity and type, assigned an estimated effort to fix, and linked to documentation that explains why the pattern is problematic and how to resolve it.

Rather than just flagging issues in a log, SonarQube provides a web dashboard where you can browse findings per project, drill down by module or file, and track how the number of issues changes over time.
You can define quality gates — a set of conditions that new code must meet before it is considered acceptable — and wire them into your CI pipeline so that a pull request cannot be merged until the gate passes.
This combination of deep analysis, clear reporting, and enforceable gates is what sets SonarQube apart as a platform rather than just another tool in the chain.

Several factors made SonarQube the right fit for Debezium specifically:

* **Comprehensive Java support.** SonarQube ships with hundreds of rules for Java out of the box, covering everything from null-pointer risks to concurrency pitfalls.
* **GitHub integration.** Analysis results show up directly on pull requests as status checks and inline annotations, so contributors get feedback without leaving their workflow.
* **Historical tracking.** The dashboard lets us see how code quality evolves over time, making it easy to spot regressions or measure the impact of cleanup efforts.
* **Free analysis for open-source projects.** Sonar provides a https://www.sonarsource.com/open-source-editions/[free SonarQube Cloud offering for open-source projects], which lets Debezium use the hosted service at no cost. SonarQube Cloud is not itself open source; the separate, self-hosted SonarQube Community Build is free and open source, with a different feature set.

[id="integration"]
== Integrating SonarQube into the Debezium workflow

For now, the scope is limited to the main Debezium repository.
This includes the core framework and the connectors that live in that repo.
Other repositories in the Debezium organization — such as the UI, the operator, or the standalone connectors — are not yet part of the analysis.

The analysis runs as a GitHub Actions workflow on the main https://github.com/debezium/debezium[Debezium repository].
A scheduled job triggers every night, so by the time the team starts their day the dashboard already reflects the latest state of the codebase with fresh metrics.

Since the workflow runs on a schedule rather than on every push, it does not add any overhead to the pull request pipeline.
Contributors can open and merge pull requests without waiting for a SonarQube check to complete.
The nightly run then picks up all the changes that landed during the day and produces a consolidated report, making it easy to review the overall trend without noise from intermediate commits.

The dashboard is public — you can browse the current state of the analysis at any time on https://sonarcloud.io/project/overview?id=debezium_debezium[Debezium's SonarCloud project page].

== Key findings and early wins

The initial scan of the Debezium codebase did not surface any major issues, which is a testament to the quality of the code that contributors have built over the years.
SonarQube did identify a handful of potential arithmetic exceptions — division operations where a zero denominator is theoretically possible — along with a collection of minor code smells findings.
None of these are critical, but they are worth addressing to keep the codebase clean going forward.

image::sonarcloud-findings.png[SonarCloud findings view showing sample issues identified in the Debezium codebase]

What stands out most is the overall grade: Debezium already holds an **A rating on Maintainability**.
This is the highest grade SonarQube assigns, and earning it on a codebase of this size and age is not trivial.
It reflects the care that contributors and reviewers have put into the project throughout its history.
The remaining findings on Security and Reliability are similarly minor, and bringing those to an A grade as well is a realistic near-term goal.

[id="impact"]
== Impact on the development process

For the time being, nothing changes in the day-to-day workflow of contributors.
Pull requests are not gated on SonarQube today, and there are no new checks to pass or annotations to respond to.
The analysis runs in the background, and the results are reviewed by the maintainers.

The plan is to get there in stages.
The first step is to reach an A grade across all three of SonarQube's main dimensions — Security, Reliability, and Maintainability.
Maintainability is already at A; the remaining two need a small number of findings resolved to reach the same level.
Once all three dimensions hold a clean A grade, we will start enforcing quality gates so that new code does not introduce regressions that lower the rating.
At that point, contributors will see SonarQube feedback on their pull requests, similar to how existing CI checks work today.

We know that static analysis is not perfect.
False positives happen, and there will be cases where the team disagrees with a rule or a specific finding.
When that happens, the right thing to do is raise it — reach out on https://debezium.zulipchat.com/[Zulip] and we will work through it together.
Depending on the case, we may suppress the finding, adjust the rule configuration, or mark it as won't fix.
The goal is to keep the signal-to-noise ratio high so that the tool remains useful rather than becoming a source of friction.

[id="whats-next"]
== What's next

The current setup is just the starting point.
Here is what we have planned next:

* **Expand to other repositories.** The Debezium organization includes several repositories beyond the main one — the UI, the operator, Debezium Server, and the standalone connectors. We plan to bring SonarQube analysis to these repositories as well, so that the entire project benefits from the same quality baseline.
* **Run analysis on every pull request.** Once the codebase reaches A grades across all dimensions, we will wire SonarQube into the pull request workflow so that every PR gets analyzed before it is merged. This will catch issues early, before they land on the main branch.
* **Community contributions.** If you are looking for a way to contribute to Debezium beyond features and bug fixes, helping resolve SonarQube findings is a great place to start. Many of the open findings are small, self-contained improvements — fixing a code smell, closing a resource properly, or removing dead code. They are ideal for a first contribution or for getting familiar with a part of the codebase you have not worked in before.
* **Share your ideas.** SonarQube is one tool among many. If you know of other tools or practices that could help improve the quality of the Debezium codebase, we would love to hear about them. Drop by https://debezium.zulipchat.com/[Zulip] and let us know.

Automated quality tooling is not a replacement for good engineering practices — it is a multiplier.
Debezium's codebase is already in great shape thanks to the people who build and review it every day.
Tools like SonarQube help us keep it that way as the project continues to grow.
