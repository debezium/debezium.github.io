Command Query Responsibility Segregation (CQRS) is a design pattern that separates read and write operations to and from the database.
It can also be used to aggregate data from multiple sources into a single, centralized data store.
Although this pattern is commonly used in microservice architectures, it is not limited to them.
In this blog post, we will explore how to implement the pattern in different setups and how Debezium can simplify its implementation.

+++<!-- more -->+++

== Understanding the CQRS Design Pattern

In a traditional architecture, both reads and writes are handled by the same application and use the same database for all operations.
This means they share the same data model and are subject to the same performance constraints.
As the application grows, this unified approach can become a bottleneck.
Read and write operations often have different performance characteristics, and operating on the same data can lead to lock contention.
Using a single data model can also increase database load, since reads and writes may need different sets of fields.
A shared database also requires elevated permissions, which can introduce security risks.

In a microservice architecture, it’s common to use the link:https://microservices.io/patterns/data/database-per-service.html[Database per Service pattern], where each microservice has its own database.
However, workflows and user interfaces often require combining data from multiple microservices.
This can be challenging and may result in delayed responses, as one slow service can block the entire query.
It’s often more efficient to have an aggregating database that continuously collects data from all microservice databases and serves as a read-only database for complex queries.

All these challenges can be addressed with the CQRS design pattern.
The pattern separates reads and writes into distinct data models stored in separate databases, handled by different parts of the application—or even by entirely separate microservices.

=== Benefits and challenges

The database that serves read operations is typically configured as read-only for the application.
This reduces the attack surface and improves the overall security of the system.
The read database can be a replica of the write database, but it can also be a completely different type of database—one that is better optimized for read queries (for example, a time-series database) or one that aggregates data from multiple data sources.
In principle, both read and write data models can reside within the same database instance, but in practice, it is much more common to use separate databases.
This approach allows each database to be tuned and scaled independently according to its workload.

In the microservice world, different microservices are often developed by different teams and deployed on independent schedules.
Synchronizing data schemas and managing changes in data formats can therefore become challenging.
The CQRS pattern helps mitigate this issue by decoupling data models between services, allowing each service to evolve its schema independently without tight coordination with other teams.

Of course, adopting the CQRS pattern also introduces some challenges.
The most obvious one is the increased complexity of deployment and data management.
Replicating data between databases can lead to an eventual consistency model, where newly written data might not be immediately available on the read side.
However, in most microservice architectures, this short delay is acceptable and rarely causes real issues.

=== Possible Deployment Architectures

The main challenge in implementing the CQRS pattern is how to replicate data from the write database to the read database.
There are three typical deployment scenarios.

The first scenario is when both data models exist in the same database.
In such a case, there is no need to replicate data to another database instance, which makes this setup very simple to implement.
However, this approach forfeits most of the benefits of the CQRS pattern and is therefore rarely used in production.

A more common setup is to use the same database type for both instances and leverage the database’s built-in replication capabilities.
This, of course, assumes that the database you are using supports replication.
Databases with replication features are usually mature enough to provide several options how to configure replication.
In some cases, you can even configure the primary database to commit transactions only after the data has been replicated to the replica.
This ensures strong consistency between the two instances if your use case requires it.

The third scenario arises when the database does not natively support replication, or when you want to use different database types, or even aggregate data from multiple databases into one central read database.
In such cases, you need to set up replication using a third-party tool.
A convenient and reliable approach is to use Change Data Capture (CDC) with Debezium.
Debezium can capture database changes in real time and propagate them to one or more target databases.

In this blog post, we will focus on the latter two approaches—replication via database-native mechanisms and replication using Debezium.

== The Demo Application

=== Use Case

Since our main objective is to demonstrate how to implement data replication within the CQRS pattern, we will use a very simple use case.
We will build a basic voting application, without any user management or security checks.
A user will be able to create a poll with several options through a REST API, and other users will be able to cast their votes for any of these options.
Naturally, we will also want to view the results of the polls.
Results will be available again over a REST API, and to make the application a bit more engaging, we will add a simple web UI that displays the current voting results.

The application will be split into two microservices, each with its own database.
The first microservice will expose a REST API for creating new polls and casting votes.
New polls and votes will be written into its database.
Poll and voting data will then be replicated into another database instance, which will serve the second microservice responsible for displaying poll results.

You can find the application source code in the *Debezium example repository*.
The application uses the link:https://quarkus.io/[Quarkus] framework and its link:https://quarkus.io/guides/rest[REST module] for implementing REST APIs, along with link:https://quarkus.io/guides/hibernate-orm-panache[Panache] and link:https://quarkus.io/guides/hibernate-orm[Hibernate ORM] for persistence.
In the first microservice, there is a one-to-one mapping between entities and database tables, and Panache handles most of the persistence logic automatically.

The application leverages link:https://docs.quarkiverse.io/quarkus-quinoa/dev/index.html[Quarkus Quinoa] to integrate a lightweight Node.js web application using ReactJS.
The frontend periodically polls the REST API to fetch the latest results and updates the displayed chart.
Thanks to Quarkus, the entire application codebase remains compact, and a notable highlight is how effectively Quarkus reduces boilerplate.

== CQRS with Database Built-in Replication

As mentioned earlier, the simplest implementation of the CQRS pattern is when your database provides built-in replication capabilities.
In our example, we use the PostgreSQL database, which supports link:https://www.postgresql.org/docs/current/runtime-config-replication.html[streaming replication].
Schematically, our demo application looks like this:

<div class="imageblock centered-image">
    <img src="/assets/images/2025-10-14-cqrs/cqrs-replication.png" class="responsive-image" alt="Demo application with DB replication">
</div>
++++

To enable streaming replication between two PostgreSQL instances, we first need to create a publication on the primary instance and a replication role with `SELECT` rights on the required tables:

[source,sql,options="nowrap"]
----
CREATE PUBLICATION poll_pub FOR ALL TABLES;
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'replicator';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO replicator;
----

For simplicity, we granted `SELECT` rights on all tables.
In a production setup, you should limit these privileges to only the tables that actually need to be replicated.

Because Hibernate may drop and recreate tables as part of schema updates, we also need to replicate `DELETE` operations.
To do this, we configure full table replication for the tables that need to be synchronized:

[source,sql,options="nowrap"]
----
ALTER TABLE OptionEntity REPLICA IDENTITY FULL;
ALTER TABLE PollEntity REPLICA IDENTITY FULL;
...
----

Since Hibernate can dynamically create tables, you may also want to grant `SELECT` permissions to the replication role for any tables that might be created in the future:

[source,sql,options="nowrap"]
----
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO replicator;
----

However, this is not required in our demo application, as all tables are created in advance.

On the replica database, you simply need to subscribe to the publication created on the primary database using the appropriate credentials:

[source,sql,options="nowrap"]
----
CREATE SUBSCRIPTION poll_sub
    CONNECTION 'dbname=postgres host=postgres_primary user=replicator password=replicator'
    PUBLICATION poll_pub;
----

After setting this up, all changes will automatically be replicated from the primary database, which serves the writer microservice, to the replica database used by the reader microservice.
This is a straightforward and reliable solution that does not require any third-party tools.
It can serve well until you need to integrate multiple data sources or use a different database type for the reader microservice.

== CQRS in Heterogeneous Environments

In more heterogeneous environments, where different database technologies are used for the write and read sides, built-in replication mechanisms are usually not sufficient.
You may want to replicate data between different types of databases or aggregate data from several systems into a single read-optimized store.
In such cases, a Change Data Capture (CDC) solution like Debezium becomes extremely useful.

Debezium continuously monitors changes in a source database by reading its transaction log and publishes these changes as events to Apache Kafka.
From there, the data can be written into another database or system using a suitable Kafka Connect sink connector.
For database which support inserting data over JDBC, we can use link:https://debezium.io/documentation//reference/connectors/jdbc.html[JDBC sink connectr], eventually for MongoDB we can use link:https://debezium.io/documentation//reference/connectors/mongodb-sink.html[MongoDB sink connector].
For databases which don't support inserts over JDBC, other than MongoDB, we have to rely on the custom sink connector provided by the database vendor.

However, Debezium usage is not limited to Kafka Connect runtime.
We can e.g. embed Debezium into our custom microservice, but in such case we have to implement sink part (part which writes the captured data into target database) ourselves.

=== Replicating from PostgreSQL to MySQL

This setup demonstrates how to use Debezium with Kafka Connect to replicate data between two relational databases and target database supports JDBC API.

The source side uses the Debezium PostgreSQL connector with a minimal configuration that specifies connection details and the tables to monitor:

[source,json,options="nowrap"]
----
{
    "name": "postgres-source",
    "config": {
        "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
        "tasks.max": "1",
        "database.hostname": "postgres",
        "database.port": "5432",
        "database.user": "postgres",
        "database.password": "postgres",
        "database.dbname": "postgres",
        "topic.prefix": "polls",
        "table.include.list": "public.optionentity, public.pollentity, public.pollentity_optionentity, public.pollentity_voteentity, public.voteentity"
    }
}
----

This configuration captures all changes in the specified tables and publishes them to Kafka topics under the prefix `polls`.

On the sink side, we use the Debezium JDBC Sink Connector to insert these records into a MySQL database.
Since the JDBC sink understands Debezium’s event format, no single message transformation (SMT) is required.

[source,json,options="nowrap"]
----
{
    "name": "mysql-sink",
    "config": {
        "connector.class": "io.debezium.connector.jdbc.JdbcSinkConnector",
        "tasks.max": "1",
        "connection.url": "jdbc:mysql://mysql:3306/polls",
        "connection.username": "mysqluser",
        "connection.password": "mysqlpw",
        "insert.mode": "upsert",
        "delete.enabled": "true",
        "primary.key.mode": "record_key",
        "schema.evolution": "basic",
        "collection.name.format": "${source.table}",
        "topics": "polls.public.voteentity, polls.public.optionentity, polls.public.pollentity, polls.public.pollentity_optionentity"
    }
}
----

In this configuration, the `insert.mode` is set to `upsert`, which ensures that both new inserts and updates are properly reflected in the target database.
Deletes are enabled as well, since Hibernate may drop tables.
The `${source.table}` placeholder ensures that each target table in MySQL matches the corresponding table name in PostgreSQL.

With just two simple configurations, Debezium ensures continuous data replication between two different database vendors.

=== Replicating from PostgreSQL to QuestDB

One of the advantages of using CQRS design pattern is that for aggregating and reading data we may use some special-purpose database which is able to optimize our query much better than general-purpose database.
However, such database may not work with Debezium JDBC sink connector and if our database of choice is not MongoDB, it may look like we are out of luck.
Fortunately not.
We can take advantage of popularity of Kafka Connect platform.
Due to Kafka popularity many database vendors provides their own sink connectors for Kafka Connect.

In the second example, we replicate data from PostgreSQL into link:https://questdb.com/[QuestDB], a high-performance time-series database optimized for analytical queries.
To keep out demo application simple and unified across all the examples, we don't use any QuestDB features or don't so provide any time-related charts, e.g. how the number of votes evolved during the time, but you can easily image that it would just a simple modification of the reader microservice to provide such plots.
We cannot use JDBC sink connector for QuestDB as for ingesting the data it supports InfluxDB Line Protocol.
However, QuestDB provides their own link:https://questdb.com/docs/third-party-tools/kafka/[sink connector] for Kafka Connect.
Moreover it works well with Debezium format.

QuestDB sink connector behaves little bit differently to Debezium sink connectors.
It coverts into table columns all fields in the records.
Thus, as the first step, we will modify our PostgreSQL source connector configuration little bit and flatten the record to contain only new record state.
Conveniently Debezium provides link:https://debezium.io/documentation//reference/transformations/event-flattening.html[New record state SMT], which does exactly this - extracts only new state from the Debezium record.
The configuration of the PostgreSQL source connector now looks like this:

[source, json, options="nowrap"]
----
{
    "name": "postgres-source",
    "config": {
        "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
        "tasks.max": "1",
        "database.hostname": "postgres",
        "database.port": "5432",
        "database.user": "postgres",
        "database.password": "postgres",
        "database.dbname" : "postgres",
        "topic.prefix": "polls",
        "table.include.list": "public.optionentity, public.pollentity, public.pollentity_optionentity, public.pollentity_voteentity, public.voteentity",
        "transforms": "unwrap",
        "transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
        "transforms.unwrap.add.fields": "table"
    }
}
----

In the SMT configuration we also add additional field - the name of the table which the record comes from.

Another difference from the Debezium sink connectors is that single sink connector ingest data only to a single table.
We can either put everything into a single table or we have to deploy multiple connector.
Not to mix everything together and at the same time not to create several sink connectors and their configs for this simple demo, we can choose a compromise and create two sink connectors - one for polls and one for votes.
To be able to distinguish what was the original table, we included `table` field into the records.

The configuration for poll sink would look like this:

[source, json, options="nowrap"]
----
{
    "name": "questdb-sink-polls",
    "config": {
        "connector.class": "io.questdb.kafka.QuestDBSinkConnector",
        "tasks.max": "5",
        "topics": "polls.public.optionentity, polls.public.pollentity, polls.public.pollentity_optionentity",
        "table": "polls",
        "client.conf.string": "http::addr=questdb:9000;",
        "timestamp.field.name": "ts",
        "value.converter": "org.apache.kafka.connect.json.JsonConverter",
        "value.converter.schemas.enable": true,
        "include.key": false,
        "key.converter": "org.apache.kafka.connect.storage.StringConverter"
    }
}
----

And the votes sink like this:

[source, json, options="nowrap"]
----
{
    "name": "questdb-sink-votes",
    "config": {
        "connector.class": "io.questdb.kafka.QuestDBSinkConnector",
        "tasks.max": "5",
        "topics": "polls.public.voteentity",
        "table": "votes",
        "client.conf.string": "http::addr=questdb:9000;",
        "timestamp.field.name": "ts",
        "value.converter": "org.apache.kafka.connect.json.JsonConverter",
        "value.converter.schemas.enable": true,
        "include.key": false,
        "key.converter": "org.apache.kafka.connect.storage.StringConverter"
    }
}
----

This configuration ensures that poll-related data and vote data are written into separate QuestDB tables.
Even though this setup requires slightly more configuration compared to the JDBC sink, it remains straightforward and easy to configure.

== Application point of view

We have shown several ways how to replicate data from one database instance to the other as a main building block for implementing CQRS pattern.
No matter which setup you choose, the end result from the user perspective should be always the same and you should see something like this when looking on the poll results:

++++
<div class="imageblock centered-image">
	<img src="/assets/images/2025-10-14-cqrs/poll-results.png" class="responsive-image" alt="Demo application ">
</div>
++++

The results plot should be automatically update as the votes are castes by the voters.
The writer microservice which accepts the votes doesn't need to be changed as you change the backend databases.
The reader microservice which shows the results needs to be changed and re-deployed as we change the replica database.
But the only change which needs to be done is change in database URL and connection credentials.
In the case of QuestDB we also have to slightly modify SQL query as we simplified the deployment and merged several tables together.
However, all these things can be parametrized and be solved by using Quarkus profiles.
As a result we don't have to do any changes in the application source code, we just need to recompile the reader application with appropriate Quarkus profile and redeploy the microservice.
This nicely demonstrates another advantage of CQRS pattern - decoupling of the reader and writer parts into separate applications/microservices allows to change the backend, but it also shows the microservices can also change their data model without letting the other microservice know.
Thus each microservice can be developed and updated completely independently and using CQRS pattern gives developer teams much more freedom and flexibility.

=== Summary

CQRS design pattern is a powerful pattern which suggests to split the application into part responsible for manipulating with the database data and part responsible for reading this data.
This separation allows us to use different databases for each microservice.
Independent databases allows independent scaling and tuning adjusted exactly to their needs and workload of given microservice.
This segregation also allows different data models for each microservice allowing fine tuning of the models, but also independent evolution of each microservice.
Other benefits of implementing this pattern involves increased security as only microservice which push data into database needs to have write access, better clarity and simplicity of the code and more.

In this blog post, besides introducing the pattern itself, we concentrate on the main obstacle in implementation of this pattern - how to replicate the data between the databases.
We discussed several possible architectures and described ways how to ensure data replication in each setup.
We started with the simple case when the replication is ensured by database itself, continued with replication between two different relational databases and concluded with setup where the relational database is replicated in to special-purpose database.

We have shown how Debezium can tackle this problem, while the setup and configuration remains simple and declarative.
It allows you to replicate data between heterogeneous databases in real time, regardless of vendor differences.
This flexibility makes Debezium a perfect fit for implementing CQRS in complex, polyglot environments.
