The https://debezium.io/documentation/reference/stable/operations/debezium-platform.html[Debezium Platform] has been able to show you how your pipelines are doing for a while now.
The monitoring dashboard tells you the event rate, the source lag, the queue utilization, whether the snapshot finished.
It is genuinely useful, but it is passive: it only helps while somebody is looking at it.

In his https://debezium.io/blog/2026/07/10/debezium-platform-status-update/[mid-year Platform update], Mario listed alerting as one of the next things we wanted to tackle, for exactly that reason.
That work has now landed.
The Platform can watch those same panels for you and tell you when one of them crosses a line you care about.

This post walks through what alerting looks like in the Platform: how a rule is defined, how it moves from quiet to firing, where the notifications go, and what you can configure.

[id="monitoring-recap"]
== First, a quick recap of monitoring

Alerting is built directly on top of monitoring, so it is worth spending a paragraph on where the numbers come from.

A pipeline in the Platform is a Debezium Server instance deployed by the Debezium operator.
The Platform wires it up with the https://opentelemetry.io/docs/zero-code/java/agent/[OpenTelemetry Java Agent], which exports metrics over OTLP to an https://opentelemetry.io/docs/collector/[OpenTelemetry Collector].
The collector re-exposes them in Prometheus format, Prometheus scrapes the collector, and the Conductor (the Platform backend) queries Prometheus with PromQL when the UI asks for a panel.

Those panels are not hard-coded in the frontend.
The Conductor ships a `panels.yml` of PromQL-backed panel definitions, each with an id, a title, a category (`streaming` or `snapshot`), a unit, and a visualization type.
The UI renders whatever `/api/monitoring/panels` returns, which also means you can add your own panels or override a built-in one without touching the frontend.

The design details are in https://github.com/debezium/debezium-design-documents/blob/main/DDD-38.md#ddd-38-pipeline-monitoring-for-debezium-platform[DDD-38: Pipeline Monitoring for Debezium Platform].

[id="alerting-overview"]
== Alerting, built on the panels you already have

The obvious way to build alerting on Prometheus would be to let people write PromQL expressions.
We deliberately did not do that.

The Platform exists to give you a pipeline without making you learn the stack underneath it, and that principle applies here too.
An alert rule in the Platform does not reference a metric or an expression.
It references *a monitoring panel you can already see in the UI*, and adds a comparison and a threshold on top of it.

If you can read the Source Lag panel, you can write a rule about Source Lag.

A few consequences of that choice:

* No new infrastructure.
  The whole alerting engine lives inside the Conductor and reuses the Prometheus instance and the PostgreSQL database the Platform already has.
* Rules stay valid as panels evolve, because the rule stores the panel id and the engine resolves the query at evaluation time.
* Custom panels are alertable too.
  If you added your own panel through `monitoring.panels.additionalPanelsPath`, it shows up in the rule form's panel picker like any built-in one.

Rules are evaluated *globally*: a rule fires for any pipeline that breaches the threshold, and each pipeline gets its own incident.
You do not have to remember to attach the rule to new pipelines, because new pipelines are covered the moment they start reporting metrics.
Per-pipeline scoping is a reasonable next step and the data model is ready for it, but it is not in this first iteration.

The full design is in https://github.com/debezium/debezium-design-documents/blob/main/DDD-57.md[DDD-57: Alerting for Debezium Platform].

[id="alert-rule"]
== Anatomy of an alert rule

You will find a new *Alerts* section in the left navigation, with *Rules*, *Channels* and *History*.

The create-rule form is deliberately written as a sentence rather than a form of disconnected fields:

[source]
----
When    Source Lag          (panel)
Reduce  last                (how to collapse the time series)
Is      greater than  10    (operator and threshold)
For     5 minutes           (how long it has to hold)
----

Reading left to right: *when the last value of Source Lag is greater than 10 seconds for 5 minutes*.
The form shows that sentence back to you as you build it, so you are never guessing what the rule will actually do.

The pieces:

*Panel* -- picked from a dropdown grouped by *Streaming* and *Snapshot*, exactly as they are grouped on the monitoring tab.

*Reduce* -- a panel is a time series, and a rule needs a single number.
The reduce function decides how to get one: `last`, `avg`, `min`, `max` or `sum`.
`last` is the default and is what you want for gauges like lag, connection status or queue utilization.
`avg` is the better choice for noisy rate panels, where a single spike should not wake anybody up.

*Evaluation window* -- how much history the reduce function looks at, from 1 minute to 1 hour, 5 minutes by default.
It is ignored when reduce is `last`, and the form hides it in that case.

*Operator and threshold* -- the comparison, with the panel's own unit shown next to the input, so you are entering seconds for a lag panel and a percentage for a utilization panel.

*For* -- the noise suppression knob, and the one I would encourage you to actually use.
The condition has to hold continuously for this long before the alert fires.
Set it to *Immediately* and a single bad scrape pages you; set it to *5 minutes* and a transient blip resolves itself quietly.

*Severity* -- *Critical*, *Warning* or *Info*.
Severity is shown with both a colour and an icon rather than colour alone, and it determines whether the alert contributes to the badge in the header.

*Additional channels* -- where to notify, on top of the UI itself.

[id="lifecycle"]
== From quiet to firing and back

The Conductor runs an evaluation loop every 60 seconds by default.
For each enabled rule it queries Prometheus, applies the reduce function, compares the result against the threshold for every pipeline reporting that metric, and moves that `(rule, pipeline)` pair through a small state machine:

[cols="1,2", options="header"]
|===
|Transition |What happens

|OK -> Pending
|The condition is met for the first time. Nothing is sent yet; the engine just remembers when it started.

|Pending -> OK
|The condition cleared before the `for` duration elapsed. Silent reset, no notification. This is the case the `for` duration exists for.

|Pending -> Firing
|The condition held for the whole `for` duration. An incident is created and notifications go out.

|Firing -> Resolved
|The condition cleared. The incident is closed and a resolution notification goes out.

|OK -> Firing
|Same as above but with `for` set to *Immediately*, skipping the pending state.
|===

One behaviour worth calling out: when a pipeline pod disappears, its metrics go stale in Prometheus and the rule has no data to evaluate.
Rather than treating missing data as "everything is fine", the engine keeps the last state.
A firing alert stays firing, which is almost always what you want, because a pipeline that stopped reporting is usually the incident, not the end of it.

[id="channels"]
== Where the notifications go

Alerts always appear in the Platform UI.
That part is not configurable and does not need to be set up, which means a freshly installed Platform gives you working alerting with zero notification configuration.

On top of that there are two channel types, managed from *Alerts -> Channels*:

*Email* -- a list of recipients and an optional subject prefix.

*Webhook* -- a URL, an HTTP method and optional headers, which is the integration point for Slack, PagerDuty, OpsGenie, Teams, or anything else that accepts a POST.

Channels are named and reusable: one channel can serve many rules, and one rule can notify through several channels.
Each channel has a *Test* button that sends a sample notification and reports back, so you can find out that your SMTP credentials are wrong now rather than during an actual incident.

The webhook payload is intentionally flat and stable, with a `version` field so it can evolve without breaking your receiver:

[source,json]
----
{
  "version": "1",
  "status": "firing",
  "alert": {
    "ruleName": "high-source-lag",
    "severity": "CRITICAL",
    "pipelineId": "inventory-pipeline",
    "value": 15.2,
    "threshold": 10.0,
    "message": "Source lag (15.2s) exceeded threshold (10.0s)",
    "firedAt": "2026-10-21T14:30:00Z"
  }
}
----

The same shape is sent with `"status": "resolved"` when the incident closes, so a receiver can correlate the two.

One security note, because it affects what you can configure.
Webhook URLs are user-supplied and the Conductor runs inside your cluster, so an unvalidated webhook would be a convenient way to probe internal services.
The webhook notifier therefore resolves the URL *at send time* and rejects loopback, private and link-local addresses by default.
If your target genuinely is in-cluster -- an internal Slack relay, say -- you can opt out with `alerting.webhook.allowPrivateNetworks: true`.

[id="history"]
== Alert history

Notifications tell you about the moment.
The *History* page is for everything after that.

Every fire/resolve cycle is recorded as an incident with its rule, pipeline, severity, the value that triggered it, the threshold it breached, when it fired, and how long it lasted.
Rows expand to show the full detail, and the table can be filtered by severity, status, pipeline, rule and date range.
Incidents that are still firing are pinned to the top, so the page opens on "what is broken right now" and the rest is history underneath.

The pipeline name in each row links straight to that pipeline's monitoring dashboard, which is usually the next click anyway: you see that Source Lag fired, and you want to look at the chart.

There is also a badge in the header, counting active Critical and Warning alerts across all pipelines.
It takes the colour of the highest active severity -- red if anything critical is firing, amber if it is only warnings -- and clicking it drops you into the history page filtered to firing incidents.
`Info` alerts are recorded but deliberately left out of the badge, so you can use that severity for things you want in the log without turning the header into a permanent distraction.

Resolved incidents are cleaned up daily after a retention period of 30 days by default.
Still-firing incidents are never purged, regardless of age.

[id="configuration"]
== What you configure at install time

Rules and channels are created in the UI, not in Helm values.
The chart configures the machinery underneath them:

[source,yaml]
----
alerting:
  evaluation:
    interval: "60s"       # how often the evaluation loop runs
  history:
    retention: "30d"      # how long resolved incidents are kept
    cleanup:
      interval: "24h"
  webhook:
    allowPrivateNetworks: false
    maxAttempts: 3        # retries with exponential backoff
    connectTimeout: "5S"
    readTimeout: "10S"
  email:
    host: ""              # leave empty to keep email disabled
    port: 587
    from: ""
    startTls: "REQUIRED"
    auth:
      existingSecret: ""  # Secret with username and password keys
----

There is no `alerting.enabled` toggle, and that is on purpose: the evaluation loop is a no-op when no rules exist, so alerting costs nothing until you create your first rule.

Email is the one piece that needs install-time configuration, since the SMTP transport has to come from somewhere.
Point `alerting.email.host` at your server and reference a Kubernetes Secret with `username` and `password` keys:

[source,shell]
----
kubectl create secret generic smtp-credentials \
  --from-literal=username=myuser \
  --from-literal=password=mypassword
----

If no SMTP host is configured, email channels report a clear error when you test them, rather than silently swallowing notifications.

[id="try-it-out"]
== Try it out

The fastest way to see this end to end is the https://github.com/debezium/debezium-examples/tree/main/debezium-platform/platform-postgresql-kafka-monitoring-example[platform monitoring example] in the `debezium-examples` repository.
It brings up a local minikube cluster with PostgreSQL, Kafka, the OpenTelemetry Collector, Prometheus and the Platform, seeds a pipeline, and includes scripts that deliberately make the panels move -- generating traffic, stalling the pipeline, replaying a snapshot, and breaking the source connection.

Those same scripts are what you want for alerting, because an alert rule is hard to appreciate until you have watched one fire.
A good first rule is on *Time Since Last Event*, with `last greater than 60` for 1 minute: start the traffic generator, watch the rule sit quietly, stop it, and watch the rule go pending and then firing while the panel climbs.
Then insert a single row and watch it resolve.

[id="whats-next"]
== What is not there yet

Worth being explicit about the edges of this first iteration:

* No alert grouping, silencing windows or escalation policies.
  Disabling a rule is the current workaround for planned maintenance.
* No repeat notifications while an alert stays firing.
  You get one notification when it fires and one when it resolves.
* No raw PromQL rules.
  Rules are panel-based, though you can reach any metric you like by defining a custom panel for it.
* No per-pipeline rule scoping yet, as described above.
* The UI polls rather than receiving pushed updates, so the badge and history can lag a firing alert by a few seconds.

[id="conclusion"]
== Conclusion

Monitoring answered "how is my pipeline doing?" as long as you were looking.
Alerting answers it when you are not, using the same panels, the same metrics pipeline, and no extra infrastructure to run.

Give it a try on the latest Platform images, and tell us which rules you end up writing -- the set of panels people actually alert on is the best input we can get for where to take this next, per-pipeline scoping included.
