Identity and Access Management is a highly anticipated feature for the Debezium Platform, slatted for Q4.

Until then, we can explore what is currently possible: Single Sign-on, OpenID Connect, and even brokering Entra ID.
In this first post, I will walk you through putting a Debezium Platform deployment on Kubernetes behind a single sign-on (SSO) login with Keycloak as an Identity Provider.

The scenario throughout the blog series is **Contoso Retail**, a fictional company on the domain `contoso.com`, running the Platform on a Kubernetes cluster
and wanting its own staff list to govern access to it. Contoso Retail uses Entra ID as its corporate directory.

+++<!-- more -->+++

This works thanks to a https://github.com/debezium/debezium-platform/pull/472[PR] I authored.
But as is often the case with OSS contributions, my work rests on the shoulders of giants: the conductor, the Platform's API, is a Java Quarkus application, and Quarkus has excellent https://quarkus.io/guides/security-oidc-bearer-token-authentication[support for OIDC] -- most of the hard part was already done.

As I will show, the Debezium Platform doesn't care if your organization uses Entra ID, Amazon Cognito, Okta, etc.
An OAuth2 proxy intercepts the request to the Platform and hands you to Keycloak, whose login page carries an SSO button
for the third-party identity provider (Entra ID, for example) with all its capabilities -- 2FA, geolocation, and other conditional-access policies.
Keycloak then brokers that corporate directory information: it mints ID and access tokens compliant with OIDC by mapping the identity and authorization information it receives.

Getting there takes three steps, one per post:

* **This post -- a working login.** The Kubernetes deployment, with oauth2-proxy in front and Keycloak as the identity provider behind it -- no brokering to Entra ID yet.
* **The second -- a real corporate directory.** Replacing the hand-made Keycloak users by brokering to Microsoft Entra ID, so that user lifecycle and group membership live where the
organization already manages them.
* **The third -- laying the groundwork for RBAC.** The difference between an ID token and an access token, and how to get roles into the correct token.

[NOTE]
.A word on scope
====
In his link:/blog/2026/07/10/debezium-platform-status-update/[mid-year update post], Mario highlights the exciting coming features for the platform,
including Identity and Access Management (IAM).

This series of posts is an experiment that precedes the final architecture. It focuses on Single Sign-On (SSO) using the OpenID Connect (OIDC) protocol.
Two tokens will be issued by Keycloak, the _platform's_ identity provider (IdP): an ID token (who are you -- authentication) and an access token (what claims are you entitled to -- authorization).
At the time of writing, the Debezium Platform does not enforce roles defined in the access token.

Role-Based Access Control (RBAC) and other critical points of the security architecture are currently being worked on.
I encourage readers to subscribe to the link:/blog/[Debezium blog] for exciting announcements on the IAM implementation progress.
====

All the host names in this post are Contoso's, but the lab behind them ran on a domain I own, `1int.io` -- which is what the screenshots and decoded tokens actually show: `demo.1int.io` where the text says `demo.contoso.com`.
Nothing about that domain is special.
Anyone with a domain name of their own can reproduce all of it.

Two things are genuinely required:

* **A machine with a public IPv4 address, and a domain whose DNS you can point at it.** Two A records under a sub-zone of your own choosing, which is where link:#dns[section 2] starts. The posts rely on valid TLS certificates, and a Let's Encrypt DNS-01 challenge proves you own the zone by writing a record into it -- so the name has to be genuinely yours.
* **A Microsoft Entra ID account** -- for the next post in this series, so it can wait a short while. An Azure free trial or a pay-as-you-go subscription both produce a usable tenant, and everything that post does -- app registrations, app roles, users, groups -- is Entra ID Free, so the lab itself costs nothing to run.

[NOTE]
.Why not a self-signed certificate?
====
Because the browser is not the only client, and it is the only one with a "proceed anyway" button.

A self-signed certificate is still HTTPS, and you can click through the browser's warning.
However, two of the exchanges in this post never involve a browser at all: oauth2-proxy resolves OIDC discovery against Keycloak at startup
and trades the authorization code for tokens on every login, and the conductor fetches the realm's public keys to validate every bearer it is handed.
Those clients are a Go binary and a JVM.
Neither has a warning to click through; both just fail the handshake.

Entra ID arrives in the second post with a rule of its own -- a redirect URI must never be plain HTTP -- but a self-signed certificate satisfies that one.
It is the two calls above that rule it out, and they are already here in this post.

Working around it means installing your CA into each trust store independently: the JVM's for the conductor, the container's bundle for oauth2-proxy, and every browser and operating system that will ever open the UI.
That is more work than the DNS-01 challenge it replaces, and it has to be repeated for every component you add.

[id="dns"]
== 2. DNS first, because everything else waits on it

Take the public IPv4 address of the machine you provisioned and point a name at it.
The zone has to exist and be yours before cert-manager can do anything: a Let's Encrypt DNS-01 challenge proves ownership by writing a TXT record into it,
so you will need to obtain API credentials from whoever hosts your DNS.
The A records are what make the platform reachable once the certificate exists.

I recommend giving the lab **a sub-zone of its own**. Two advantages: no risk of collision if `contoso.com` already does something, and everything is nicely scoped under `demo.*`.

[source]
----
demo.contoso.com      A   <public-ip>
*.demo.contoso.com    A   <public-ip>
----

If following the guide in the companion repo, set `DPL_DOMAIN=demo.contoso.com`, and the platform publishes `auth.demo.contoso.com` and `dmp.demo.contoso.com`.
Two records, one throwaway branch of your zone, and nothing that already works stops working.

=== One naming trap

For those following the guide, do not make the sub-zone `dmp.`.
The platform publishes its UI at `+dmp.${DPL_DOMAIN}+`, so `DPL_DOMAIN=dmp.contoso.com` gets you `dmp.dmp.contoso.com`.
Pick a label that names the environment -- `demo`, `lab2`, `sso` -- not one that names a component.

=== At Gandi

Their DNS product is LiveDNS, and records are named **relative to the zone**.
The zone is still `contoso.com`; the two record names are `demo` and `*.demo`.

In the web console: **Domain -> DNS Records -> Add record**, type `A`, name `demo`, then again with name `*.demo`.

=== Everywhere else

The concept ports exactly; only the tool changes.

[cols="1,2", options="header"]
|===
| Provider | Equivalent

| **Route 53**
| `aws route53 change-resource-record-sets` with an `UPSERT` batch, or the console

| **Cloudflare**
| `POST /zones/<id>/dns_records`, or `flarectl dns create`

| **Google Cloud DNS**
| `gcloud dns record-sets update <name> --type=A --rrdatas=<ip>`

| **Anything else**
| Two A records under a sub-zone. Every registrar can do this.
|===

For the certificate step later, the only thing that matters is whether cert-manager has a DNS-01 solver for your provider.
It ships built-in solvers for Route 53, Cloud DNS, Cloudflare and a handful of others; Gandi is not among them, which is why that part of the lab runs an out-of-tree webhook.
If your DNS lives at one of the built-ins, that section gets simpler rather than harder. Just remember to use the shortest TTL possible for the records, so the propagation is as fast as possible.

=== Check it before moving on

[source,console]
----
$ dig +short demo.contoso.com
203.0.113.10  # should be your IPv4 public address
$ dig +short auth.demo.contoso.com
203.0.113.10
----

The second one is the one that matters -- it is answered by the wildcard, and it is what every component host depends on.
You can also run `dig +short anything.contoso.com` to make sure everything is contained to `demo` or whatever you chose. It should return nothing.

[NOTE]
.Why not sslip.io
====
Wildcard DNS services like `sslip.io` and `nip.io` resolve `203-0-113-10.sslip.io` to `203.0.113.10` with no configuration at all, but they are useless here.
Let's Encrypt will not issue for them, and DNS-01 needs a zone you can write to.

And downstream of both: Entra ID rejects any redirect URI that is not HTTPS, with only `localhost` exempt.
So the whole single-sign-on path depends on a real certificate, which depends on a real zone.
This is the step that decides whether the rest of the post is possible -- which is why it comes first.
====
But enough about DNS, on to the actual SSO setup.

[id="proxy-config"]
== 3. The proxy config, and how it relates to the IdP

Everything that follows rests on one file: the configuration of the `oauth2-proxy` instance that fronts the platform host.
It is short but well worth reading closely because most of its values are critical to a secured OIDC flow and depend on Keycloak's settings.

[NOTE]
====
An important concept related to Keycloak is that of a `realm`. It will be mentioned several times going forward.
A Keycloak realm is a self-contained identity domain — its own users, roles, clients and
signing keys — so an account in one realm does not exist as far as another is concerned.
====

Below is the file as I configured it in the companion repo, with its comments stripped.

[source,yaml]
----
config:
  existingSecret: oauth2-proxy-secret
  configFile: |-
    provider = "oidc"
    oidc_issuer_url = "https://auth.demo.contoso.com/realms/dmp"
    redirect_url = "https://dmp.demo.contoso.com/oauth2/callback"
    email_domains = ["*"]
    insecure_oidc_allow_unverified_email = true
    cookie_domains = [".demo.contoso.com"]
    cookie_secure = true
    cookie_refresh = "4m"
    cookie_expire = "10h"
    whitelist_domains = [".demo.contoso.com"]
    reverse_proxy = true
    pass_authorization_header = true
    pass_access_token = true
    skip_provider_button = true
    upstreams = [
      "http://conductor.dmp.svc.cluster.local:8080/api/",
      "http://stage.dmp.svc.cluster.local:3000/"
    ]

extraArgs:
  code-challenge-method: S256

ingress:
  enabled: true
  className: traefik
  path: /
  pathType: Prefix
  hosts:
    - dmp.demo.contoso.com
  tls:
    - secretName: wildcard-demo-contoso-com-tls
      hosts:
        - dmp.demo.contoso.com
----

The upstreams are the interesting structural part.
`/api/` goes to the conductor and everything else to stage, which is what makes this a reverse proxy rather than an authentication side-car.
Note the **trailing slash** on `/api/`: it makes the match a subtree.
Without it the match is exact, `/api/pipelines` falls through to the `/` upstream, and the stage UI answers an API call with HTML.

`skip_provider_button` removes the "Sign in with…" since there is exactly one provider: Keycloak.

=== The realm is the source of truth

The values that govern _time_ are not free variables.
Keycloak decides them, and the proxy either agrees or behaves incoherently.

Four numbers on those two screens determine how the proxy has to be configured to avoid a slew of 401 errors while still appearing to have a browser session:

[cols="1,1,2", options="header"]
|===
| Keycloak realm setting | Value | What it forces

| **Access Token Lifespan**
| 5 minutes
| The proxy must renew its access token more often than this

| **SSO Session Idle**
| 30 minutes
| After 30 minutes of inactivity the refresh token is dead and the user logs in again

| **SSO Session Max**
| 10 hours
| A hard ceiling: no proxy session should outlive it

| **Revoke Refresh Token**
| Disabled
| A refresh token can be used multiple times
|===

Keycloak even states the relationship on screen -- _"It is recommended for this value to be shorter than the SSO session idle timeout: 30 minutes"_.

=== Correct OIDC behavior

An oauth2-proxy session holds the access token it received at login.
It does not renew that token unless told to, and the setting that tells it is `cookie_refresh` -- **disabled by default**.
So with a 5-minute access token, the proxy hands the conductor a token that is valid for five minutes and then indefinitely stale, and the conductor rejects it.
The user sees a UI that loads perfectly while every API call fails, because the stage SPA component is unaware of any OIDC setup -- remember, the proxy fronts it.

The other half is `cookie_expire`, which defaults to **168 hours**.
Against an SSO Session Max of 10 hours, that is a proxy session widely outliving the identity session it was derived from.

Which is where the two lines already in the config above come from:

[source,toml]
----
# Renew before the 5-minute access token expires.
cookie_refresh = "4m"
# Do not outlive SSO Session Max.
cookie_expire = "10h"
----

This is worth remembering: **the identity provider owns the various TTLs**.

[NOTE]
.A reality check
====
Single sign-on here covers the Debezium Platform and nothing else: one host, behind one proxy.
Everything else in the list is left as an exercise for the reader.

Orchestrating single sign-on across an entire stack is that same work repeated per component: a client registration and a redirect URI for each, a proxy in front of anything that cannot speak OIDC itself, and a decision about the ones that can do neither.
Single sign-on is not a component you install, it is a property that only holds where every component in scope has been made to agree.

=== Hands on Keycloak... finally

Of the entries that are there `keycloak-initial-admin` contains the first admin account credentials generated by the Keycloak operator. To read it, use your
favorite Kubernetes admin tool, or simply in a terminal, one command for the username, once for the password:

[source,bash]

  -o jsonpath='{.data.password}' | base64 -d
----

=== First, a permanent admin

The account you just pulled out of that Secret is a bootstrap credential.
Keycloak calls it a _temporary_ admin and logs a warning about it on every startup; the operator generates it so that there is some way in on a fresh install, not so that you keep using it.
Replace it before doing anything else.

It lives in **`master`** -- Keycloak's own realm, the one that administers the server itself.
The permanent admin belongs in `master` as well, so stay where you are rather than switching realms for this.

**Users -> Add user.** Username, email, first and last name.

**Credentials -> Set password**, and turn **Temporary** to **Off**.

That toggle defaults to On, which marks the password as already expired and forces a change at next login.

**Role mapping -> Assign role -> Realm Roles -> `admin`.**

=== Configuring our first Keycloak client

Authorization code flow with Proof Key for Code Exchange (PKCE) is a mouthful.
I will leave it as an exercise for the reader to learn more about it https://oauth.net/2/pkce/[here]. There are many good tutorials out there as well.

In summary: `oauth2-proxy` sends you to Keycloak to log in, Keycloak sends you back carrying
a one-time ticket (the code) and `oauth2-proxy` redeems that ticket for your tokens in a
direct conversation the browser never sees.

PKCE adds one guarantee on top: before sending you off, the application (`oauth2-proxy`) invents a secret and hands over only a fingerprint of it.
Redeeming the ticket requires producing the original. So a ticket stolen in transit is worthless to whoever took it.
Since https://datatracker.ietf.org/doc/html/rfc9700[RFC 9700] (OAuth 2.0 Security Best Current Practice) it's recommended for all clients using the authorization code flow.

The second post in this series adds one hop: Keycloak stops checking the password itself and
forwards you to Entra ID, then brokers what comes back.

=== Creating it

A Keycloak client is a registration bound to a set of **valid redirect URIs**, and that binding is the load-bearing security control in the whole flow.

**Clients -> Create client**, then:

* **Client ID**: `oauth2-proxy` -- the proxy sends it as `client_id`, so a typo here surfaces later as `invalid_client`.
* **Client authentication: On.** This makes it a _confidential_ client, which is what generates the secret the proxy needs. Left off, the client is public, there is no Credentials tab, and there is nothing to put in the Kubernetes Secret.
* **Standard flow** enabled. That is authorization-code, the flow in the diagram above.
* **Valid redirect URIs**: `https://dmp.demo.contoso.com/oauth2/callback`

Then **Credentials -> Client secret -> copy**.
That value goes into Kubernetes next, and Keycloak will show it again later, so there is no need to be precious about it.

**Require PKCE is On, with PKCE Method `S256`.**
That is the Keycloak half of the `code-challenge-method: S256` line in the values file from link:#proxy-config[section 3], and the two halves have to agree.
Turn it on here while the proxy is not sending a challenge and every login dies at the authorization request with `invalid_request: Missing parameter: code_challenge_method` -- so set the proxy side first if you are enabling it on a running deployment.

=== The second client, which nobody redirects to

The conductor expects a client named `conductor` as well.
It never appears in the flow above, because it never logs anybody in -- it _validates_ tokens rather than issuing them, running as a Quarkus OIDC resource server.
No redirect URI, no callback, no browser involvement. It is strictly needed by the conductor (a resource server in OIDC parlance) as its own entry in the `dmp` realm,
and will carry the RBAC configuration -- out of scope for now.

=== Handing the credentials back to Kubernetes

Feed the secret you copied from Keycloak above to Kubernetes:

[source,bash]
----
kubectl -n identity create secret generic oauth2-proxy-secret \
  --from-literal=client-id=oauth2-proxy \
  --from-literal=client-secret='<from Keycloak>' \
  --from-literal=cookie-secret="$(openssl rand -base64 24)"
----

The `cookie-secret` has nothing to do with Keycloak.
It is the key the proxy uses to encrypt its own session cookie, so it is generated locally and never leaves the cluster.

=== A user to log in with

Everything is running, and nobody can log in.

The administrator from earlier lives in `master`.
The proxy authenticates against `/realms/dmp`, so that account is not merely unprivileged at the platform's login form -- it is _invisible_ to it.
Keycloak will not find it because it is not looking in that realm.

This is the realm boundary paying off exactly as advertised a few paragraphs ago.
Nobody had to remember to withhold platform access from the administrator.
The two populations are separate because they live in different realms, and the proxy only ever asks about one of them.

* **Fill in all four fields: username, email, first name, last name.**
+
The **email** is what oauth2-proxy uses to build a session.

=== OIDC in action behind the scenes

That "Welcome to Stage" screen is doing more work than it looks like.

A rendered page, on its own, proves only that the proxy let the request through -- the SPA shell is served by stage and would render regardless.
What makes this screen evidence is that stage immediately calls the conductor at `/api/`, and the conductor is an OIDC **resource server**: it validates the bearer token on every request against the realm's JWKS.

* oauth2-proxy matched `/api/` as a subtree and routed it to `conductor:8080`, while everything else went to `stage:3000`.
* `pass_authorization_header` injected `Authorization: Bearer <access_token>` into the _upstream_ request -- not the auth response, which is the distinction that makes reverse-proxy mode work where forward-auth would not.
* The conductor fetched the realm's JWKS from `https://auth.demo.contoso.com` -- a server-to-server call, with no browser to click a warning through -- and validated the signature.
* It answered `200` with an empty pipeline list, which is what the welcome screen _is_.

"No pipelines yet" is a successful API response.
Had any link in that chain broken, the page would have loaded and then failed: a spinner, an error panel, or a blank frame where the pipeline list should be.
Which is precisely why the empty state, and not the page loading, is the proof.

=== Where the session actually lives

Worth noting that the proxy holds a cookie of its own, scoped to the zone the platform lives in, encrypted with its own cookie secret -- seen here in a browser developer console:

++++
<div class="imageblock centered-image">
    <img src="/assets/images/2026-07-24-single-sign-on-for-the-debezium-platform/oauth2-proxy-session-cookie.png" style="max-width:100%;" class="responsive-image" alt="Browser developer tools, Application tab, cookies for https://dmp.demo.1int.io: the _oauth2_proxy cookie holding an opaque 3569-byte value, scoped to domain .demo.1int.io on path /, flagged HttpOnly and Secure, alongside a small i18next session cookie">
</div>
++++

What that cookie is _derived from_ sits one layer up: **Keycloak's own session**, held as a cookie on `auth.demo.contoso.com`.
When the proxy redirected there, Keycloak decided whether the user was already authenticated, and returned an authorization code without asking again if they were.
The proxy then ran its own code exchange and minted its own independent cookie.

The private window is the control that proves it.
Same URL, same proxy, same everything except a browser profile carrying no Keycloak cookie -- and the login form appears.
Nothing about the platform changed; the only thing missing was the session at the identity provider.

Two things follow, and they are the reason to build it this way:

* **Revocation works.** End the session in Keycloak and access is gone at the next redirect. A cookie the application minted for itself would keep working until it expired.
* **It scales past one host.** Putting a second UI behind its own proxy means registering a second client, not widening a cookie's reach -- and that second host inherits the same Keycloak session, so the user is not asked to log in twice.

The sign-on is single.
The sessions, deliberately, are not.
