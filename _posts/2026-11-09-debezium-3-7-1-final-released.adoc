We're pleased to announce **Debezium 3.7.1.Final**, the first maintenance release of the 3.7 series, focused on stability and reliability.

This release resolves a number of cases where change events could be skipped or duplicated after a connector restart, and it restores pieces of the Debezium Server distribution that went missing in 3.7.0.Final.
It also brings updated database drivers that address several recently published CVEs.
If you use the Oracle connector, be sure to review the breaking changes before upgrading.

Read on for the full details!

== Breaking changes

With any new release of software, there can be breaking changes.
This release is no exception, so let's discuss the major changes you should be aware of before upgrading to **Debezium 3.7.1.Final**

=== Debezium for Oracle

==== Snapshot locks are held for the whole snapshot

The Oracle connector now holds its table locks until the snapshot has finished reading the data, rather than releasing them once the table schemas were captured.
This protects an initial snapshot from most schema changes made while it runs, which is the usual cause of an `ORA-01466` failure that forces the snapshot to start over.

The `snapshot.database.errors.max.retries` property has been removed, because retrying could never succeed.
The connector reads every table at the position it recorded when the snapshot began, and Oracle rejects that query for as long as the table's definition is newer than that position.
Each retry therefore failed in exactly the same way.

With the default `snapshot.locking.mode` of `shared`, other sessions can still read and write the captured tables during the snapshot, so most deployments will not notice a difference.
Schema changes that need exclusive access to a table now wait until the snapshot completes.
Some non-blocking schema changes, such as `ALTER TABLE ... ADD COLUMN` on Oracle 23.3 and later, are still allowed by this lock and can still interrupt a snapshot.

For environments where that is a concern, a new `extended` locking mode prevents all schema changes on the captured tables.
The trade-off is that writes to those tables are also blocked until the snapshot completes, so it is best suited to snapshots taken in a maintenance window.
The connector waits up to `snapshot.lock.timeout.ms` for each table lock, and fails the snapshot if a lock cannot be obtained in that time.

[source,properties]
----
snapshot.locking.mode=extended
snapshot.lock.timeout.ms=10000
----

When upgrading, remove `snapshot.database.errors.max.retries` from your connector configuration if you had set it.
If you run schema changes against captured tables on a schedule, plan them outside of the initial snapshot.
You can also set `snapshot.mode` to `no_data` and load the existing data with an incremental snapshot, which does not rely on a single point-in-time read.
(https://github.com/debezium/dbz/issues/2787[dbz#2787])

=== Debezium Core

==== MariaDB Connector/J upgraded to 3.5.11

The MariaDB driver that ships with the MariaDB connector and the JDBC sink has been upgraded to 3.5.11.
This picks up the fixes for CVE-2026-119210, CVE-2026-119276, CVE-2026-119280, and CVE-2026-119281, which were published at the end of October.

The new driver version also fixes a defect where the database password could be exposed through the connection URL reported by the driver.
No configuration changes are required.
(https://github.com/debezium/dbz/issues/2998[dbz#2998])

[id="new-features-and-improvements-debezium-mongodb"]
=== Debezium for MongoDB

==== MongoDB driver upgraded to 5.14

The MongoDB connector now ships with version 5.14.0 of the MongoDB Java driver, up from 5.9.2.
The upgrade keeps the connector current with the driver's latest fixes and requires no configuration changes.
(https://github.com/debezium/dbz/issues/3022[dbz#3022])

[id="new-features-and-improvements-debezium-mysql"]
=== Debezium for MySQL

==== MySQL Connector/J upgraded to 26.10.0

The MySQL driver that ships with the MySQL connector and the JDBC sink has been upgraded from 9.1.0 to 26.10.0.
The previous version was affected by CVE-2025-30706, and the newest 9.x driver carries several more recent CVEs, so the upgrade moves directly to the 26.x line.

Most deployments need no changes, but there are two things worth knowing.
Starting with 26.7.0, the driver's release notes list MySQL Server 8.4 and later as supported.
MySQL 8.0 is no longer in that documented range, although the driver does not reject it and the connector's tests continue to pass against it.

The driver also now requires SSL keystores to be local files.
The connector's own SSL settings already work this way, so this only matters if you pass custom `+driver.*+` properties that point at a remote keystore URL.
(https://github.com/debezium/dbz/issues/3015[dbz#3015])

[id="new-features-and-improvements-debezium-oracle"]
=== Debezium for Oracle

==== Column reselection uses the physical standby

When the Oracle connector streams from a physical standby, the `ReselectColumnsPostProcessor` now runs its queries against the standby as well.
Previously those queries always went to the primary database, even though the standby was already handling everything else for streaming.

This keeps the extra read load of reselecting column values off the primary, which is often the reason for capturing from a standby in the first place.
The behavior applies automatically when `capture.mode` is set to `physical_standby`, and other capture modes continue to use the primary connection.
(https://github.com/debezium/dbz/issues/2444[dbz#2444])

[id="new-features-and-improvements-debezium-server"]
=== Debezium Server

==== Apache Pulsar client upgraded to 4.2.5

Debezium Server now packages version 4.2.5 of the Apache Pulsar client, up from 4.2.1.
The older client bundled Bouncy Castle 1.84 libraries that security scanners flagged for a number of CVEs, including certificate validation issues.
The new client bundles Bouncy Castle 1.86, which resolves those findings for the Pulsar libraries.

The Pulsar sink's configuration and runtime behavior are unchanged.
(https://github.com/debezium/dbz/issues/2799[dbz#2799])
