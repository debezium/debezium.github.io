We're pleased to announce the release of *Debezium 3.7.0.Alpha2*, the second preview release in the 3.7 series, packed with new features and important changes across the platform.

This release introduces an incubating TiDB connector, adds retry and dead letter queue support for the JDBC sink, and improves Debezium Server with a proper readiness probe.
On the Oracle side, the OpenLogReplicator client is now non-blocking and continuous mining for Oracle 12 has been removed.
The Debezium Platform UI now surfaces pipeline failures directly, and several other connectors receive important fixes and improvements.

Let's take a closer look at all these changes and more; read on for the full details!

== Breaking changes

With any new release of software, there can be breaking changes.
This release is no exception, so let's discuss the major changes you should be aware of before upgrading to *Debezium 3.7.0.Alpha2*

=== Debezium for Oracle

==== Continuous mining removed for Oracle 12

Oracle deprecated continuous mining in Oracle 12c and permanently removed it in 19c, and Debezium previously only supported it on a best-effort basis for Oracle 12c deployments.
This feature has now been removed entirely from the Oracle connector.

If you are currently using continuous mining with Oracle 12c, you will need to switch to a different capture mode before upgrading.
The LogMiner adapter remains the recommended approach for Oracle change data capture.
(https://github.com/debezium/dbz/issues/1953[dbz#1953])

=== Debezium for Cassandra

==== Removal of Cassandra 3 connector

Cassandra 3 has reached end of life, and the Cassandra 3 connector has been removed from Debezium.
As part of this change, the Guava dependency has been upgraded to version 32.0.0, which is incompatible with Cassandra 3 but aligns with the requirements of Cassandra 4 and later.

If you are currently using the Cassandra 3 connector, you will need to upgrade to Cassandra 4 or later before moving to this release.
The Cassandra 4 and Cassandra 5 connectors remain fully supported.
(https://github.com/debezium/dbz/issues/2273[dbz#2273])

=== Debezium for Db2

==== LOB column serialization support

The Db2 connector now correctly serializes LOB columns (CLOB, BLOB, and DBCLOB) during both snapshot and streaming.
Previously, CLOB and DBCLOB columns emitted internal driver handle strings during snapshots and null values during streaming, while BLOB columns always produced null values.

With this fix, text-based LOB columns are emitted as their string content, and binary LOB columns are serialized according to the configured `binary.handling.mode` (e.g., base64).
(https://github.com/debezium/dbz/issues/2304[dbz#2304])

[id="new-features-and-improvements-debezium-mariadb"]
=== Debezium for MariaDB

==== Support for InnoDB-based binary logs

MariaDB 12.3 introduced a new InnoDB-based binary log storage format designed for improved throughput and crash recovery.
The MariaDB connector and binary log client have been updated to ensure compatibility with this new format, allowing Debezium to capture changes from MariaDB deployments that use InnoDB-based binary logging.
(https://github.com/debezium/dbz/issues/2259[dbz#2259])

==== Correct boolean conversion for negative TINYINT(1) values

The `TinyIntOneToBooleanConverter` now correctly treats negative `TINYINT(1)` values as `true`, matching MySQL's own semantics where any non-zero value is considered true.
Previously, negative values such as -1 or -128 were incorrectly converted to `false` because the converter used a greater-than-zero check instead of a not-equal-to-zero check.
(https://github.com/debezium/dbz/issues/2260[dbz#2260])

[id="new-features-and-improvements-debezium-oracle"]
=== Debezium for Oracle

==== Non-blocking OpenLogReplicator client

The OpenLogReplicator client has been converted from a blocking to a non-blocking architecture.
This improves the responsiveness of connector shutdown operations, as the client can now promptly exit its read loop when a stop is requested rather than waiting for the socket read timeout to expire.
(https://github.com/debezium/dbz/issues/1198[dbz#1198])

==== Snapshot-only mode no longer requires archive log configuration

The Oracle connector no longer validates archive log destination configuration when running in snapshot-only mode (`initial_only`).
Previously, the archive log validation ran unconditionally at startup, causing snapshot-only runs to fail on managed deployments like Oracle Autonomous Database where the archive log configuration is hidden from the connector user.

This change makes snapshot-only deployments simpler, particularly in cloud-managed Oracle environments where archive log destinations are controlled by the service provider.
(https://github.com/debezium/dbz/issues/2305[dbz#2305])

[id="new-features-and-improvements-debezium-sqlserver"]
=== Debezium for SQL Server

==== Support for specifying capture instance

The SQL Server connector now allows users to specify which CDC capture instance to use when multiple capture instances exist for the same table.
This is useful when different capture instances track different column subsets, preventing unwanted schema changes in downstream topics when a new capture instance is created.
(https://github.com/debezium/dbz/issues/960[dbz#960])

[id="new-features-and-improvements-debezium-jdbc"]
=== Debezium JDBC sink

==== Retry and dead letter queue support

The JDBC sink connector now supports automatic retries with configurable backoff when encountering transient database errors, along with dead letter queue (DLQ) integration for records that fail after all retry attempts.
Previously, any SQL exception would immediately stop the sink task, requiring manual intervention to restart.

This makes JDBC sink deployments significantly more resilient in production environments where transient database connectivity issues or constraint violations can occur.
(https://github.com/debezium/dbz/issues/984[dbz#984])

==== Sink support for PostgreSQL enum columns

The JDBC sink connector now correctly handles writing to PostgreSQL enum columns.
Previously, sinking to a PostgreSQL enum column would fail with a type mismatch error because the generated SQL did not include the necessary type cast.
The connector now detects enum column types via the propagated source type metadata and applies the appropriate PostgreSQL cast.
(https://github.com/debezium/dbz/issues/1344[dbz#1344])

==== Record value and header primary key modes now support deletion

The JDBC sink connector now supports row deletion when using `record_value` or `record_header` primary key modes.
Previously, deletion was only supported with `record_key` mode.
This provides more flexibility for pipelines where the primary key is derived from the record value or headers rather than the Kafka record key.
(https://github.com/debezium/dbz/issues/1421[dbz#1421])

[id="new-features-and-improvements-debezium-platform"]
=== Debezium Platform

==== Connection validation for Azure Event Hub

The Debezium Platform now includes a connection validator for Azure Event Hub destinations.
This allows users to verify their Event Hub connection settings directly from the Platform UI before creating a pipeline, providing immediate feedback on connectivity issues.
(https://github.com/debezium/dbz/issues/1088[dbz#1088])

==== Complete CLI platform subsystem

The Debezium JBang CLI now includes a complete platform management subsystem with several new commands (https://github.com/debezium/dbz/issues/2176[dbz#2176]):

`pipeline signal`:: Send signals to running pipelines (e.g., stop snapshot, force re-read).
`source verify-signals`:: Verify that signaling is correctly configured for a source.
`config set/get`:: Manage CLI settings such as the platform URL.
`switch`:: Switch between multiple platform environments (development, staging, production) without passing connection details on every command.

image::https://github.com/user-attachments/assets/9b128c24-f2b2-4a72-bc21-4206dff837b9[width=100%,align="center"]

==== Pipeline failure visibility

The Debezium Platform UI now displays pipeline deployment failures with their error details directly in the interface.
Users can see what went wrong when a pipeline fails to deploy and trigger a re-deployment from the UI, eliminating the need to check server logs for troubleshooting.
(https://github.com/debezium/dbz/issues/2261[dbz#2261])

video::https://github.com/user-attachments/assets/fb092df2-5531-44b8-bfda-58c8f125a243[width=100%,align="center"]

==== Optional OIDC bearer token authentication

The Debezium Platform conductor now supports optional OIDC bearer token authentication for its API endpoints.
When configured, all `+/api/*+` endpoints require a valid bearer token, while health check endpoints (`+/q/*+`) remain open.

This enables integration with identity providers like Keycloak for securing Platform API access in production environments.
(https://github.com/debezium/dbz/issues/2306[dbz#2306])

[id="new-features-and-improvements-debezium-server"]
=== Debezium Server

==== JDBC sink consumer delegates to the JDBC sink connector

Debezium Server now delegates all JDBC consumer operations to the JDBC sink connector, minimizing future maintenance and inheriting all future improvements to the sink connector out of the box.
(https://github.com/debezium/dbz/issues/2265[dbz#2265])

==== Readiness probe for health checks

Debezium Server now includes a proper readiness health check that reflects whether the connector is actually ready to process changes.
Previously, the `/q/health/ready` endpoint always returned UP as soon as the Quarkus application started, regardless of the connector's actual state.

The new readiness probe checks the engine's polling status, giving orchestration tools like Kubernetes an accurate signal for routing traffic.
(https://github.com/debezium/dbz/issues/2393[dbz#2393])

[id="new-features-and-improvements-debezium-cockroachdb"]
=== Debezium for CockroachDB

==== Documentation and warnings for static capture sets

The CockroachDB connector now documents that `table.include.list` patterns are resolved once at startup, meaning tables created after the connector starts are not automatically captured.
Additionally, an `execute-snapshot` signal targeting a table outside the running capture set now produces a clear warning instead of silently succeeding without emitting any rows.
This aligns the CockroachDB connector's behavior with all other Debezium connectors.
(https://github.com/debezium/dbz/issues/2392[dbz#2392])

[id="new-features-and-improvements-debezium-informix"]
=== Debezium for Informix

==== Updated to Informix JDBC driver v15.0.1.4

The Informix connector now ships with the latest Informix JDBC driver version 15.0.1.4, bringing driver-level bug fixes and compatibility improvements.
(https://github.com/debezium/dbz/issues/2342[dbz#2342])

[id="new-features-and-improvements-tidb-connector"]
=== TiDB Connector

==== Incubating TiDB connector

https://pingcap.com/tidb[TiDB] is an open-source, MySQL-compatible distributed SQL database designed for hybrid transactional and analytical processing (HTAP) workloads.
It is commonly used in scenarios that require horizontal scalability, strong consistency, and high availability across large datasets.

An incubating Debezium connector for TiDB is now available, using Kafka-based change data capture.
This enables users running TiDB to integrate with the broader Debezium ecosystem for real-time data streaming and event-driven architectures.
(https://github.com/debezium/dbz/issues/789[dbz#789])

[id="new-features-and-improvements-debezium-ai-python"]
=== Debezium AI for Python

==== Structured metadata filtering and reactive LangGraph agent

PyDebeziumAI now includes a unified metadata filtering API for vector store adapters, allowing consistent filter syntax across Chroma, PGVector, and Milvus backends.
A new https://github.com/debezium/debezium-ai-python/tree/main/examples/reactive_agent[reactive LangGraph agent example] demonstrates how CDC-driven updates can feed real-time context changes into AI agent decision-making.
(https://github.com/debezium/dbz/issues/2156[dbz#2156])
