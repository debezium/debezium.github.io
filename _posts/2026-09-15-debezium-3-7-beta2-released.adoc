As the leaves start to turn, we're pleased to announce **Debezium 3.7.0.Beta2**, a release that delivers the first official release of the Milvus and SQLite source connectors and the Debezium CLI, alongside new capabilities across the platform, core library, and connectors.

Among the highlights, the Debezium Platform gains alerting, the reselect columns post processor gets a RocksDB-backed cache, a new embeddings transformation supports OpenAI models, and a rework of the JMX `LastEvent` metric rendering delivers improved snapshot throughput.
Debezium Server adds TLS and mutual TLS support for the RabbitMQ Stream sink, and the JDBC sink can now map arrays to SingleStore JSON columns.

Read on for the full details!

== Breaking changes

With any new release of software, there can be breaking changes.
This release is no exception, so let's discuss the major changes you should be aware of before upgrading to **Debezium 3.7.0.Beta2**

=== Debezium for Oracle

==== Savepoint partial rollbacks handled correctly

The Oracle connector handles a rollback to a savepoint by walking back through the buffered events of the transaction and discarding the change that was undone.
Two defects in this process could cause the target to drift out of sync with the source.

First, when LOB support is enabled, the connector consolidates related `INSERT` and `UPDATE` events for the same row, but this consolidation only carried the column values forward and left the merged `INSERT` with a placeholder row identifier.
When the partial rollback arrived, the connector could not find the event to discard, logged a _"Cannot undo"_ warning, and emitted the rolled-back change that looked like a normal change to the target.

Second, when a rollback-to-savepoint event was mined near the end of a LogMiner session for a transaction that had not yet committed, the same rollback could be applied a second time when the transaction's events were re-read in the next mining session.
Depending on the shape of the transaction, this produced either a spurious _"Cannot apply undo change"_ warning or, more seriously, marked an earlier legitimate change such as the original `INSERT` as rolled back and silently dropped it from the change stream.

The connector now preserves the correct row identifier when an `UPDATE` is folded into an `INSERT`, and partial rollbacks are applied idempotently so that a rollback already processed is never re-applied in a later mining session.
Together these ensure the connector emits exactly the changes that survived the rollback.

No configuration changes are required.
After upgrading, changes that were rolled back to a savepoint no longer reach downstream consumers, changes that were previously dropped in this scenario are emitted correctly, and the associated warnings no longer appear in the connector log.
Any downstream compensation put in place to filter the spurious events can be removed.
(https://github.com/debezium/dbz/issues/1422[dbz#1422], https://github.com/debezium/dbz/issues/1914[dbz#1914])

=== Debezium Core

==== Embeddings SMT for OpenAI models

Debezium's AI embeddings transformations gain a new module for OpenAI.
Built on the LangChain4j OpenAI integration, the transformation sends the configured text field of each change event to an OpenAI embedding model and adds the resulting vector to the record.

This lets users who already standardize on OpenAI models enrich their change events with embeddings directly in the pipeline, alongside the existing embedding providers, without any custom code.
(https://github.com/debezium/dbz/issues/1067[dbz#1067])

==== Dedicated metric for snapshot read events

Snapshot events are emitted with the `READ` operation, which previously had no dedicated counter in Debezium's event metrics.
As a result, monitoring dashboards in the Debezium Platform or in Prometheus showed zero create, update, and delete events while a snapshot was actively processing rows, making snapshot throughput effectively invisible.

Debezium now exposes a `TotalNumberOfReadEventsSeen` metric through JMX, following the same pattern as the existing create, update, and delete counters.
The OpenTelemetry JMX configuration generated by the Debezium Operator maps the new attribute as a `read` event type, and the Debezium Platform gains a snapshot event count rate panel built on it.
Note that the counter covers both initial and incremental snapshot events.
(https://github.com/debezium/dbz/issues/2167[dbz#2167])

==== RocksDB cache for the reselect columns post processor

The `ReselectColumnsPostProcessor` re-queries the source database to replace unavailable value placeholders in events for TOASTed or LOB columns that the database does not include unless the column actually changed.
An earlier improvement added a bounded, heap-based cache of previously reselected values to reduce the number of queries against the database.

This release introduces a standard cache contract that any storage backend can implement, and ships a RocksDB-based implementation out of the box.
Cached column values can now live in persistent, disk-backed storage rather than being limited by JVM heap, allowing much larger working sets to be served from the cache and further reducing round trips to the source database.
(https://github.com/debezium/dbz/issues/2435[dbz#2435])

==== Faster JMX LastEvent metric rendering improved snapshot throughput

The common pipeline metrics render a JSON summary of every dispatched change event to populate the JMX `LastEvent` attribute.
Previously, each rendering constructed a brand new Jackson `ObjectMapper`, a cost paid for every snapshot and streaming event across all source connectors and both the Kafka Connect and Debezium Server runtimes.

The rendering now uses jackson-core's stateless `JsonStringEncoder`, which is roughly seven times faster and allocates about five times less memory per event.
In end-to-end snapshot benchmarks of a one million row table, this translated to up to 47% higher throughput on PostgreSQL and 38% on MySQL, with allocation per row roughly halved and noticeably fewer garbage collections and lower CPU usage.
The rendered output is byte-identical to before and no new dependency is introduced.
(https://github.com/debezium/dbz/issues/2492[dbz#2492])

=== Debezium for MongoDB

==== Date type keys in incremental snapshots

Incremental snapshots of MongoDB collections now support collections whose key is a BSON Date type.
This continues the ongoing work to broaden the key types that can be used to chunk and resume MongoDB incremental snapshots, so collections keyed by dates no longer need a workaround to be captured incrementally.
(https://github.com/debezium/dbz/issues/765[dbz#765])

[id="new-features-and-improvements-debezium-mysql"]
=== Debezium for MySQL

==== Accurate binlog positions beyond 4GB

The `log_pos` field in a MySQL binlog event header is an unsigned 32-bit value, yet a binlog file can legitimately grow beyond 4GB because MySQL never splits a transaction across files.
Once a file crosses that boundary the server truncates the position it writes into the header, and the binlog client previously trusted that wrapped value.
Every position the connector exposed past 4GB was therefore wrong, even though streaming itself continued: committed offsets, the `source.pos` field of emitted events, the reconnect position, and the `BinlogPosition` metric.
On servers without GTIDs, a restart from a wrapped offset could land in the middle of an unrelated event and fail with the misleading _"log event entry exceeded max_allowed_packet"_ error.

The binlog client now tracks the real 64-bit position itself, anchored on the 8-byte position carried by the ROTATE event and advanced by the length of each event read from the stream.
Behavior for positions below 4GB is unchanged.
Above it, offsets and `source.pos` now report the real position, consistent with what `SHOW BINARY LOGS` and `mysqlbinlog` report, and positions compare in the correct order.
This change is complemented by the fix for the schema history comparator in https://github.com/debezium/dbz/issues/2506[dbz#2506].

One limitation remains: the binlog dump protocol itself only carries a 32-bit start position, so restarting from a position beyond 4GB on a server without GTIDs is still not possible.
Tracking the real position removes the silent corruption and lays the groundwork for handling that case explicitly.
(https://github.com/debezium/dbz/issues/2508[dbz#2508])

[id="new-features-and-improvements-debezium-jdbc"]
=== Debezium JDBC sink

==== SingleStore ARRAY to JSON mapping

The JDBC sink connector can now write Kafka Connect `ARRAY` schema values into SingleStore `JSON` columns.
Array values arriving from Kafka topics are serialized to JSON on the way into the target column, so users no longer need a custom transformation or additional pre-processing to sink array fields into SingleStore.
(https://github.com/debezium/dbz/issues/2567[dbz#2567])

[id="new-features-and-improvements-debezium-operator"]
=== Debezium Operator

==== Support for priorityClassName in the DebeziumServer pod template

The `DebeziumServer` custom resource's pod template already exposed affinity, node selectors, tolerations, security context, and image pull secrets, but not a priority class.
The pod template now accepts `priorityClassName`, so a Kubernetes priority class can be assigned to Debezium Server pods managed by the operator, allowing scheduling and preemption behavior to be controlled in the same way as other workloads in the cluster.
(https://github.com/debezium/dbz/issues/2251[dbz#2251])

==== Image pull secrets for the operator Helm chart

The operator Helm chart already allowed the operator image to be overridden, but offered no way to attach an image pull secret to the operator pod itself.
Deployments in clusters that cannot pull from public registries had to fork the chart or maintain hand-written manifests.

The chart now supports configuring `imagePullSecrets` for the operator deployment, completing the picture alongside the pull secret support that the `DebeziumServer` resource already provided for server pods.
(https://github.com/debezium/dbz/issues/2461[dbz#2461])

[id="new-features-and-improvements-debezium-platform"]
=== Debezium Platform

==== Improved pipeline log viewer

The pipeline log screen in the Debezium Platform has received a series of usability improvements aimed at making large, fast-moving logs easier to work with.
These include a proper loading state, the ability to pause and resume live log updates, and filtering by log level such as error, warning, info, and debug, so users can focus on the entries that matter when diagnosing a pipeline.
(https://github.com/debezium/dbz/issues/1380[dbz#1380])

==== Image pull secrets and pull policy for all Helm chart images

The Debezium Platform Helm chart previously only allowed the image pull policy to be overridden for the conductor and stage images, and had no support for image pull secrets at all.

The chart now supports configuring `imagePullPolicy` for every image it deploys, including the descriptors and Debezium Server images, and introduces `imagePullSecrets` support with a hybrid model: a chart-level setting applies to all containers by default, and an optional per-component setting overrides it where needed.
This makes the platform straightforward to deploy from private registries, in air-gapped environments, and across dev, staging, and production clusters with differing pull policies.
All new fields are optional, so existing values files continue to work unchanged.
(https://github.com/debezium/dbz/issues/1851[dbz#1851])

==== User-friendly names and descriptions for Debezium Server sink connectors

When listing Debezium Server sink connectors, the platform previously returned fully qualified implementation class names such as `io.debezium.server.kinesis.KinesisChangeConsumer` as both the connector name and description.
Sink connectors now carry proper, human-readable names and descriptions, making them far easier to identify and select in the Platform UI.
(https://github.com/debezium/dbz/issues/1919[dbz#1919])

video::https://github.com/user-attachments/assets/9014f662-5d19-4a26-8d1a-c73df8d19704[width=100%,align="center"]

==== MongoDB signal data collection verification

The conductor's signal verification endpoint, used by the `debezium source verify-signals` CLI command, lets users confirm that a signal data collection is correctly set up for a source connection.
For MongoDB connections this check was previously a stub that always reported success, so a misconfigured or non-existent signal collection went unnoticed.

The verification is now fully implemented for MongoDB sources, checking that the signal collection actually exists in the configured namespace.
This brings MongoDB in line with the behavior already available for relational connections and makes the verification results trustworthy across all supported sources.
(https://github.com/debezium/dbz/issues/2270[dbz#2270])

==== Alerting support

The Debezium Platform has offered pipeline monitoring through a set of predefined panels, but monitoring was passive: users had to watch dashboards to notice problems.
Alerting closes this gap by letting users define threshold-based rules against existing monitoring panels and receive notifications when those thresholds are breached.

Alert rules are built by selecting a monitoring panel, a comparison operator, a numeric threshold, and an optional duration to suppress transient spikes.
Rules are evaluated globally across all pipelines, and each alert identifies which pipeline triggered it.
Alerts follow a pending, firing, and resolved lifecycle with incident tracking, support critical, warning, and info severity levels, and can be delivered via email over SMTP or an HTTP webhook in addition to always-on in-app visibility.
A queryable, filterable alert history with configurable retention rounds out the feature.

The UI gains a new Alerts section with Rules, Channels, and History pages, plus a global alert badge in the header.
Alert grouping, silencing, escalation policies, and repeat notifications are out of scope for this initial implementation.
(https://github.com/debezium/dbz/issues/2314[dbz#2314])

==== Alerts in the Stage UI

The Stage user interface now surfaces alerts, giving users in-app visibility into alert rules, notification channels, and alert history.
This is the user-facing counterpart to the alerting support introduced in dbz#2314.
(https://github.com/debezium/dbz/issues/2450[dbz#2450])

==== Table explorer in the incremental snapshot action

Triggering an incremental snapshot from the Platform Stage previously required typing collection names by hand.
The incremental snapshot action now embeds the same table explorer component already used in the source configuration, so users can browse and select the tables or collections to snapshot using the existing collection API rather than entering identifiers manually.
(https://github.com/debezium/dbz/issues/2465[dbz#2465])

The Platform Stage previously only distinguished the failed state for a pipeline.
With the conductor now reporting additional states such as deploying and running, the Stage UI displays the full set of pipeline statuses, giving users a clearer picture of where each pipeline is in its lifecycle at a glance.

=== Debezium Server

==== Connection validator for RocketMQ

The Debezium Platform can now verify connections to Apache RocketMQ before a pipeline is deployed.
A dedicated connection validator, connection type, and schema have been added for RocketMQ, so users get immediate feedback on misconfigured hosts or credentials rather than discovering the problem when the pipeline starts.
(https://github.com/debezium/dbz/issues/1094[dbz#1094])

==== TLS and mTLS support for the RabbitMQ Stream sink

The RabbitMQ Stream sink previously had no way to configure TLS, so connecting to a TLS-enabled stream port failed with a closed connection as the client sent plaintext to the encrypted endpoint.

The `rabbitmqstream` sink now supports TLS and mutual TLS, with configurable trust and client certificate material and hostname verification, bringing it to parity with the TLS support already available in the AMQP-based RabbitMQ sink.
This allows Debezium Server to publish to RabbitMQ Stream clusters that enforce encrypted, certificate-authenticated connections, a common requirement in Kubernetes deployments.
(https://github.com/debezium/dbz/issues/1582[dbz#1582])

[id="new-features-and-improvements-debezium-cli"]
=== Debezium CLI

==== First official release of the Debezium CLI

Until now, creating, managing, and monitoring change data capture pipelines outside of Kafka Connect meant working through the Debezium Platform user interface or its REST API.
With this release, the Debezium CLI has its first official release, giving developers and operators a single command-line entry point for the whole pipeline lifecycle, whether they are iterating locally or automating production workflows.

The CLI is distributed through JBang and is organized around two subsystems.
The platform subsystem talks to a running Debezium Platform and provides commands to list, create, update, and delete pipelines, sources, destinations, connections, and transforms, to stream pipeline logs, send signals, and verify signal configuration, and to switch between multiple platform environments.
The build subsystem lets users scaffold a configuration, assemble a trimmed Debezium Server distribution containing only the connector and sink they need, wrap it in an OCI container image without a Docker daemon, and push the image to a registry.

Together these allow a user to go from an empty terminal to a running pipeline without hand-managing JAR files or configuration.
(https://github.com/debezium/dbz/issues/1955[dbz#1955])

==== CockroachDB connector graduates from incubating

The CockroachDB connector has carried an incubating designation since its first release.

[id="new-features-and-improvements-debezium-milvus"]
=== Debezium for Milvus

==== Incubating Milvus source connector

https://milvus.io[Milvus] is an open-source vector database built for storing, indexing, and searching high-dimensional embeddings at scale, and it sits at the heart of many retrieval-augmented generation and semantic search systems.
Debezium has supported Milvus as a sink for some time, and this release adds the other direction: an incubating source connector that captures inserts, updates, and deletes from Milvus collections in real time.

Milvus does not expose a change stream through its API, so the connector reads directly from the internal message queue channels that Milvus publishes every write to, resolving collection schemas through the Milvus metadata API and using etcd checkpoints and timestamp-oracle ordering to provide resumable, correctly ordered events.
Change events carry full schema fidelity, including vector field dimensions, so downstream consumers can replicate embeddings to other stores, keep search indexes in sync, or feed AI pipelines.
The connector supports an initial snapshot of existing collections with a seamless hand-off to streaming, heartbeats, notifications, and metrics.

The connector requires Milvus 2.5 or later deployed with Kafka as the message queue backend.
As an incubating connector, its configuration and behavior may still change in future releases.
(https://github.com/debezium/dbz/issues/2065[dbz#2065])

[id="new-features-and-improvements-debezium-sqlite"]
=== Debezium for SQLite

==== Incubating SQLite source connector

SQLite is the most widely deployed database engine in the world, embedded in browsers, mobile and desktop applications, and a growing number of edge and IoT devices, and increasingly used as a primary application database.
Until now it has been one of the most common sources of data with no standard way to stream its changes, and this release closes that gap with an incubating Debezium source connector for SQLite.

The connector brings Debezium's familiar pipeline to a SQLite database file: an initial snapshot of existing table data followed by continuous streaming of inserts, updates, and deletes.
Because SQLite has no server process or transaction log to tap into, changes are captured through a change data capture log table that database triggers keep up to date, which the connector then reads and translates into standard Debezium change events with the usual envelope and source metadata.
Table and column include and exclude filters and offset-based resume after a restart are supported, and the connector runs against the standard `sqlite-jdbc` driver with no external services required.

As an incubating connector, its configuration and behavior may still change in future releases.
(https://github.com/debezium/dbz/issues/2056[dbz#2056])
