When I started working on migrating Debezium's MySQL connector from the Positive Technologies grammar to Oracle's official MySQL grammar, I honestly thought it would be straightforward.
"_Just replace the grammar files and fix a few tests, right?_"
Well, turns out parsing DDL is like opening a Matryoshka doll, every layer reveals a smaller, even trickier one inside.

Let me walk you through what we did, why we did it, and several interesting challenges we experienced along the way.

+++<!-- more -->+++

== Why does Debezium need to parse DDL?

Before diving into grammars, let's talk about why Debezium needs a DDL parser.

Debezium's MySQL connector reads MySQL's binary log (binlog), a sequential record of every database change.
It transforms these binlog entries into structured change events and streams them for downstream consumers.

When the MySQL connector reads from the binlog, it analyzes row-level changes (inserts, updates, deletes) and here's the catch: the binlog doesn't include the table schema with each event.
It only tells you "_row X in table Y changed_" with an array of column values.
No column names, no types, nothing.

To generate meaningful change events, Debezium needs to know the name and type of each column.
We can't just ask the database for the current schema because the connector can lag behind, and by the time we read an event, the table might have changed.
And hitting the database for schemas every time would add unnecessary load on production.
We need the schema as it was _at that exact point in time_.

The solution?
Parse every DDL statement in the binlog and maintain an in-memory model of how each table's schema evolved over time.
When we encounter an _INSERT_ event, we use the table definition from that moment to generate the right change event.

This is why getting DDL parsing right is critical.
A bug in parsing can cause us to miss a column, get the wrong type, or completely fail to process events.

== The grammar behind the parser

=== What exactly is a grammar?

_A grammar is a formal specification of a language's syntax_.

It defines what's valid and what's not.
You could try parsing SQL with regular expressions, but that seems faster.
SQL has nested structures, context-sensitive keywords, and ambiguous syntax that regex simply can't handle reliably.

In our case, we're talking about _https://github.com/antlr[ANTLR]_ (ANother Tool for Language Recognition), which is a parser generator.
You write grammar rules in a special format (.g4 in our case), and ANTLR generates Java code that can parse text matching those rules.

MySQL Server actually uses _Yacc_ officially for its own parser, with .yy grammar files.
So why didn't Debezium just use that?

The short answer is portability.
_Yacc_ and _Bison_ were designed around C and C++.
They're fast and reliable, but they generate C code.
If you want to use them in Java, you're looking at JNI bindings for example or porting the entire grammar manually.
The syntax is also tightly coupled to C conventions, which makes adaptation harder.

ANTLR, on the other hand, was built with multi-language support from the start.
The same .g4 grammar file can generate parsers for Java, Python, JavaScript, C#, or whatever target you need.
The grammar syntax is cleaner and more declarative.
You can embed Java code directly in the grammar to customize parsing behavior.
And the tooling ecosystem is significantly better, with IDE plugins, parse-tree visualization, and built-in debugging support.

Oracle published an official ANTLR grammar for MySQL specifically to support cross-language parser implementations.
MySQL Workbench, for example, uses these .g4 grammar files for its SQL parsing and syntax highlighting.
That's what we migrated to, and it's actively maintained alongside MySQL releases.

Let's take a look at a simplified example from MySQL's ANTLR grammar:

[source,antlr]
----
createTable
    : CREATE TABLE tableName OPEN_PAR columnDefinition (COMMA columnDefinition)* CLOSE_PAR
    ;

columnDefinition
    : columnName dataType columnConstraint*
    ;

dataType
    : INT
    | VARCHAR OPEN_PAR INT_NUMBER CLOSE_PAR
    | TIMESTAMP (OPEN_PAR INT_NUMBER CLOSE_PAR)?
    ;
----

This defines: a CREATE TABLE statement has a table name, followed by parentheses containing one or more column definitions separated by commas.
Each column has a name, a data type, and optional constraints.

When ANTLR sees `CREATE TABLE users (id INT, name VARCHAR(100))`, it matches these rules and builds a parse tree we can walk through.

=== How grammars are composed

ANTLR grammars have two main parts:

*Lexer grammar* - Defines tokens.
Think of it as the scanner that recognizes individual words and symbols:

[source,antlr]
----
CREATE_SYMBOL  : C R E A T E ;
TABLE_SYMBOL   : T A B L E ;
INT_SYMBOL     : I N T ;
COMMA          : ',' ;
OPEN_PAR       : '(' ;
----

*Parser grammar* - Defines how tokens combine into valid statements.
This is where the actual syntax rules live:

[source,antlr]
----
createTable
    : CREATE_SYMBOL TABLE_SYMBOL tableName ...
    ;
----

MySQL's complete grammar is _massive_.
The Oracle grammar we migrated to has over *3,600* lines in the lexer and *5,400+* lines in the parser, at this moment.
It covers everything from basic CREATE TABLE to advanced features such as window functions, JSON_TABLE, spatial types, and MySQL-specific syntax.
And one important thing should be mentioned here: even though Debezium only really cares about DDL that affects table schemas, we can't just parse half a language.
The parser needs to handle every valid MySQL statement, even the ones we end up ignoring.

The grammar also includes semantic predicates (code that runs during parsing) to handle version-specific features, context-sensitive keywords, and character set introducers.

=== Why we migrated from Positive Technologies to Oracle

Debezium originally used the Positive Technologies MySQL grammar.
The main reason we had to move is that the PT grammar has been https://github.com/antlr/grammars-v4/pull/4443[deprecated] in the grammars-v4 repository in favor of Oracle's official grammar.
On top of that, it accepted SQL that MySQL would actually reject, for example, it let you write `NVARCHAR` without specifying a length, which MySQL doesn't allow.
That meant Debezium could parse invalid DDL and build an incorrect schema without anyone noticing.

Meanwhile, Oracle, which owns MySQL, published an official ANTLR grammar for MySQL.
We maintain our own copy in Debezium, but having the official grammar as our reference changed everything.
When MySQL adds new syntax or fixes parsing edge cases, we have an authoritative source to sync against.
No more guessing.
No more reverse-engineering MySQL's parser from documentation and hoping we got it right.
When we need to pull upstream changes, we're aligning with the same grammar Oracle uses internally, not some community interpretation that might have missed edge cases.

=== How ANTLR works in Debezium

When ANTLR processes a .g4 grammar file, it generates several Java classes.
For MySQL, you get `MySqlLexer` (tokenizes the input), `MySqlParser` (builds the parse tree), and a few base classes for walking that tree.
The question is: how do you actually extract information from the parse tree?

ANTLR gives you two options.
The `Visitor` pattern, which lets you manually walk the tree node by node, it's useful when you're transforming code, but more work than we need here.
We use the `Listener` pattern instead.
ANTLR walks the tree for you and fires events when it enters and exits each rule.
We just hook into the events we care about and extract what we need.
Since we're not rewriting SQL or controlling traversal order, listeners are the natural fit, we want to react to what the parser finds, not drive the walk ourselves.

==== How it works in practice

The main parser (`MySqlAntlrDdlParser`) creates a dispatcher listener that registers specialized listeners for different DDL types:

[source,java]
----
public MySqlAntlrDdlParserListener(MySqlAntlrDdlParser parser) {
    listeners.add(new CreateAndAlterDatabaseParserListener(parser));
    listeners.add(new DropDatabaseParserListener(parser));
    listeners.add(new CreateTableParserListener(parser, listeners));
    listeners.add(new AlterTableParserListener(parser, listeners));
    listeners.add(new DropTableParserListener(parser));
    listeners.add(new RenameTableParserListener(parser));
}
----

When ANTLR walks through the parse tree, it passes events to listeners for each specific statement type.
To make this clearer, let's look at what happens when it parses `CREATE TABLE users (id INT, name VARCHAR(100))`.

First, the `CreateTableParserListener` catches `enterCreateTable()` and creates an empty `TableEditor` for the `users` table:

[source,java]
----
@Override
public void enterCreateTable(MySqlParser.CreateTableContext ctx) {
    TableId tableId = parser.parseQualifiedTableId(ctx.tableName());

    if (parser.databaseTables().forTable(tableId) == null) {
        tableEditor = parser.databaseTables().editOrCreateTable(tableId);
        super.enterCreateTable(ctx);
    }
}
----

The interesting part is what happens next.
As ANTLR walks into each column, `ColumnDefinitionParserListener` fires and does the heavy lifting:

[source,java]
----
@Override
public void enterColumnDefinition(MySqlParser.ColumnDefinitionContext ctx) {
    uniqueColumn = false;
    optionalColumn = new AtomicReference<>();

    resolveColumnDataType(ctx.fieldDefinition().dataType());

    parser.runIfNotNull(() -> {
        defaultValueListener = new DefaultValueParserListener(this, optionalColumn);
        listeners.add(defaultValueListener);
    }, tableEditor);
    super.enterColumnDefinition(ctx);
}
----

It extracts the column name and type, creates a `ColumnEditor`, and, this is the crucial part, registers a nested `DefaultValueParserListener` specifically for that column's default value.
That nesting matters.
If a column has `DEFAULT CURRENT_TIMESTAMP`, the `DefaultValueParserListener` picks it up:

[source,java]
----
private ColumnEditor getColumnEditor() {
    return columnDefinitionListener.getColumnEditor();
}

@Override
public void enterColumnAttribute(MySqlParser.ColumnAttributeContext ctx) {
    if (ctx.DEFAULT_SYMBOL() != null) {
        if (ctx.nowOrSignedLiteral() != null) {
            if (literalCtx.now() != null) {
                getColumnEditor().defaultValueExpression("1970-01-01 00:00:00");
                return;
            }
            if (signed.ulong_number() != null) {
                getColumnEditor().defaultValueExpression(sign + signed.ulong_number().getText());
            }
        }
    }
}
----

Notice that `getColumnEditor()` doesn't hold a direct reference, but instead, it asks the parent listener for the column currently being processed.
I'll come back to why that matters when we get to the multi-column ALTER TABLE bug.

Once all columns are processed, `exitCreateTable()` fires and commits the table:

[source,java]
----
@Override
public void exitCreateTable(MySqlParser.CreateTableContext ctx) {
    parser.runIfNotNull(() -> {
        if (!tableEditor.hasDefaultCharsetName()) {
            tableEditor.setDefaultCharsetName(parser.charsetForTable(tableEditor.tableId()));
        }

        parser.databaseTables().overwriteTable(tableEditor.create());
        parser.signalCreateTable(tableEditor.tableId(), ctx.getParent());
    }, tableEditor);

    tableEditor = null;
}
----

It sets the default charset if needed and saves the table to Debezium's in-memory schema model.
At that point we have a complete picture of `users`, ready to be used when binlog events come in.

*This is the important context for the migration.*
When we switched from the Positive Technologies grammar to Oracle's grammar, the generated Java classes changed.
Method signatures changed.
Parse tree structure changed.
The rule for handling default values in the PT grammar was named differently from that in Oracle's grammar.
Every listener that assumed a specific tree shape or token name had to be updated.
That's where most of our pain during the migration.

== The migration process

As I mentioned earlier, I went into the migration process thinking I'd swap the grammar files, fix a few imports, and be done in a couple of days.
That's not what happened.
The Oracle grammar had different assumptions, different tokenization rules, and it exposed edge cases in our listeners that the PT grammar had quietly ignored.
Every time I fixed one thing, something else broke in a way I didn't expect.

I won't cover every single issue here, there were many, but these are some of the more interesting ones that kept me busy and are worth mentioning.

=== Double quotes vs single quotes

MySQL has a quirk: by default, double quotes (`"`) delimit identifiers like backticks, not strings.
But when `ANSI_QUOTES` mode is enabled, double quotes become string delimiters like in standard SQL.

Old DDL often has things like:

[source,sql]
----
ENGINE "InnoDB"
DEFAULT "some value"
ENUM("option1", "option2")
----

The Oracle grammar strictly enforces standard MySQL syntax, which means single quotes for strings.
We needed a preprocessing layer to normalize double quotes to single quotes, but only for actual string literals, not for identifiers.

Enter the `QuoteNormalizer`:

[source,java]
----
public class QuoteNormalizer {
    private static final Pattern DOUBLE_QUOTED_STRING = Pattern.compile(
        "\"((?:[^\"\\\\]|\\\\.|\"\")*)\"|(`(?:``|[^`])*`)"
    );

    public static String normalize(String ddl) {
        Matcher matcher = DOUBLE_QUOTED_STRING.matcher(ddl);
        StringBuilder result = new StringBuilder();

        while (matcher.find()) {
            if (matcher.group(1) != null) {
                String content = matcher.group(1).replace("'", "''");
                matcher.appendReplacement(result,
                    "'" + Matcher.quoteReplacement(content) + "'");
            } else {
                matcher.appendReplacement(result,
                    Matcher.quoteReplacement(matcher.group(2)));
            }
        }
        matcher.appendTail(result);
        return result.toString();
    }
}
----

This preprocesses the DDL, converting `"value"` → `'value'` but leaving `` `column` `` unchanged.

=== Window function keywords

MySQL 8.0 added window functions like `LAG`, `LEAD`, `RANK`, etc.
These are keywords in window function contexts but valid column names in CREATE TABLE statements:

[source,sql]
----
CREATE TABLE metrics (
    timestamp BIGINT,
    lag INT,              -- LAG as column name
    rank INT              -- RANK as column name
);
----

The Oracle grammar has different keyword categories:

- `reservedKeywords` - Cannot be used as identifiers
- `identifierKeywords` - Can be used as identifiers in most contexts
- `identifierKeywordsUnambiguous` - Can always be used as identifiers

Window function keywords weren't in the identifier rules.
We added them:

[source,antlr]
----
identifierKeywordsUnambiguous
    : ...
    | CUME_DIST_SYMBOL
    | DENSE_RANK_SYMBOL
    | FIRST_VALUE_SYMBOL
    | LAG_SYMBOL
    | LAST_VALUE_SYMBOL
    | LEAD_SYMBOL
    | NTH_VALUE_SYMBOL
    | NTILE_SYMBOL
    | PERCENT_RANK_SYMBOL
    | RANK_SYMBOL
    | ROW_NUMBER_SYMBOL
    ;
----

=== TIMESTAMP precision

MySQL allows precision on temporal types:

[source,sql]
----
CREATE TABLE events (
    created TIMESTAMP(6),    -- 6 fractional seconds
    updated DATETIME(3)      -- 3 fractional seconds
);
----

The PT grammar parser didn't extract this precision.
The Oracle grammar has a separate rule for it:

[source,antlr]
----
typeDatetimePrecision
    : OPEN_PAR INT_NUMBER CLOSE_PAR
    ;
----

We added a handler in our listener:

[source,java]
----
if (dataTypeContext.typeDatetimePrecision() != null) {
    String precisionText = dataTypeContext.typeDatetimePrecision()
        .INT_NUMBER().getText();
    Integer precision = Integer.valueOf(precisionText);
    columnEditor.length(precision);
}
----

=== Multi-column ALTER TABLE

This was subtle.
When parsing:

[source,sql]
----
ALTER TABLE t ADD COLUMN (
    created TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated TIME DEFAULT '08:00'
);
----

Default values were being assigned to the wrong columns.
The `created` column ended up with `updated` 's default value.

The root cause: our `DefaultValueParserListener` held a fixed reference to a `ColumnEditor`.
When the parser moved to the second column, it updated the editor reference in `ColumnDefinitionParserListener`, but `DefaultValueParserListener` still pointed to the first column's editor.

The fix was to make `DefaultValueParserListener` hold a reference to the _parent listener_ and call `getColumnEditor()` dynamically:

[source,java]
----
public class DefaultValueParserListener extends MySqlParserBaseListener {
    private final ColumnDefinitionParserListener columnDefinitionListener;

    private ColumnEditor getColumnEditor() {
        return columnDefinitionListener.getColumnEditor();
    }

    private void handleLiteral(MySqlParser.LiteralContext ctx, String sign) {
        // Always get current editor
        getColumnEditor().defaultValueExpression(value);
    }
}
----

Now it always writes to whichever column is currently being processed.

=== Contributing back: Fixing bugs in the official grammar

One unexpected benefit of migrating to the official grammar was that we could actually improve it.
While running our test suite against the Oracle grammar, I kept hitting cases where valid MySQL syntax was being rejected.
Not edge cases from old DDL dumps, stuff you'd write today that works fine on MySQL 8.0.46 and 9.0.1 but fails in the grammar.

The first one I noticed was `GEOMCOLLECTION`.
MySQL has accepted it as a synonym for `GEOMETRYCOLLECTION` for years, in column types, in `CAST`, in spatial functions.
But the grammar only knew about the long form.
Then I found that charset introducers like `_UTF8MB4'text'` were rejected because the lexer pattern only matched lowercase `[a-z0-9]+`.
Real-world DDL has both cases, and MySQL doesn't care.
Same story with backtick escaping: `` `test``table` `` is how MySQL handles backticks inside identifiers, but the `BACK_TICK_QUOTED_ID` rule didn't recognize the doubled backtick as an escape sequence.

Two more came up during the investigation.
`ALTER EVENT db1.evt RENAME TO db2.evt` failed because the grammar used `identifier` instead of `qualifiedIdentifier` in the `RENAME TO` clause, it didn't account for moving events between databases.
And there was a version predicate that blocked `DEFAULT` in charset/collation contexts for MySQL 8.0.11+, even though `SET CHARSET DEFAULT` works in all MySQL versions.

I could have worked around all of these inside Debezium, but that felt wrong.
The whole point of using an official grammar is that it's correct.
So I https://github.com/antlr/grammars-v4/issues/4826[filed the issues], spun up Docker instances of MySQL 8.0.46 and 9.0.1 to verify each one, and https://github.com/antlr/grammars-v4/pull/4827[submitted a PR] with all five fixes.
It got merged a few days later.

While I was at it, I found another one: `OPTIMIZE TABLES` (plural) was being rejected even though MySQL accepts both singular and plural forms.
That became a https://github.com/antlr/grammars-v4/issues/4833[separate issue] and https://github.com/antlr/grammars-v4/pull/4834[a second PR], also merged.

This is one of the things I like about working with an official grammar maintained on a public repo.
When you find a bug, you can fix it for everyone, not just patch it locally and move on.

== Looking back

Looking back, this migration was way more work than I expected.
But I'm glad we did it.

The biggest thing I took away is that strictness is your friend.
The PT grammar is more "open", it would happily parse SQL that MySQL itself would reject.
That feels convenient until you realize it means Debezium could silently build incorrect schemas.

I also learned that most of what broke wasn't actually about the grammar.
It was about assumptions baked into our listeners, things like how default values are resolved, or which keywords can double as identifiers.
The PT grammar had its own quirks, and our code had quietly adapted to them over the years.
Switching grammars just made those assumptions visible.

The `QuoteNormalizer` was a nice reminder that sometimes a simple preprocessing step saves you from polluting the grammar with special cases.
Real-world DDL is messy, and trying to handle every quirk inside the grammar itself would have been painful.

*Was it worth the effort?*
Absolutely.
Debezium's MySQL connector now parses DDL the same way MySQL does.
When MySQL adds new syntax, we have an official reference to sync against.
And we went from a grammar we had to guess about to one we can actually trust.

To put it in numbers, we started at 19% test pass rate and ended at 100% on all enabled tests.
Every core DDL parsing scenario that Debezium relies on in production is now covered and passing against the Oracle official grammar.
