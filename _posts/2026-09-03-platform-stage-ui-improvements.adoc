The https://debezium.io/documentation/reference/stable/operations/debezium-platform.html[Debezium Platform] UI gives you a central place to design pipelines, configure sources, transforms, and destinations, and keep an eye on what is running.
Over the last few preview releases, we have shipped improvements that make that work faster and clearer, with less need to leave the UI to look something up.

This post walks through four of those changes:

* xref:doc-access[Quick access to documentation from inside Debezium Platform UI]
* xref:pipeline-status[Pipeline status, failure feedback, and restart]
* xref:transform-descriptors[Transform configuration driven by component descriptors]
* xref:export-server-config[Exporting a Debezium Server configuration from an existing pipeline]


+++<!-- more -->+++

[id="doc-access"]
== Documentation where you are working

Debezium has a lot of configuration, and the right answer is often a specific section of the docs.
You should not have to leave UI, search the documentation site, and try to land on the page that matches the screen you were just looking at.

Platform UI now opens the relevant documentation section based on where you are in the UI: sources, destinations, transforms, pipelines, connections, and so on.
The mapping is contextual, so for example PostgreSQL source takes you to relevant section in the PostgreSQL connector documentation rather than a generic overview.

[id="pipeline-status"]
== Pipeline status, failure feedback, and restart

Until recently, Debezium Platform did not surface pipeline deployment status.
If a deploy failed, the UI looked much as it did when things were fine, and the actual error lived in the server logs.

The Debezium platform now tracks pipeline status and exposes it on the pipeline API, including an error message when something goes wrong.
Platform UI shows that status on the pipeline, so you can see where things stand without leaving the UI:

* *Deploying* -- a create or update has been requested and is waiting for confirmation
* *Running* -- the pipeline is up
* *Failed* -- the pipeline did not start, or it exited unexpectedly

When the pipeline is *Failed*, you get an access to the detailed error message, and a restart control that redeploys from within the UI.

In addition, the Actions and Monitoring tabs are disabled when the pipeline has failed, since those tabs aren't meaningful until it is running again.

[id="transform-descriptors"]
== Transforms driven by component descriptors

Sources and destinations in Debezium Platform already build their configuration forms from https://github.com/debezium/debezium-design-documents/blob/main/DDD-13.md#ddd-13-debezium-component-descriptors[component descriptors], as Mario described in the https://debezium.io/blog/2026/07/10/debezium-platform-status-update/[mid-year Platform update].
Transforms were the remaining piece still backed by a static catalog in the frontend.

That is no longer the case.
Debezium Platform now loads available SMTs from the catalog API (`/api/catalog`) and renders each transform from its descriptor, the same way it already does for connectors.

That means:

* Newly registered transforms show up in the UI without a frontend update
* Configuration fields, types, defaults, and validation come from the descriptor instead of a hard-coded form
* Predicates are selected and configured from the catalog as well, including variant selection

When you create or edit a transform you get a grouped, searchable typeahead instead of a flat static list.
SMTs are organized into categories such as *Debezium SMT*, *Connector-specific*, *Kafka Connect SMT*, *AI*, and *Other*.
After you pick a type, the form is schema-driven: related settings are grouped into sections with jump links, so you can move through a long configuration without scrolling blindly.

Connector-specific transforms (`io.debezium.connector.*`) are only enabled when they match the source already selected on the pipeline, and the Transform node in the pipeline designer stays disabled until a source is chosen.

[id="export-server-config"]
== Generate Debezium Server configuration from a pipeline

Earlier we added the ability to *import* an existing Debezium Server `application.properties` file into Debezium Platform UI and turn it into a pipeline.
That is still the fastest way to onboard a server you already run; see https://debezium.io/blog/2025/09/15/debezium-platform-smart-editor/[Simplifying pipeline creation with existing Debezium configurations].

The other direction is just as useful.
If you designed the pipeline in the Platform UI, you may still want a standard Debezium Server configuration for a host-based deployment, a local test, or to share the equivalent `application.properties` with someone not using the Platform.

You can now download that configuration from an existing pipeline in Platform UI.
Passwords, secrets, and credentials are redacted in the generated file, so you can share or store it without leaking sensitive information.
Predicates that are not actually configured are omitted, so the file is valid Debezium Server configuration rather than a dump of empty objects.

A downloaded file looks like a normal Debezium Server `application.properties`:

[source,properties]
----
debezium.source.connector.class=io.debezium.connector.postgresql.PostgresConnector
debezium.source.topic.prefix=inventory
debezium.source.plugin.name=pgoutput
debezium.source.database.hostname=postgresql
debezium.source.database.port=5432
debezium.source.database.user=debezium
debezium.source.database.password=********
debezium.source.database.dbname=debezium
debezium.source.schema.include.list=inventory

debezium.sink.type=kafka
debezium.sink.kafka.producer.bootstrap.servers=dbz-kafka-kafka-bootstrap:9092

debezium.transforms=unwrap
debezium.transforms.unwrap.type=io.debezium.transforms.ExtractNewRecordState
debezium.transforms.unwrap.add.fields=op
----

Together with the earlier import path, you can move configuration in both directions: Server to Debezium Platform, and Debezium Platform back to Server.
