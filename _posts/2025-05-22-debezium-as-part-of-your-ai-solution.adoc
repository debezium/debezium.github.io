One question that we encountered recently is how to effectively integrate change data capture (CDC) with AI workloads — particularly for scenarios in which critical organizational knowledge is not publicly available.
To help you to take advantage of your internal data, Debezium 3.1 introduces AI-focused features such as the Embeddings SMT and the Milvus sink, which you can combine to supply inputs to an LLM.  
You can read more about these enhancements in the https://debezium.io/blog/2025/04/02/debezium-3-1-final-released/[Debezium 3.1 release notes].

== Introduction

In this post, we'll show how Debezium, Milvus, and Ollama can work together to form a Retrieval-Augmented Generation (RAG) pipeline.
By capturing changes from a relational database, enriching them with vector embeddings, and enabling similarity search across these vectors, you can build AI-driven applications that are powered by up-to-date, domain-specific knowledge.

Let's look at an example that illustrates how you can use Debezium to enrich your AI applications with knowledge captured from experts within your organization.

Suppose that our organization introduces a new AI-driven application that is backed by an LLM.
To enrich and extend the language model, we want to take advantage of internal organizational knowledge that is stored in text documents in a PostgreSQL database.
Whenever users within the organization interact with the AI application, we want to make sure that its responses are informed by the most current local knowledge.
Because the local knowledge that is stored in the PostgreSQL database is in constant flux, with documents being added, updated, or withdrawn to comply with regulatory requirements, we need a solution that has the agility to keep up with these changes. 

The common solution to address this problem is to implement Retrieval-Augmented Generation (RAG).
This post demonstrates how to use Debezium to build a CDC-fed RAG system that uses the following components:

* A PostgreSQL database for data storage
* Milvus vector database
* Debezium Server to feed Milvus from PostgreSQL
* A local https://ollama.com/[Ollama] hosted LLM
* A Java application that interacts with the LLM and uses RAG to provide prompt context

== What is RAG (Retrieval-Augmented Generation)?

Retrieval-Augmented Generation (RAG) is an AI technique that combines information retrieval with generative models to produce more accurate and contextually relevant responses.
Instead of relying solely on a model's internal knowledge, RAG pipelines retrieve relevant documents or data from an external source (like a vector database) and use that information to enrich the model's responses.
In our scenario, Debezium, Milvus, and Ollama work together to form a RAG workflow: data changes are captured and vectorized, stored in Milvus, and then retrieved to augment LLM outputs with up-to-date, domain-specific information.

== What is Debezium Server?

https://debezium.io/documentation/reference/3.1/operations/debezium-server.html[Debezium Server] is a Debezium implementation that you can use to stream change events from databases to various sinks without the need to deploy a Kafka cluster.
It provides a lightweight way to consume CDC events and forward them to destinations from which they can be consumed by other applications.
Debezium Server also supports the use of Kafka Connect single message transformations within its processing pipeline.

== What is Milvus?

Milvus is a specialized vector database designed for similarity search and AI-heavy workloads.
Whether it's product recommendations, image search, or any other use case that relies on fast vector retrieval, Milvus is built for that.
A vector database and fast vector retrieval is the heart of any RAG solution.
The vector database stores so called *embeddings* - vector representations of the data that can be used for tasks like similarity search or clustering.
Based on similarities between a prompt and the stored data, the AI application extends the context of the prompt.

=== Why Milvus as a Sink?

For applications where you need up-to-date vector representations of your data, pushing changes from a transactional database into Milvus makes a lot of sense.
By using Milvus, not only can you keep your AI models in sync with operational data, you can also offload similarity search to a system that is built for it.

=== How Debezium Milvus Sink Works

A typical deployment of Milvus sink uses the following workflow:

* The Debezium connector captures changes from a source database.
* If the source database does not contain a field with embeddings, then the https://debezium.io/blog/2025/04/02/debezium-3-1-final-released/#new-features-and-improvements-ai[FieldToEmbedding SMT] is used to enrich change events with vector embeddings.
* Milvus sink writes the vector data into Milvus.
* Milvus stores and indexes the vectors for fast similarity search.

=== Data pipeline

Our organization sources documents in an https://arxiv.org/[arXiv service] that provides scholarly articles for download in different formats.
The test application downloads a requested article based on its identifier and stores it in a PostgreSQL table.

The PostgreSQL table is created with the following https://github.com/debezium/debezium-examples/blob/main/ai-rag/config-postgres/ai-sample-data.sql[DDL]:
[source,sql]
----
CREATE TABLE documents (
  id VARCHAR(64) PRIMARY KEY,
  metadata JSON,
  text TEXT
);
ALTER TABLE documents REPLICA IDENTITY FULL;
----

The replica identity of the table is set to `FULL`, so Debezium preserves the original state of a row in update and delete messages.
Our demo doesn't require preservation of the original row state, but being able to refer back to the original state is useful for some implementations.

Upon user request the application will download the document in text form and store it in the table.
Debezium stores the document identifier in the `id` field of the event; the textual representation of the article in the `text` field; and JSON metadata `{"id:" "<document id>"}` in metadata.
The table does not provide a column with embeddings, so Debezium must use its `FieldToEmbedding` SMT (described later) to calculate them.

In our environment, we run a local LLM that is based on the Ollama LLM framework.
For the model, we selected https://ollama.com/library/granite3.1-dense:2b[granite3.1-dense:2b], a text-only model that optimized for RAG.
Our model is one of large family of open-source https://huggingface.co/ibm-granite[IBM Granite models], but the application is not limited to it and can use an arbitrary model.

Debezium Server provides an interface between the PostgreSQL store and the Milvus sink.
Because embeddings are not provided, we can use the https://github.com/debezium/debezium-examples/blob/main/ai-rag/config-server/application.properties#L16[Debezium FieldToEmbedding SMT] to calculate them and store them a field named `vector`.

Our application uses LangChain4j Milvus store module internally so we will keep the default collection structure https://github.com/langchain4j/langchain4j/blob/main/langchain4j-milvus/src/main/java/dev/langchain4j/store/embedding/milvus/MilvusEmbeddingStore.java[expected by it]

* `id` - `VarChar`
* `metadata` - `JSON`
* `text` -`VarChar`
* `vector` - `FloatVector`

There is a known https://github.com/langchain4j/langchain4j/issues/2834[issue] in the module that causes an application failure when the store is empty.
We are going to store one dummy document in the database (and thus in Milvus) to work around it.

== AI Application

The AI application is the application that interacts with LLM and extends the prompt with data loaded from Milvus stored base on the data and prompt embeddings similarity.

The demo application is a command-line written using https://quarkus.io/[Quarkus framework].
For AI features it uses Quarkus https://docs.quarkiverse.io/quarkus-langchain4j/dev/index.html[LangChain4j extension], specifically https://docs.quarkiverse.io/quarkus-langchain4j/dev/ollama.html[Ollama LLM] and https://docs.quarkiverse.io/quarkus-langchain4j/dev/milvus-store.html[Milvus Store] for RAG.

The AI service is registered via the https://github.com/debezium/debezium-examples/blob/main/ai-rag/client/src/main/java/io/debezium/examples/airag/Chat.java[Chat] class.

[source,java]
----
package io.debezium.examples.airag;

import dev.langchain4j.service.SystemMessage;
import dev.langchain4j.service.UserMessage;
import io.quarkiverse.langchain4j.RegisterAiService;

@RegisterAiService(retrievalAugmentor = MilvusRetrieavalAugmentor.class)
public interface Chat {

    @SystemMessage("You are an expert that provides short summaries.")
    String chat(@UserMessage String message);
}
----

The module itself is configured in https://github.com/debezium/debezium-examples/blob/main/ai-rag/client/src/main/resources/application.properties[application.properties].

----
quarkus.langchain4j.ollama.base-url=http://localhost:11434
quarkus.langchain4j.ollama.chat-model.model-id=granite3.1-dense:2b
quarkus.langchain4j.ollama.embedding-model.model-id=granite3.1-dense:2b
quarkus.langchain4j.ollama.timeout=120s
----

RAG is enabled using the `retrievalAugmentor` parameter on the`@RegisterAiService` annotation and is implemented in the https://github.com/debezium/debezium-examples/blob/main/ai-rag/client/src/main/java/io/debezium/examples/airag/MilvusRetrieavalAugmentor.java[MilvusRetrieavalAugmentor] bean.

[source,java]
----
@ApplicationScoped
public class MilvusRetrieavalAugmentor implements Supplier<RetrievalAugmentor> {

    private final RetrievalAugmentor augmentor;

    MilvusRetrieavalAugmentor(MilvusEmbeddingStore store, EmbeddingModel model) {
        EmbeddingStoreContentRetriever contentRetriever = EmbeddingStoreContentRetriever.builder()
                .embeddingModel(model)
                .embeddingStore(store)
                .maxResults(3)
                .build();
        augmentor = new RetrievalAugmentorDecorator(DefaultRetrievalAugmentor
                .builder()
                .contentRetriever(contentRetriever)
                .build());
    }

    @Override
    public RetrievalAugmentor get() {
        return augmentor;
    }

    private class RetrievalAugmentorDecorator implements RetrievalAugmentor {

        private final RetrievalAugmentor delegate;

        public RetrievalAugmentorDecorator(RetrievalAugmentor delegate) {
            this.delegate = delegate;
        }

        @Override
        public AugmentationResult augment(AugmentationRequest augmentationRequest) {
            Log.infof("Requested augmentation of %s", augmentationRequest.chatMessage());
            final var result = delegate.augment(augmentationRequest);
            Log.infof("Result of augmentation is %s", result.contents());
            return result;
        }
    }
}
----

The `EmbeddingStoreContentRetriever` class is responsible for querying the Milvus vector database and enhances the prompt context with the three most similar documents.
The class itself also provides the `RetrievalAugmentorDecorator`, which logs the detail of the augmentation operation.

The Milvus embedding store is again configured in https://github.com/debezium/debezium-examples/blob/main/ai-rag/client/src/main/resources/application.properties[application.properties].

----
quarkus.langchain4j.milvus.host=localhost
quarkus.langchain4j.milvus.port=19530
quarkus.langchain4j.milvus.create-collection=false
quarkus.langchain4j.milvus.collection-name=demo_ai_documents

# These two settings are not supported by the current version of Quarkus Langchain4j extension
# Also field with text cannot be overriden and is default text
quarkus.langchain4j.milvus.primary-field=id
quarkus.langchain4j.milvus.vector-field=vector
----

== Demo

The demo is composed of two components

* Docker Compose configuration https://github.com/debezium/debezium-examples/blob/main/ai-rag/docker-compose.yml[file] that starts all services.
* Java CLI application in https://github.com/debezium/debezium-examples/tree/main/ai-rag/client[client] directory that emulates both data pipeline and AI application.

=== Start deployment

In *Terminal 1* execute command and wait for the containers to start.

----
$ docker-compose up --build
----

The command will extend the standard Debezium Server image with the `debezium-ai-embeddings-ollama` module (the AI embeddings modules are not by default included).
PostgreSQL (`postgres`), Milvus (`milvus`), Debezium Server (`debezium-server`) and ollama (`ollama`) containers are started.

In *Terminal 2* execute this command to start the Granite LLM model.

----
$ docker exec -it ollama ollama run granite3.1-dense:2b
----

We need to make sure that we are testing the application with facts that the model is unaware of.
First, we will check the model's cut-off date (what's the latest data the model has seen).

----
>>> What is your cut off date?
My knowledge cut off date is April 2024. I can provide information and answer questions based on data up to 
that point. For more recent events or discoveries, I'm unable to include those details in my responses as 
they weren't available at the time of my training data. If you have any questions within this timeframe, 
feel free to ask!
----

Based on that fact we selected paper https://arxiv.org/abs/2504.05309v1[2504.05309v1] (IterQR: An Iterative Framework for LLM-based Query Rewrite in e-Commercial Search System) as the sample of the new knowledge.
It was published in February 2025 so after cut off date and contains very specific keyword - `IterQR`.
We will test the model by asking about the framework.

----
>>> Describe IterQR framework in 20 words.
Iterative Quantized Ridge Regression (IterQR), a scalable method for large-scale regression, iteratively 
refines coefficients via quantization and ridge regression techniques to minimize computational complexity 
while maintaining accuracy.
----

The answer is completely unrelated to the framework and exhibits traits of https://en.wikipedia.org/wiki/Hallucination_(artificial_intelligence)[hallucination].
The model does not know about the fact so it invents its own without any connection to reality.
When model is asked multiple times it will provide different and unrelated descriptions.

== Conclusion

This blogpost explains how Debezium 3.1 can be integrated into AI workflows, particularly those using Retrieval-Augmented Generation (RAG).
Debezium captures real-time changes from a database and feeds them into vector databases.
These updates are essential for keeping AI systems current with fresh, domain-specific data.
The example setup involves PostgreSQL, Debezium Server, Milvus, and Granite LLM (with embeddings).
This architecture enables intelligent applications that respond with accurate, up-to-date information.
