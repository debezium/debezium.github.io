Hey community!

After a long period of development and testing, we are excited to announce that
the shared sink framework is now the default in Debezium 3.8.0.Alpha1.

This framework introduces a new buffer and batch processing layer that lays the
groundwork for a unified sink connector architecture across Debezium. It also provides
a shared set of functionality for all sink connectors, such as key/payload mapping, filtering fields or collection name mapping.

+++<!-- more -->+++

== What changed

Previous versions of the JDBC sink connector used a connector-specific buffering and write path.
With 3.8.0.Alpha1, the shared sink framework is now enabled by default.
This means all new deployments automatically benefit from the new batching and buffering behavior and other shared functionality that most sink connectors require.

The shared framework buffers incoming records and groups them into batches before writing them to the destination database.
How records are buffered depends on whether a primary key is configured and which batch mode is selected.

When a primary key is configured, the connector tracks records by their key within the buffer.
In *deduplication* mode (the default), if multiple records share the same key within a batch window, only the most recent record is kept.
In *passthrough* mode, all events are preserved and the buffer is flushed whenever a duplicate key is encountered, so each individual batch contains no duplicate keys.

When no primary key is configured, or when a record has a null key, each record receives a unique sequence number and both modes behave identically.

== New configuration options

The shared sink framework introduces a few new configuration properties for the JDBC sink connector:

* `keyed.message.batch.mode` controls how keyed records are batched: `deduplication` (default, last-write-wins) or `passthrough` (preserves all events, splits batches at duplicate-key boundaries).
* `cloud.events.schema.name.pattern` is a regular expression pattern to identify CloudEvents messages by their schema name (defaults to `.\*CloudEvents\\.Envelope$`).


For full details on these configuration options, see the https://debezium.io/documentation/reference/nightly/connectors/jdbc.html[JDBC sink connector documentation].

== Switching back to the legacy mode

If you run into any severe issues with the new framework, you can switch back to the legacy buffering behavior by setting the following configuration property on your connector:

[source,properties]
----
internal.enable.sces=false
----

This is an internal property and is intended as a temporary escape hatch.
Our plan is to remove the legacy code path entirely once the shared framework has proven stable, likely with the Debezium 3.8.0.Final release.

== Next steps

== We need your feedback

The shared sink framework is a significant architectural change, and we want to make sure it works well for everyone before we remove the legacy path.
If you are using the JDBC sink connector, please try the 3.8.0.Alpha1 release and let us know how it goes.

If you encounter any issues, unexpected behavior, or performance differences compared to previous versions, please open an issue on https://github.com/debezium/debezium/issues[Debezium GitHub] or reach out on https://debezium.zulipchat.com/[Zulip chat] or the https://groups.google.com/g/debezium[Debezium mailing list].

Your feedback is invaluable in helping us make the right call on when the legacy mode can be retired.
