One choice deserves stating up front, because my proposal said the opposite. I pitched this connector against Milvus 2.6, whose Woodpecker WAL replaces the external message queue, and I built it against 2.5, which still publishes every write to Kafka. Three things made me to choose 2.5: the 2.6 WAL protos were still changing in early 2026, the only prior art, Zilliz's milvus-cdc, reads the 2.5 message queue, and most production deployments are on 2.5.So, I built for the MQ and put the transport behind an abstraction rather than threading Kafka through the connector. Everything above that line is transport-agnostic: the streaming engine pulls from a `MilvusMessageConsumer` interface and works on a `RawMilvusMessage`, not on a Kafka `ConsumerRecord`, and the deserializer, the timetick ordering engine, the schema layer, the dispatcher and the offset model never learn where the bytes came from. Supporting 2.6 is then a Woodpecker implementation of that one interface plus a WAL offset type, and nothing else in the pipeline moves.

== Introduction

A vector database stores embeddings (the high-dimensional float arrays that machine-learning models produce to represent text, images, or audio) and answers nearest-neighbor queries over them: "give me the 10 stored vectors most similar to this one." Relational and keyword-search databases are built around exact matches and B-tree or inverted-index lookups, not approximate similarity search.

Milvus is an open source vector database built for that workload: scalable embedding storage, ANN indexes, and hybrid metadata-plus-vector retrieval. It underpins semantic search, retrieval-augmented generation (RAG), recommendation systems, multimodal search, and deduplication and similarity pipelines.

Once Milvus holds production data, a second problem shows up that has nothing to do with vector search: everything around Milvus needs to know when that data changes.

== Event-Driven Vector Architectures

Once Milvus becomes a live system of record for embeddings, it stops being the end of your data pipeline and becomes the middle of it. Downstream systems need its inserts and deletes as events:

* a keyword-search mirror (Elasticsearch) that must never drift from the collection,
* a cache or companion store (Redis) serving payloads next to ANN results,
* analytics pipelines counting what was added and removed,
* backup and compliance systems that need a durable record of every deletion.

Teams solve this today with two patterns, and both fail in well-understood ways. Dual writes (the application writes to both Milvus and Elasticsearch or Redis) desynchronize on the first partial failure, and there is no way to reconcile because neither side knows which write was the truth. Batch export cannot see deletes at all: by the time the export job runs, the row is already gone from Milvus, so the downstream copy keeps serving data the source deleted. Milvus's `query_iterator` is one-shot; it can copy a collection, but it cannot follow one.

The Milvus maintainers describe this gap themselves. In https://github.com/milvus-io/milvus/discussions/36683[milvus discussion #36683], a user who needed to export ~1M records from Milvus to Elasticsearch had hand-rolled a batch Java tool; the maintainers conceded that `query_iterator` "is the only way to export readable data from milvus" and pointed at CDC for "incremental export to kafka." In https://github.com/milvus-io/milvus/discussions/17088[discussion #17088], maintainers confirmed that a change-subscription interface was "still waiting for design." Zilliz built a dedicated CDC daemon, https://github.com/zilliztech/milvus-cdc[milvus-cdc], for active-standby disaster recovery, but it can only sink into another Milvus.

The alternative is an event-driven vector architecture: Milvus stays the source of truth for embeddings, its commit stream is published to Kafka as ordered change events, and any number of consumers subscribe independently. Adding a consumer changes nothing in the source system.

== Why a Milvus Source Connector

Milvus exposes no change stream over its gRPC API, so something has to bridge its internals to Kafka. A Debezium source connector is the natural shape for that bridge, because Debezium brings the CDC machinery for free:

* **A snapshot + streaming model**, with the handoff between them anchored to a Milvus checkpoint.
* **Ordered delivery** and Kafka Connect's standard offset management, so restarts resume from a persisted position instead of from scratch.
* **The standard Debezium change-event envelope** (`before`/`after`/`source`/`op`), which means every existing single message transform and converter in the Debezium ecosystem works unchanged.
* **The entire Kafka Connect sink ecosystem.** Once Milvus changes are Debezium events on a topic, the Elasticsearch sink, the Redis sink, the S3 sink, and the JDBC sink are all Milvus integrations, with zero custom code. This is what generalizes the milvus-cdc idea from "replicate to another Milvus" to "replicate to anything."

Three things separate this connector from relational CDC:

. **Vector-aware payloads.** Float vectors are emitted as the `io.debezium.data.FloatVector` logical type; JSON and geometry fields map to `io.debezium.data.Json`. Consumers see typed vectors, not opaque blobs.
. **No WAL, no binlog.** The connector's starting point comes from a Milvus channel checkpoint stored in etcd; from there its position is an offset into Milvus's message queue plus a timetick watermark per virtual channel.
. **TSO ordering.** Events are ordered by Milvus's own timestamp oracle (TSO) using its timetick protocol.

You reach for the connector whenever Milvus graduates from "index we can rebuild" to "system other things depend on": adding keyword or hybrid search next to vector search, keeping a scalar-prefilter companion store in sync, taking continuous incremental backups with a queryable deletion audit trail, or making Milvus the embedding source of truth after a migration.

The rest of this post takes the connector apart, which means taking a bit of Milvus apart first, and then builds a complete, reproducible example: a pgvector table in Postgres kept in sync with Milvus, where similarity search in plain SQL returns the same neighbours as Milvus.

== Dissecting Milvus and the Debezium Connector

=== The Milvus write path, and why the connector taps the message queue

Milvus publishes every write to an internal message queue before it persists it. When a client calls `insert`, `upsert`, or `delete` over gRPC, the proxy validates the request and produces messages onto a _physical channel_ (pchannel), a topic on Milvus's MQ backend. Milvus's own data nodes are consumers of that channel; consuming it is how Milvus builds its segments and applies deletes.

So the connector does what Milvus's own components do: it becomes another consumer of the pchannel. Zilliz's milvus-cdc reads the same MQ. The consequence is that capturing changes requires access to three Milvus components, not one.

. **The MQ backend (Kafka).** The connector subscribes to the pchannel topic (`milvus.pchannel.name`, e.g. `by-dev-rootcoord-dml_0`) and consumes the raw insert, delete, and timetick messages Milvus writes there. These come in two wire formats, msgpack batches and single protobuf messages, and neither is documented; the schema lives in https://github.com/milvus-io/milvus-proto/blob/master/proto/msg.proto[`msg.proto`].
. **etcd.** Milvus stores the per-channel checkpoint (a TSO and the MQ offset it had consumed up to) in etcd and does not expose it through any API, which is why the connector needs direct etcd access. This checkpoint is where streaming starts once the snapshot is done.
. **The Milvus gRPC API.** Used during the snapshot to list collections, read schemas, and query rows, and during streaming the first time a collection shows up on the channel: to resolve its primary key, and to fetch its whole schema if that first event is a delete.

An alternative design, polling collections through the API and diffing, was never seriously on the table: it cannot see deletes (the defining failure of batch export) and it cannot recover ordering. Reading the commit stream is more invasive infrastructurally (three endpoints instead of one), but it is the only design that observes what Milvus actually did, in the order it did it.

=== How collections are discovered

The connector does not require collections to be declared up front, which matters when collections are created per tenant or per model version and come and go.

* **During the snapshot**, the connector lists collections through the Milvus metadata API, filters them against `milvus.collection.include.list` / `exclude.list` (literal names or Java regular expressions), and reads each schema.
* **During streaming**, a collection is registered when its first event arrives on the pchannel. The raw insert message carries typed column data, which is enough to build the Connect schema; one `DescribeCollection` call over gRPC resolves the primary key (with a name-and-type heuristic as fallback), and if the first event is a delete, the whole schema comes from that call. The include and exclude lists are not consulted on this path: today every collection on the pchannel is streamed (see Limitations).

Each captured collection gets its own topic, named `<topic.prefix>.<database>.<collection>`. Note the database segment: the topic is `milvus.default.products`, not `milvus.products`; a sink configured with the short name finds no topic.

=== The snapshot and the handoff

The classic CDC failure mode sits at the seam between "copy the existing data" and "stream the new data": lose an event in the gap and the mirror is silently incomplete; overlap them carelessly and you resurrect a deleted row. The connector's answer is to anchor the stream at a point the snapshot is guaranteed to cover, the etcd checkpoint.

The snapshot starts by reading the channel checkpoint from etcd. That checkpoint pairs two values: a TSO and the MQ offset Milvus had consumed up to at that timestamp. The connector keeps both, then queries each included collection over gRPC with `consistency_level=Strong`, which makes Milvus answer with everything committed up to the query, and emits every row it gets back as an `op=r` snapshot-read event stamped with the checkpoint TSO. When the last collection has been read, it records `snapshot_completed = true` in the connector offsets, seeks the MQ consumer to the message after the checkpoint offset, and begins streaming from there.

The order of those two reads is what makes the handoff safe. The checkpoint is taken before the query, so everything the checkpoint covers is inside the snapshot, and everything after it is in the stream the connector is about to read: nothing is lost. What the handoff does allow is overlap. A write that lands between the checkpoint and the snapshot query appears twice, once as `op=r` and again as `op=c` when the stream replays it, and `insert.mode=upsert` on the sink is what makes the second copy harmless. Milvus's checkpoint trails its writes (by about a second in the run below), so seeded rows are exactly that case: in a run of the walkthrough's example with the checkpoint path corrected, the four seeded rows came through as four reads followed by four creates. An earlier design pinned the query to the checkpoint TSO with `guarantee_ts` to close that window; the Milvus SDK's query request has no such field, so the connector settles for at-least-once at the seam.

Milvus 2.5 stores that checkpoint under `meta/datacoord-meta/channel-cp/<vchannel>`, and the connector's default looks under `data-coord/checkpoint/binlog/channel/<pchannel>`, a key that does not exist. Out of the box it therefore finds no checkpoint, logs a warning, snapshots anyway, and starts streaming from the end of the channel, which is why the snapshot event in the walkthrough carries `"tso": 0`. A write that lands between the snapshot query and that seek would be missed. Pointing `milvus.etcd.checkpoint.path` at the real key produces the behaviour described above (checkpoint found, stream resumed from the following offset, the overlap replayed and absorbed); fixing the default is the first item on the list at the end of this post.

=== Streaming, timeticks, and strict TSO order

Once streaming, the connector deserializes each raw MQ message, but arrival order on the pchannel is not commit order. Milvus multiplexes several _virtual channels_ (vchannels) onto one pchannel, and each vchannel makes progress independently; a message that arrives later may carry an earlier commit timestamp.

Milvus solves this internally with the timetick protocol, and the connector implements the same watermark logic in its timetick ordering engine:

* Every event carries a TSO, a timestamp from Milvus's central timestamp oracle, which defines the global commit order.
* Each vchannel periodically publishes a _timetick_: a promise that it will never again produce an event older than that tick.
* The engine buffers incoming events and maintains a global watermark, the minimum of the latest timeticks across all vchannels. Once the watermark reaches an event's TSO, no vchannel can still produce anything older, so the event is released.

A four-message example shows the mechanism. Two vchannels, A and B, share one pchannel, and the connector reads, in arrival order: an event from A with TSO 105, an event from B with TSO 101, a timetick of 110 from A, and a timetick of 108 from B. The two events arrived in the wrong order, so the engine holds both in its buffer, sorted by TSO. Once both ticks are in, the watermark is the smaller of the two, 108, and every buffered event with a TSO at or below it is safe to release, because neither vchannel can produce anything older. The engine emits the event with TSO 101 and then the one with TSO 105, in strict TSO order, the reverse of how they arrived. An event with a TSO above 108 would stay buffered until a later round of ticks lifted the watermark past it.

Downstream consumers therefore observe changes in exactly the order Milvus committed them, across collections and across vchannels. Two decisions in that engine cost me the most to get right:

**Deletes sort before inserts within one TSO.** Milvus implements an upsert as a delete followed by an insert at a single TSO. Since the pair shares a timestamp, the engine must impose an order within the bucket, and it must be delete first: a consumer that applies insert-then-delete ends up with the row deleted after an upsert. An early version of the connector got this wrong, and no unit test noticed; the end-to-end demo did, when an upserted product vanished from Elasticsearch, the sink in an earlier iteration of the demo. (You'll see the corrected pair, sharing one TSO, in the walkthrough.)

**Liveness beats strictness under stall.** The watermark only advances if every vchannel keeps ticking. If one goes quiet (a rebalance, an idle shard), strict ordering would buffer events forever. The `milvus.timetick.stall.timeout.ms` setting bounds this: once the watermark has not moved for that long (30 seconds by default) while events are waiting, the engine force-flushes what it has, logging that strict TSO ordering was relaxed, rather than halting the pipeline. It is a deliberate trade: strict ordering and roughly a second of commit-to-queryable latency on the healthy path, delivery instead of strictness when a channel goes silent.

=== Offsets: how progress is tracked

The connector's offset (what Kafka Connect persists to resume from) is its position in Milvus's message queue: the Kafka offset of the last message read from the pchannel, the latest timetick seen per vchannel, the etcd checkpoint TSO the snapshot started from, and the `snapshot_completed` flag.

One caveat sits in that list. The MQ position is advanced as messages are polled, before the events they carry have cleared the ordering buffer, and the offset attached to each emitted record is that latest polled position. If the connector crashes while events are still buffered, the restart seeks past them and they are lost. The window is short, the time events wait in the buffer, but it exists, so delivery is not strictly at-least-once in the current build. What is safe by construction is the snapshot: until `snapshot_completed` is committed, a restart re-runs it in full, which is why an idempotent, primary-key-addressed sink matters. One early demo run proved that point: crash-restarts duplicated the snapshot, producing 3,001 events on the topic for a 1,001-row collection, yet Elasticsearch converged to exactly 1,001 documents, because the Milvus PK was the ES document `_id`.

== Use Case: Keeping Postgres (pgvector) in Sync with Milvus

Two services share one product corpus. An _ingestion service_ owns writes: it embeds product data and inserts, upserts, and deletes rows in Milvus, the source of truth for the vectors and the engine that answers high-throughput ANN queries. Everything else about the business (orders, inventory, pricing, the reporting queries) already lives in Postgres, and the questions the back office asks are half vector, half relational: "the ten products most similar to this one that are still in stock," "which listings are near-duplicates of each other," "how far apart are two categories' embeddings on average." With https://github.com/pgvector/pgvector[pgvector], each of those is a single SQL query with a join, provided the embeddings are in Postgres. Today they get there through a nightly batch copy that cannot see deletes, or not at all. The ingestion service should not know Postgres exists, and Postgres should hold the same vectors Milvus does, current to within a second.

The pipeline that delivers it is a Debezium source feeding a Debezium sink, with no transforms and no custom code anywhere.

=== Prerequisites

* Docker + Docker Compose, with ≥8 GB free RAM (six containers: Milvus with its etcd and MinIO, Kafka, Kafka Connect, Postgres)
* `curl` for everything that talks to Milvus and Connect, and `jq` for the pretty-printing in this post

=== Step 1: Get the stack running

The connector is not in the Debezium Connect image yet, so its released plugin archive is unpacked from Maven Central into the example's `plugins/` directory, which the Compose file mounts into Connect. Everything else is one `docker compose up`, with the repository's `.env` file supplying the Debezium image version. That two-line fetch is in the example's https://github.com/debezium/debezium-examples/blob/main/milvus-to-pgvector/README.md#get-the-milvus-connector[README] and there is no point repeating it here; pick the walkthrough up once the plugin is in place:

[source,bash]
----
DC='docker compose --env-file ../.env -f docker-compose.yaml'   # shorthand for the rest of the walkthrough
$DC up -d
until curl -sf localhost:9091/healthz; do sleep 5; done          # Milvus needs about a minute
curl -s localhost:8083/connector-plugins | grep -o -e MilvusConnector -e JdbcSinkConnector
# JdbcSinkConnector
# MilvusConnector
----

If `MilvusConnector` is missing, `plugins/debezium-connector-milvus` is empty: Docker creates an empty directory for a missing bind-mount source instead of failing.

Six services come up: Milvus standalone with its etcd and MinIO, one Kafka that serves as both Milvus's MQ and Connect's broker, Kafka Connect with the plugin mounted, and Postgres from the official pgvector image. The one file worth reading is https://github.com/debezium/debezium-examples/blob/main/milvus-to-pgvector/milvus-user.yaml[`milvus-user.yaml`]. It points Milvus at the etcd and MinIO containers, puts it on Kafka as its MQ backend, which is the connector's single hard deployment requirement, and sets one DML channel, which is why the pchannel throughout is `by-dev-rootcoord-dml_0`. The Debezium JDBC sink needs no installation; it ships inside the Connect image.

=== Step 3: The same four rows, after the source connector

https://github.com/debezium/debezium-examples/blob/main/milvus-to-pgvector/source-milvus.json[`source-milvus.json`] is pointing the connector at the three touchpoints: `milvus.uri` for the gRPC endpoint, `milvus.etcd.endpoints` with `milvus.etcd.root.path` for the checkpoint, and `milvus.kafka.bootstrap.servers` with `milvus.pchannel.name` for the MQ. One setting needs a word, `milvus.wire.format=proto_single`, which has to be set explicitly because the `auto` default fails on the first streamed message.

[source,bash]
----
curl -s -X POST localhost:8083/connectors -H 'Content-Type: application/json' -d @source-milvus.json
CONSUME="$DC exec -T kafka /kafka/bin/kafka-console-consumer.sh --bootstrap-server kafka:9092 --topic milvus.default.products"
$CONSUME --from-beginning --max-messages 4 --timeout-ms 20000 | jq -r '.payload.op' | sort | uniq -c
#    4 r
$CONSUME --partition 0 --offset 0 --max-messages 1 | jq -c '.schema.fields[] | select(.field=="after") | .fields[] | select(.field=="embedding")'
# {"type":"array","items":{"type":"float","optional":false},"optional":true,"name":"io.debezium.data.FloatVector","version":1,"field":"embedding"}
$CONSUME --partition 0 --offset 0 --max-messages 1 | jq '.payload'
----

----
{
  "before": null,
  "after": {
    "pk": 1001,
    "name": "trail running shoes",
    "category": "outdoor",
    "price": 89.99,

Row 1001 from the table above, now a Debezium change event on `milvus.default.products` (`<topic.prefix>.<database>.<collection>`), with the embedding intact and carrying a type name, and with a key Struct holding `pk` that is not shown here. Four events, all `op=r`, one per seeded row. Nobody declared that schema to the connector; it read it from Milvus during the snapshot.

==== What the connector takes responsibility for

That one event is small, but almost everything a CDC pipeline needs is already decided by the time it lands on the topic. The connector owns:

* **The snapshot and the handoff.** It lists collections through the Milvus metadata API, pages through each one with `consistency_level=Strong` at `milvus.snapshot.batch.size` rows a time (1,000 by default, so a big collection never has to come back in one response), emits every row as `op=r`, then starts streaming from the etcd channel checkpoint and records `snapshot_completed` in its offsets, so a restart resumes instead of re-reading everything. `snapshot.mode` takes `initial`, `never`, `recovery` and `when_needed`.
* **Schema, without declarations.** Collection schemas come from Milvus during the snapshot and from the first event while streaming, with one `DescribeCollection` call to resolve the primary key. Collections that appear later are picked up on their own.
* **Every Milvus field type, not only float vectors.** Bool, the Int8 through Int64 family, Float and Double, VarChar and Text, Array, JSON and Geometry as `io.debezium.data.Json`, and the whole vector family: `FloatVector` as the typed logical vector in the event above, BinaryVector, Int8Vector, Float16Vector and BFloat16Vector as bytes, SparseFloatVector as JSON. `decimal.handling.mode` decides whether Float and Double arrive as floats, as Connect `Decimal`, or as strings. That `FloatVector` type name is what lets a generic JDBC sink create a pgvector column one step from now instead of a float array.
* **Identity.** Every event is keyed by a Struct holding the Milvus primary key, which is what makes downstream idempotent: upsert on conflict, delete by key, replay safely.
* **Order.** Events leave in strict Milvus TSO order across vchannels via the timetick watermark, with the delete ahead of the insert inside an upsert's shared timestamp.
* **The Debezium envelope.** `before`, `after`, `source`, `op`, plus tombstones after deletes, which means every existing Debezium SMT, converter and sink works against Milvus with no new code. Postgres is one sink file; Elasticsearch, Redis or S3 is a different sink file against the same topic, and Milvus never learns that a consumer was added.
* **Both Milvus wire formats.** msgpack batches and single protobuf messages are both deserialized. If a message in the other format shows up, which is what a rolling Milvus upgrade produces, the task fails with a typed mismatch error naming the topic, partition and offset rather than a parse error with no address.
* **Bounded memory.** The ordering buffer is capped by `milvus.buffer.max.events` (10,000) and `milvus.buffer.max.bytes` (64 MB). When it fills, the task stops polling the channel and drains whatever the watermark allows instead of growing until the JVM gives up.
* **Filtering and topic naming.** Include and exclude lists take literal names or Java regular expressions and select collections (on the snapshot path today, see Limitations), and each collection gets its own topic, `<prefix>.<database>.<collection>`.
* **Talking to a real cluster.** `milvus.token` for authenticated deployments, `milvus.database` to choose the database, and `milvus.kafka.*` for the consumer group, poll interval and partition the connector uses on Milvus's MQ.
* **Operability.** Pause, resume, restart and offset handling are plain Kafka Connect, with Milvus-specific metrics, heartbeats and Debezium notifications on top; the last step of the walkthrough exercises them.

One thing the registration does not mention is converters, and the example depends on the default. The Debezium Connect image runs JSON converters with schemas enabled, which is what gives the sink a Struct key to derive a primary key from and the `FloatVector` type name to act on. On a worker configured schemaless, set `key.converter.schemas.enable=true` and `value.converter.schemas.enable=true` on both connectors. (An earlier version of this demo lost a day to the schemaless variant of this mistake. You're welcome.)

=== Step 4: The final output, in Postgres

https://github.com/debezium/debezium-examples/blob/main/milvus-to-pgvector/sink-postgres.json[`sink-postgres.json`] is Debezium's own JDBC sink.

* `primary.key.mode=record_key` with `primary.key.fields=pk` makes the Milvus primary key the Postgres primary key. Every idempotency guarantee below follows from that one choice.
* `insert.mode=upsert` and `delete.enabled=true` are the entire write path: `op=r` and `op=c` become `INSERT ... ON CONFLICT (pk) DO UPDATE`, `op=d` becomes a `DELETE` by key, and the tombstone is understood.
* `schema.evolution=basic` lets the sink issue the `CREATE TABLE` from the first event's schema, which is where the `FloatVector` type name turns into a pgvector column.
* `collection.name.format=products` names the table, because the default is the topic name, `milvus.default.products`, which is not valid SQL. (Debezium 3 renamed this setting; `table.name.format` still works as a deprecated alias.)

And no `transforms` at all. A third-party sink needs transforms to unwrap the Debezium envelope and extract the key, plus settings that turn tombstones into deletes; the Elasticsearch version of this demo needed two. The Debezium JDBC sink reads Debezium envelopes natively, so its config is connection details and policy, nothing else.

[source,bash]
----
PSQL="$DC exec -T postgres psql -U postgres"
$PSQL -c 'CREATE EXTENSION vector'
# register the sink with the same POST as the source, this time with sink-postgres.json
$PSQL -c '\d products'

`halfvec` (16-bit floats) is Debezium's type pairing for `FloatVector`, and the `0.099975586` where Milvus holds `0.1` is that rounding, not a bug: every pgvector distance operator works on the column, and Step 6 shows it ranking neighbours identically to Milvus. If you need strict 32-bit fidelity, create the table yourself with `embedding vector(4)` before registering the sink; `schema.evolution=basic` only adds missing columns, so the sink writes into what you defined.

=== Step 5: Changes, in order, within a second

Milvus has no SQL shell, so the "ingestion service" is three `curl` calls against its REST API, and the https://github.com/debezium/debezium-examples/blob/main/milvus-to-pgvector/README.md#change-data-in-milvus[README] carries them verbatim: insert pk 1005, a camping stove at 59.99; upsert the same row at 49.99; delete pk 1004, the building blocks. What is worth showing is not the calls but what they leave on the topic.

[source,bash]
----
$CONSUME --partition 0 --offset 4 --max-messages 6 --formatter-property print.offset=true \
  | sed -E 's/^Offset:([0-9]+)\t/\1 /' | while read -r off val; do
      if [ "$val" = null ]; then echo "[offset $off] TOMBSTONE (null value)"
      else echo "[offset $off] $(echo "$val" | jq -c '.payload | {op, tso: .source.tso, before, after: (.after | if . then {pk, name, price} else null end)}')"; fi
    done
----

[offset 5] {"op":"d","tso":469170993227628545,"before":{"pk":1005,"name":null,"category":null,"price":null,"embedding":null},"after":null}
[offset 6] TOMBSTONE (null value)

One Milvus upsert (offsets 5 to 7) became a delete and an insert sharing a single TSO, delete first. That is the intra-bucket ordering decision from the dissection, on the wire. The delete of pk 1004 (offsets 8 and 9) is an `op=d` with a primary-key-only `before` image, since Milvus does not publish the prior state of a deleted entity, followed by a tombstone. Postgres ends with exactly one row for pk 1005, at the new price, and no row for pk 1004:

[source,bash]
----
$PSQL -c 'SELECT pk, name, price FROM products ORDER BY pk'
#   pk  |        name         | price
# ------+---------------------+-------
#  1001 | trail running shoes | 89.99
#  1002 | cast iron skillet   |  34.5
#  1003 | wireless headphones |   129
#  1005 | camping stove       | 49.99
# (4 rows)
----

A dual-writing application cannot make the upsert guarantee; the connector inherits it from Milvus's own commit order. And the delete is the event that batch export can never see, with no delete-handling code anywhere in the pipeline.

=== Step 6: Both engines, one question

Everything so far would hold for any scalar table. The reason to pick pgvector is that the embedding arrived as a _working vector_, not an opaque payload, and the way to prove it is to ask both engines the same question. Take pk 1001's embedding as the query, ask Postgres for its three nearest neighbours by cosine distance (`<=>`, the same metric the Milvus index was built with), then ask Milvus:

[source,bash]
----
V=$($PSQL -tA -c 'select embedding from products where pk = 1001')

$PSQL -tA -c "select pk from products order by embedding <=> '$V' limit 3"
# 1001
# 1005
# 1003

curl -s -X POST localhost:19530/v2/vectordb/entities/search -H 'Content-Type: application/json' \
  -d '{"collectionName":"products","data":['"$V"'],"annsField":"embedding","limit":3,"outputFields":["pk"]}' \
  | jq -c '[.data[].pk]'
# [1001,1005,1003]
----

Identical top-3 from a SQL `ORDER BY` and from Milvus's ANN index, on vectors that travelled from Milvus through Kafka into Postgres as `halfvec`. The distances agree too: Postgres puts the camping stove at cosine distance 0.00915 from the running shoes, and Milvus reports a cosine similarity of 0.99085 for the same pair. From here, "similar to this product _and_ in stock" is a `JOIN` away.

=== Step 7: Pause, write, resume

Finally, the offset guarantees when the connector stops. The example scripts this step too, writing two rows during the pause; the run below is a wider variant of it, so the commands are inline: pause the source, insert three rows while it is down, and resume.

[source,bash]
----
curl -s -X PUT localhost:8083/connectors/milvus-source/pause
curl -s -X POST localhost:19530/v2/vectordb/entities/insert -H 'Content-Type: application/json' \
    -d '{"collectionName": "products", "data": [
          {"pk": 1006, "name": "yoga mat",         "category": "fitness", "price": 29.99,  "embedding": [0.3, 0.2, 0.6, 0.2]},
          {"pk": 1007, "name": "espresso grinder", "category": "kitchen", "price": 149.00, "embedding": [0.8, 0.2, 0.1, 0.4]},
          {"pk": 1008, "name": "board game",       "category": "toys",    "price": 39.99,  "embedding": [0.5, 0.3, 0.8, 0.2]}]}'
curl -s -X POST localhost:19530/v2/vectordb/entities/query -H 'Content-Type: application/json' \
    -d '{"collectionName":"products","filter":"pk > 0","outputFields":["count(*)"]}' | jq -c '.data'
# [{"count(*)":7}]
$PSQL -tA -c 'select count(*) from products'
# 4
curl -s -X PUT localhost:8083/connectors/milvus-source/resume
$PSQL -tA -c 'select count(*) from products'
# 7
$DC exec -T kafka /kafka/bin/kafka-run-class.sh org.apache.kafka.tools.GetOffsetShell \
  --bootstrap-server kafka:9092 --topic milvus.default.products
# milvus.default.products:0:13
----

On resume, the topic replays exactly the three missed `op=c` events and the two counts match. The topic ends at 13 records: four snapshot reads, the insert, the three records of the upsert, the two of the delete, and the three rows written while the connector was paused. No loss, no duplicates, on vanilla Kafka Connect offset management with no bespoke daemon involved.

For monitoring in anger rather than a demo: the connector exposes snapshot and streaming metrics over JMX, where the standard `MilliSecondsBehindSource` is computed from the TSO watermark and the snapshot bean reports the checkpoint TSO it started from; interval heartbeats (`heartbeat.interval.ms`) prove liveness on quiet collections.

== Limitations and What's Next

The connector is incubating, and its edges deserve stating as plainly as its features:

* **Kafka only, as Milvus's MQ backend.** Deployments backed by Pulsar or RocksMQ are not supported; the connector reads the MQ directly, so it must speak the deployment's MQ. Milvus 2.6 has no MQ at all: supporting it means a Woodpecker implementation of `MilvusMessageConsumer` and a WAL offset type, and nothing else in the pipeline changes.
* **Single task, single pchannel.** One connector instance consumes one pchannel; `tasks.max` values above 1 are ignored.
* **No** `op=u` **events.** A Milvus upsert surfaces as the delete+insert pair, not a synthesized update event.
* **PK-only** `before` **images on deletes.** Milvus does not publish the prior state of a deleted entity, so the connector cannot either.
* **Collection DDL is not emitted.** Create/drop operations are tracked internally for ordering but not yet emitted as schema-change events.
* **The default etcd checkpoint key does not match Milvus 2.5.** The snapshot runs without a checkpoint and streaming starts from the end of the channel; `milvus.etcd.checkpoint.path` can point at the real key for a known collection, but the default needs fixing in the connector.
* **Include and exclude lists apply to the snapshot only.** During streaming, every collection on the pchannel is captured.
* **Offsets can run ahead of the ordering buffer.** A crash while events are buffered can drop them; see the offsets section above.
* `milvus.wire.format=auto` **is not yet functional.** The detector exists but is not wired in; set `proto_single` (or `msgpack_batch`) explicitly for now. A fix that wires it in is in progress.
* The emitted message format may still change; the connector is not yet recommended for production use.

That list doubles as the roadmap: the checkpoint key path, Pulsar MQ support, multi-pchannel and multi-task scaling, stream-side collection filtering, offsets that trail the ordering buffer, working wire-format auto-detection, and schema-change events. If any of these matters to your use case, issues and patches are welcome. The connector lives at https://github.com/debezium/debezium-connector-milvus[debezium/debezium-connector-milvus], and the https://debezium.zulipchat.com/#narrow/stream/302533-dev[Debezium developer chat] is where design discussions happen.
