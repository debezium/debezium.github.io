There is a recurring narrative that Debezium requires Kafka.
While this was true in the project's early days, it is no longer the case, as we explained in detail,
together with several other common misconceptions, in our recent article, https://debezium.io/blog/2026/05/22/what-nobody-explains-about-debezium-2026/["What Nobody Explains About Debezium in 2026 (But Should)"].

In this article, we’ll build on that discussion by showing the recently added JDBC sink support in Debezium Server (DS) and the Debezium Management Platform (DMP),
which opens up Kafka-less data replication and migration scenarios.


+++<!-- more -->+++

Data integration, whether for one-shot migrations or continuous replication between databases, is one of the core use cases Debezium supports.
Debezium has always focused on the CDC side of the problem: capturing changes from a database and turning them into a stream of change events.
In the past, users had to develop their own consumer to write those events into a target database.
To address this, we introduced the https://debezium.io/documentation/reference/stable/connectors/jdbc.html[JDBC Sink Connector] in the `2.2.0.Beta1` release in 2023,
enabling end-to-end replication out of the box.

Today, the same capability is available through the https://debezium.io/documentation/reference/stable/operations/debezium-server.html#_jdbc[DS JDBC sink] and within the https://debezium.io/documentation/reference/stable/operations/debezium-platform.html[DMP].
This is not intended to replace Kafka Connect (KC) connectors.
Instead, it provides an alternative for users who do not have a KC cluster, or who do not need the scalability and high availability that KC offers,
and simply want to move data between two databases.
In those cases, DS or DMP can now be an attractive option, and with the upcoming https://github.com/debezium/dbz/issues/2107[native build support], DS will be able to run as a single native executable with minimal resource footprint.

== Data Integration with Debezium Server

Let’s see how simple it is to run a data migration pipeline with a few commands.

The requirement is to have the source and the destination database up and running, so we can easily start them up with the following `Docker Compose` file:

.infrastructure-compose.yaml
[source,yaml]
----
services:
  postgres:
    container_name: postgres
    image: quay.io/debezium/example-postgres:3.6
    ports:
      - "5432:5432"
    environment:
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=postgres
    networks:
      - backend

  mysql:
    container_name: mysql
    image: mysql:9.1
    ports:
      - "3306:3306"
    environment:
      - MYSQL_ROOT_PASSWORD=debezium
      - MYSQL_DATABASE=target_db
    networks:
      - backend

networks:
  backend:
    name: debezium-jdbc-backend
----

running the Docker Compose command below:

[source, shell]
-----
docker compose -f infrastructure-compose.yaml up -d
-----

Once you have this, you can start replicating your data with the following command:

[source, shell]
-----
 docker run --name inventory-pipeline -d \
    -v $(pwd)/application.properties:/debezium/config/application.properties:z \
    -p 8080:8080 \
    --network debezium-jdbc-backend \
    quay.io/debezium/server:nightly
-----

The configuration used is the following

.application.properties
[source,properties]
----
debezium.sink.type=jdbc
debezium.sink.jdbc.connection.url=jdbc:mysql://mysql:3306/target_db
debezium.sink.jdbc.connection.username=root
debezium.sink.jdbc.connection.password=debezium
debezium.sink.jdbc.insert.mode=upsert
debezium.sink.jdbc.primary.key.mode=record_key
debezium.sink.jdbc.schema.evolution=basic
debezium.sink.jdbc.delete.enabled=true
debezium.source.connector.class=io.debezium.connector.postgresql.PostgresConnector
debezium.source.offset.storage.file.filename=data/offsets.dat
debezium.source.offset.flush.interval.ms=0
debezium.source.database.hostname=postgres
debezium.source.database.port=5432
debezium.source.database.user=postgres
debezium.source.database.password=postgres
debezium.source.database.dbname=postgres
debezium.source.topic.prefix=migration
debezium.source.schema.include.list=inventory
quarkus.log.console.json=false
----

Now, let’s check that the data has been correctly migrated to the MySQL database.

[source, shell]
----
docker exec -it mysql mysql -uroot -pdebezium target_db -e "SELECT * FROM migration_inventory_customers;"
docker exec -it mysql mysql -uroot -pdebezium target_db -e "SELECT * FROM migration_inventory_products;"
docker exec -it mysql mysql -uroot -pdebezium target_db -e "SELECT * FROM migration_inventory_orders;"
docker exec -it mysql mysql -uroot -pdebezium target_db -e "SELECT * FROM migration_inventory_products_on_hand;"
----

Then let’s add a new customer.

[source, shell]
----
docker exec -it postgres psql -U postgres -d postgres -c \
"INSERT INTO inventory.customers (first_name, last_name, email) VALUES ('John', 'Doe', 'john.doe@example.com');"
----

and verify that it is replicated on the destination

[source, shell]
----
docker exec -it mysql mysql -uroot -pdebezium target_db -e "SELECT * FROM migration_inventory_customers;"
----

There we go! You have now a data replication pipeline migrating data from PostgreSQL to MySQL, in real time, just running a single container!

Also, for those who are on board on Kubernetes, you can run the same pipeline through the https://debezium.io/documentation/reference/stable/operations/debezium-operator.html[Debezium Operator].
After having the Operator installed on you cluster you can just create the following CRD

.DebeziumServer custom resource
[source, yaml]
----
  apiVersion: debezium.io/v1alpha1
  kind: DebeziumServer
  metadata:
    name: jdbc-sink-example
    namespace: debezium
  spec:
    image: quay.io/debezium/server:latest
    sink:
      type: jdbc
      config:
        connection.url: jdbc:mysql://mysql:3306/target_db
        connection.username: root
        connection.password: debezium
        insert.mode: upsert
        primary.key.mode: record_key
        schema.evolution: basic
        delete.enabled: "true"
    source:
      class: io.debezium.connector.postgresql.PostgresConnector
      config:
        database.hostname: postgres
        database.port: "5432"
        database.user: postgres
        database.password: postgres
        database.dbname: postgres
        topic.prefix: migration
        schema.include.list: inventory
        table.include.list: inventory.customers,inventory.products,inventory.products_on_hand,inventory.orders
    quarkus:
      config:
        log.console.json: "false"
----

== Data Integration with Debezium Management Platform

Debezium Platform lets you manage your pipeline with a modern UI focusing on its design without worry about the deployment.
Once you have https://debezium.io/documentation/reference/stable/operations/debezium-platform.html#_installation[installed] it on you Kubernetes cluster in `debezium-platform` namespace, you can create your data replication pipeline with easy

[NOTE]
====
Through the https://summerofcode.withgoogle.com/[Google Summer of code initiative] we have a contributor working to support host based deploy on the Debezium Platform.
This means that in future you could deploy pipeline also on VMs, on-prem machine and cloud.
Keep an eye on https://github.com/debezium/dbz/issues/2085
====

You can create the following resources to create the source and destination databases

.Source PostgreSQL (CDC-enabled, example postgresql database):
[source, shell]
----
  apiVersion: v1
  kind: Secret
  metadata:
    name: postgresql-credentials
    namespace: debezium-platform
  type: Opaque
  stringData:
    POSTGRES_USER: debezium
    POSTGRES_PASSWORD: debezium
    POSTGRES_DB: debezium
  ---
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: postgresql
  spec:
    replicas: 1
    selector:
      matchLabels:
        app: postgresql
    template:
      metadata:
        labels:
          app: postgresql
      spec:
        containers:
          - name: postgresql
            image: quay.io/debezium/example-postgres:latest
            ports:
              - containerPort: 5432
            envFrom:
              - secretRef:
                  name: postgresql-credentials
  ---
  apiVersion: v1
  kind: Service
  metadata:
    name: postgresql
    namespace: debezium-platform
  spec:
    selector:
      app: postgresql
    ports:
      - port: 5432
        targetPort: 5432
----

.Destination PostgreSQL (vanilla, JDBC sink target):
[source, shell]
----
  apiVersion: v1
  kind: Secret
  metadata:
    name: postgresql-dest-credentials
    namespace: debezium-platform
  type: Opaque
  stringData:
    POSTGRES_USER: debezium
    POSTGRES_PASSWORD: debezium
  ---
  apiVersion: apps/v1
  kind: Deployment
  metadata:
    name: postgresql-dest
    namespace: debezium-platform
  spec:
    replicas: 1
    selector:
      matchLabels:
        app: postgresql-dest
    template:
      metadata:
        labels:
          app: postgresql-dest
      spec:
        containers:
          - name: postgresql
            image: postgres:16-alpine
            ports:
              - containerPort: 5432
            envFrom:
              - secretRef:
                  name: postgresql-dest-credentials
  ---
  apiVersion: v1
  kind: Service
  metadata:
    name: postgresql-dest
    namespace: debezium-platform
  spec:
    selector:
      app: postgresql-dest
    ports:
      - port: 5432
        targetPort: 5432
----

It is worth to mention that you can do the same thing via the REST API with the following

.Create source connection:
[source, shell]
----
curl -X POST http://platform.debezium.io/api/connections \
-H 'Content-Type: application/json' \
-d '{
"type": "POSTGRESQL",
"name": "source-postgresql",
"config": {
"hostname": "postgresql",
"port": 5432,
"username": "debezium",
"password": "debezium",
"database": "debezium"
}
}'
----

.Create destination connection:
[source, shell]
----
curl -X POST http://platform.debezium.io/api/connections \
-H 'Content-Type: application/json' \
-d '{
"type": "JDBC",
"name": "dest-postgresql-jdbc",
"config": {
"url": "jdbc:postgresql://postgresql-dest.debezium-platform.svc.cluster.local:5432/debezium",
"username": "debezium",
"password": "debezium"
}
}'
----

.Create source (use the connection id from step 1):
[source, shell]
----
curl -X POST http://platform.debezium.io/api/sources \
-H 'Content-Type: application/json' \
-d '{
"name": "pg-source",
"type": "io.debezium.connector.postgresql.PostgresConnector",
"schema": "dummy",
"connection": { "id": 1 },
"config": {
"schema.include.list": "inventory",
"table.exclude.list": "inventory.geom,inventory.spatial_ref_sys",
"topic.prefix": "inventory"
}
}'
----

.Create destination (use the connection id from step 2):
[source, shell]
----
curl -X POST http://platform.debezium.io/api/destinations \
-H 'Content-Type: application/json' \
-d '{
"name": "jdbc-destination",
"type": "jdbc",
"schema": "dummy",
"connection": { "id": 2 },
"config": {
"insert.mode": "upsert",
"primary.key.mode": "record_key",
"schema.evolution": "basic"
}
}'
----

.Create pipeline (use the source and destination ids from steps 3 and 4):
[source, shell]
----
curl -X POST http://platform.debezium.io/api/pipelines \
-H 'Content-Type: application/json' \
-d '{
"name": "database-migration",
"source": { "id": 1 },
"destination": { "id": 1 },
"logLevel": "INFO"
}'
----

== Conclusion
We have seen how simple it is to build a data migration pipeline without requiring a Kafka cluster.

There are still some limitations in the current DS JDBC sink implementation.
For example, while Kafka Connect (KC) allows processing to be parallelized by configuring `tasks.max`, this capability is not yet available in DS.

Similarly, if you want to process records from only a specific set of tables, there is no direct equivalent to the KC topics configuration.
Instead, you need to filter records at the source, using the `table.include.list` configuration, or apply a transformation to select the desired events.

These are known limitations, and addressing them is already on our radar for future releases.
