As summer winds down, we're pleased to announce **Debezium 3.6.2.Final**, a maintenance release packed with correctness, performance, and security improvements across the entire connector family.

Among the highlights, incremental snapshots now work on PostgreSQL read-only replicas, and a fix to Debezium's internal caching keeps long-running connectors from gradually losing throughput.
On the security front, Debezium Server now masks passwords in its logs, and the PostgreSQL JDBC driver has been bumped to 42.7.13 to address CVE-2026-54291.
Rounding things out are a healthy batch of DDL parser fixes for MySQL and Oracle, data-correctness fixes for incremental snapshots and heartbeat error handling, and improved PostgreSQL parallel snapshot consistency.

Read on for the full details!

=== Debezium Core

==== Fix for gradual throughput loss in long-running connectors

Connectors could slowly lose throughput the longer they ran, with no errors logged and no change in workload to explain it.
One production deployment saw its rate fall from roughly 90K records per minute at startup to 12,500 after eighteen hours, with a single thread consuming nearly a full CPU core.

The cause was in `BoundedConcurrentHashMap`, the fixed-size cache Debezium uses across the runtime for schemas, topic names, prepared statements, and similar lookups.
Its internal housekeeping ran when an entry was read, but not when an entry already in the cache was overwritten, so a caller that only ever writes never triggered it, and an internal tracking list grew without bound.
Checking the length of that list also became more expensive as it grew, so the cost of processing each record climbed along with it.

Writes now trigger the same housekeeping that reads always have, and the list length is tracked as it changes rather than recounted on every access.
Cache sizes, eviction behavior, and the entries retained are all unchanged.
(https://github.com/debezium/dbz/issues/2255[dbz#2255])

[id="new-features-and-improvements-debezium-postgresql"]
=== Debezium for PostgreSQL

==== Incremental snapshots on read-only replicas

Incremental snapshots on PostgreSQL read-only replicas previously failed with `cannot execute pg_current_xact_id() during recovery` error, because the snapshot logic attempted to create a new transaction ID, which is not permitted on replicas.
This caused connectors running with `read.only=true` to enter an infinite restart loop when an incremental snapshot was triggered.

This has been corrected, and users running against a hot standby can now use incremental snapshots for re-snapshotting subsets of data without restarting the connector or switching to the primary.
(https://github.com/debezium/dbz/issues/1080[dbz#1080], https://github.com/debezium/dbz/issues/2431[dbz#2431])

[id="new-features-and-improvements-container-images"]
=== Container Images

==== PostgreSQL GUC logical decoder support

A recent PostgreSQL security update for PostgreSQL 15 and later introduces a new `output_plugin_libraries` GUC setting that restricts which logical decoding output plugins can start.
By default, PostgreSQL now permits only `pgoutput` and `test_decoding`, so any updated PostgreSQL instance, including publicly available container images, will reject the `decoderbufs` plugin.

The Debezium PostgreSQL container images now explicitly configure this GUC to include `decoderbufs` alongside the default plugins.
For users who have not yet migrated to `pgoutput` and continue to use `decoderbufs`, the `output_plugin_libraries` setting must be specified in the PostgreSQL server configuration to include `decoderbufs`.
(https://github.com/debezium/dbz/issues/2434[dbz#2434])
